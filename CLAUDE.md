# CLAUDE.md — working rules for this repository

## Your role

You are the product and standards architect of NovaTrail. In this repository the documents are the product: write them so that an engineer, a module author or a lawyer can act on them without asking what you meant. The bar they meet is in the shared rules below.

- [repo-template/](repo-template/README.md) — the template every other NovaTrail repository starts from (repositories 2.2).

test -race`, govulncheck and go-licenses, at the versions the justfile pins; `ci-test` writes their coverage to `coverage/go.out`, and a task that touches Go code ends with them green. `just types-check` checks those types, the packages `types/formatv0` and `types/formatv0/open`, in Go and in TypeScript beside it, which `just types` generates from the schemas by `tools/types` (R72, R73). They must be what it generates, file for file. Each value of `format/` that passes a schema must be read by its Go type and written back as it was, by `tools/types/roundtrip`, a module of its own too. And `tsc` must take it as a value of its TypeScript type, from the npm package `@altnovatrail/spec` packed of the working tree; a task that changes a schema runs `just types` and ends with it green. Beside them, `types/canvas/` holds the types of the element `<novatrail-canvas>`, the contract of `canvas` and `app`, which are written by hand and which `just types` leaves as they are. `tsc` takes them by `tools/types/canvas.check.ts`, with the DOM, from the same package (R74). CI (`.github/workflows/ci.yml`) runs all five, with the tests of `tools/`, in the `toolchain` stage on every pull request and on `main`; what it runs and what holds a merge is R30. The tests run as `just coverage` runs them, all at once with their coverage — those of `tools/`, then those of the Go modules by `ci-test` —, which a job of its own sends to Codecov by OIDC, with no secret (R48). Beside them run the checks every NovaTrail repository shares — secrets, DCO, CodeQL, Scorecard and, on the Go code, `go.yml`, which runs the four `ci-` recipes as "Go / lint", "Go / test", "Go / vuln" and "Go / licenses" (the 2026-11-01 amendment to R30) — from `.github`'s shared workflows, pinned to a release of it by SHA (R03 .github); rule 12 of RUN.md has their findings closed before the next task. A release of spec, and its tag, comes out by itself once CI passes on `main` (`.github/workflows/release.yml`, R31): nobody tags by hand, and `just release-version` prints the version the next release takes, refusing a commit that gives the module format a new version in the line of the release before it (R44). From the line 0.3 on, a release carries the files code takes from spec (R64): `format-<version>.tar.gz`, and from the line 0.4 on the npm package of the types for TypeScript, `altnovatrail-spec-<version>.tgz`, which from the line 0.5 on holds the types of `<novatrail-canvas>` too (R74), which the release also publishes to npm by trusted publishing, with no token (R37, R73). `just release-files <commit> <folder> <tag>` builds them, and CI builds them on every pull request; each is signed with cosign and attested with the release. The same tag is the version of the Go module, and without its `v` the version of the npm package. Another repository releases through the same recipes, `just -f spec/justfile release-version` and `release-refusal`, rather than copies of them, and its runner runs them in its `toolchain` stage by `spec/tools/toolchain/toolchain.sh`, as spec's CI and release run every check (R31). Its license checks take spec's list and spec's check of an npm lock file the same way: `just -f spec/justfile licenses-allowed` and `licenses-check-repo` (R39). A file of a NovaTrail release enters code or CI only through `just release-verify <repository> <tag> <file> [<bundle>]`, and the packages of `@altnovatrail` in an npm lock file through `just release-verify-npm <lock file>` (R77). `tools/release/verify.mjs` verifies the file's cosign bundle by sigstore-js against Sigstore's trust root, which TUF reads afresh on every run, and holds the certificate's fields to R77. What GitHub holds — the commit of the tag, the releases of `.github` and the history of its main — it reads through git, with no token, and the numeric IDs of the repositories are `tools/release/repositories.mjs`, where a new repository's ID goes (repositories 2.2). When Sigstore or GitHub cannot be read, the file is refused. Their tests, in `just release-version-test` and `just coverage`, verify files of real releases, `tools/release/test/fixtures/`, with no network. Another repository runs them the same way, `just -f spec/justfile release-verify` and `release-verify-npm`, in its `toolchain` stage. Every commit is signed off (`git commit -s`; Source Control does it by itself here, `git.alwaysSignOff`). The Markdown preview renders Mermaid diagrams (`bierner.markdown-mermaid`).

`just new-repo <name> <kind> <card>` builds a new repository's working copy in `.repos/<name>` from `repo-template/` and the latest release tag of spec, and `just new-repo-check <name>` checks it once its gaps are filled (repositories 2.2). `.repos/` is outside this repository: Source Control shows each working copy as a repository of its own. A copy there is only built, filled and committed from here, and later given the CI files every repository shares, which are the same in each (R30); the component's own work happens in its own container, opened from a clone of its repository. That work includes what the component's code adds to its CI files — the job of its language, CodeQL's languages, its Dependabot ecosystem, its release — copied from architecture 3.3 .github (the 2026-10-21 amendment to R30).
