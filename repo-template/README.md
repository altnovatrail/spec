# repo-template

The template every NovaTrail repository other than spec starts from (R21; repositories 2.2). It holds no rules of its own: a new repository follows spec's [RULES.md](../RULES.md), which its CLAUDE.md imports from the `spec/` submodule.

`just new-repo <name> <kind> <card>` builds the new repository's working copy in `.repos/<name>`, from this template as it stands at the latest release of spec, its highest `vX.Y.Z` tag:

- `files/` is the new repository. Each `{{…}}` is filled in — the repository's name, the number of its card in architecture 3, the tag of spec and the date — and each `<!-- FILL: … -->` is left for the executor to write from the component's card.
- `README.md` in `files/` starts with the status badges every repository has from its first day — CI, CodeQL, OpenSSF Scorecard, its license and five SonarCloud measures — with the repository's name in their addresses. The others come later, each with what it reports on: a release, code, coverage, an OpenSSF Best Practices entry (R48; repositories 2.3).
- `LICENSE`, `AGENTS.md` and `.devcontainer/` in `files/` are links to spec's own, so there is one copy of each. They are copied as they are; the devcontainer then gets the repository's own name and network, what its kind adds, and a start command that checks out `spec/` when a clone has left it empty.
- `kinds.json` says what each kind adds to spec's devcontainer, at exact versions: VS Code extensions (`extensions`), VS Code settings (`settings`), lines for the end of the Dockerfile's `toolchain` stage, from a file in `kinds/` (`toolchain`), and, from a folder in `kinds/` (`devcontainer`), lines for the `devcontainer` stage, its `Dockerfile`, which go before the step of Claude Code, and the files the image copies, the rest of the folder, which go into the copy's `.devcontainer/` as they are; and keys for the end of the copy's `.claude/settings.json` (`claude`), which may not be keys the template's file already sets. A key the recipe does not know stops it. `docs` adds nothing; `go` adds the Go extension, its settings that keep it from fetching tools of its own, and gopls from its lock file, `kinds/go/gopls/`, built in the `devcontainer` stage at `GOPLS_VERSION` (R102), and Claude Code's plugin `gopls-lsp` from spec's own marketplace, [claude-plugins/](../claude-plugins/README.md), through the `spec` submodule, so that a session gets gopls's diagnostics after each edit (R143); and `typescript` adds Biome's extension, Biome as TypeScript's default formatter, and the browser the tests run in: Chrome Headless Shell from Playwright's image, pinned by tag and digest, with its system libraries from a snapshot of the Ubuntu archive, as `canvas` had it (R79). Those three versions are raised in `kinds/typescript.Dockerfile`, and gopls in `kinds/go/` — its lock file with `go get -tool golang.org/x/tools/gopls@vX.Y.Z` and `GOPLS_VERSION` together, which spec's tests and `new-repo-check` hold to each other —, and a copy takes them with its next move to a tag: it takes its `.devcontainer/` from what the recipe builds, and adds its own differences again. The lock file's `go` line is the `GO_VERSION` of the toolchain stage, and spec's tests hold it there: a raise of Go raises it too. `.devcontainer/gopls/` is a Go module that no code reads, so a Go repository leaves it out of the modules its checks list, as spec leaves `repo-template/` out of `_go-modules`.
- `docs-budgets.json` in `files/` is `{}`: the new repository's documents keep within the block `repository` of spec's `tools/docs-check/budgets.json`, and the repository names in it what differs (R145).
- spec becomes a git submodule at the same tag, and everything is staged. The first commit is the author's.

Before spec has a tag, or to read a change to the template, `just new-repo-draft <name> <kind> <card> <tag>` builds the copy from the working tree instead, names the given tag in its text, and leaves git alone.

`docs-check` reads `files/` as part of spec. Its citations of spec, written with the suffix "spec", are checked against spec's documents. The template cites its own sections through a link to its own file and the word "section" or «раздел», which `docs-check` resolves inside `files/`. A bare "architecture 2" or "R03" would be checked against spec's documents instead, so the template uses those only as examples of how to cite.

In the new repository, `just -f spec/justfile docs-check-repo` checks its documents as a repository of its own: its sections and log bare, spec's with the suffix, against its spec/ submodule (R32 in spec). An example of a citation is written in code — `R03` — so that the check does not take it for one.

`just new-repo-check <name>` checks the copy once it is filled: no `{{…}}` and no FILL left, `LICENSE` and `AGENTS.md` the same as spec's, its documents passing the same check as `docs-check-repo` — links, sections, its log and tables, its citations of spec, its diagrams — no name of spec's left in the devcontainer, and the submodule at the tag that the links to spec name.
