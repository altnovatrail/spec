# repo-template

The template every NovaTrail repository other than spec starts from. It holds no rules of its own: a new repository follows spec's [RULES.md](../RULES.md), which its CLAUDE.md imports from the `spec/` submodule.

`just new-repo <name> <kind> <card>` builds the new repository's working copy in `.repos/<name>`, from this template as it stands at the latest release of spec, its highest `vX.Y.Z` tag:

- `files/` is the new repository. Each `{{…}}` is filled in — the repository's name, the tag of spec and the date — and each `<!-- FILL: … -->` is left for the executor to write from the component's card. The card is given by its number in `docs/architecture.md`, and the recipe stops unless that card's heading names the repository; the copy names the card by the repository's name, not by the number, which a new card before it would change.
- `README.md` in `files/` is the title, the badges and a description alone: what the component is and why, and its place in the architecture, written from its card, with the card named and a link to `docs/`. It has no other section, no command or code block, and no status, version, date, number or language, and names no version of spec: the tag would age with each move, and LICENSE and the badge give the license. What a README held before — the list of the documents, how to clone, and later how to build, run, release and contribute — is `docs/README.md` in `files/`, the index of `docs/`. The README starts with the status badges every repository has from its first day — CI, CodeQL, OpenSSF Scorecard, its license and five SonarCloud measures — with the repository's name in their addresses. The others come later, each with what it reports on: a release, code, coverage, an OpenSSF Best Practices entry.
- `LICENSE`, `AGENTS.md` and `.devcontainer/` in `files/` are links to spec's own, so there is one copy of each. They are copied as they are; the devcontainer then gets the repository's own name and network, its name in that network, `--network-alias=<repository>`, what its kind adds, and a start command that checks out `spec/` when a clone has left it empty.
- `kinds.json` says what each kind adds to spec's devcontainer, at exact versions: VS Code extensions (`extensions`), VS Code settings (`settings`), lines for the end of the Dockerfile's `toolchain` stage, from a file in `kinds/` (`toolchain`), and, from a folder in `kinds/` (`devcontainer`), lines for the `devcontainer` stage, its `Dockerfile`, which go before the step of Claude Code, and the files the image copies, the rest of the folder, which go into the copy's `.devcontainer/` as they are; keys for the end of the copy's `.claude/settings.json` (`claude`), which may not be keys the template's file already sets; and the Claude Code plugins of spec's [claude-plugins/](../claude-plugins/README.md) that every session in the container loads (`claudePlugins`), which `containerEnv` of the copy's `devcontainer.json` names in `CLAUDE_CODE_PLUGIN_DIRS`, through the `spec` submodule. A key the recipe does not know stops it. `docs` adds nothing; `go` adds the Go extension, its settings that keep it from fetching tools of its own, and gopls from its lock file, `kinds/go/gopls/`, built in the `devcontainer` stage at `GOPLS_VERSION`, and Claude Code's plugin `gopls-lsp`, so that a session gets gopls's diagnostics after each edit — from the container's own path, not from a marketplace, which Claude Code records in the `~/.claude` that the containers share; and `typescript` adds Biome's extension, Biome as TypeScript's default formatter, and the browsers the tests run in, one for each engine CI checks: Chrome Headless Shell, WebKit and Firefox from Playwright's image, pinned by tag and digest, with their system libraries and Playwright's fonts from a snapshot of the Ubuntu archive. The image, the three browsers' revisions and the snapshot are raised together in `kinds/typescript.Dockerfile`, and gopls in `kinds/go/` — its lock file with `go get -tool golang.org/x/tools/gopls@vX.Y.Z` and `GOPLS_VERSION` together, which spec's tests and `new-repo-check` hold to each other —, and a copy takes them with its next move to a tag: it takes its `.devcontainer/` from what the recipe builds, and adds its own differences again. The lock file's `go` line is the `GO_VERSION` of the toolchain stage, and spec's tests hold it there: a raise of Go raises it too. `.devcontainer/gopls/` is a Go module that no code reads, so a Go repository leaves it out of the modules its checks list, as spec leaves `repo-template/` out of `_go-modules`.
- `docs-budgets.json` in `files/` names what differs from the block `repository` of spec's `tools/docs-check/budgets.json`, `{ "citations": true }` at first, the rule of citations checked; the block holds `entry` 12 and `"comments": true`, the numbers of decisions in comments of code checked.
- spec becomes a git submodule at the same tag, and everything is staged. The first commit is the author's.

Before spec has a tag, or to read a change to the template, `just new-repo-draft <name> <kind> <card> <tag>` builds the copy from the working tree instead, names the given tag in its text, and leaves git alone.

`docs-check` reads `files/` as part of spec. The template cites no decision and no section, its own or spec's: only a record of spec, with the suffix "spec", which is checked against spec's documents. A bare `architecture 2` or `R03` would be checked against spec's documents too, so the template writes those only in code, as examples.

In the new repository, `just -f spec/justfile docs-check-repo` checks its documents as a repository of its own: its own records and log bare, spec's records with the suffix, against its spec/ submodule. An example of a citation is written in code — `R03` — so that the check does not take it for one.

`just new-repo-check <name>` checks the copy once it is filled: no `{{…}}` and no FILL left, `LICENSE` and `AGENTS.md` the same as spec's, its README a description alone — one heading, no block of code or command, a link to `docs/README.md` —, its documents passing the same check as `docs-check-repo` — links, sections, its log and tables, its citations of spec, its diagrams — no name of spec's left in the devcontainer, and the submodule at a tag: the one CLAUDE.md and the opening of RUN.md give `spec/`, which any link to spec that names a version names too.
