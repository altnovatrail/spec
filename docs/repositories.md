> Статус: черновик для обсуждения, 2026-10-18.
>
> Как платформа нарезана на репозитории, что от чего зависит и в каком порядке появляется. Какие части работают во время работы платформы и как они связаны — в [architecture.md](architecture.md). Технологии каждого репозитория описывают его собственные документы (R11). Открытые вопросы Т-… — в разделе 8.

## 1. Принципы

- **`spec` — единственная общая зависимость.** В нём словарь, форматы и контракты. Остальные репозитории берут его по точной версии тега (R10): документы и правила — git-подмодулем `spec/` на теге, код — файлами релиза на том же теге (R21, R64). Код на Go берёт тег как версию модуля Go `github.com/altnovatrail/spec` — с форматом `spec.Format` и его типами, пакетами `types/formatv0` и `types/formatv0/open` (R72), а с линии 0.8 и с таблицей допуска `spec.Admission` и её типами `types/admissionv0` (R96), — любой другой код — подписанный файл релиза, `format-<версия>.tar.gz` и `admission-<версия>.tar.gz`. Код на TypeScript берёт типы формата пакетом npm `@altnovatrail/spec` той же версии, что тег, без `v`, — файлом того же релиза с линии 0.4 (R73). Код контрактов API — свой: на Go — вложенный модуль `github.com/altnovatrail/spec/contracts` по тегу `contracts/vX.Y.Z` с номером тега `spec`, на TypeScript — пакет npm `@altnovatrail/contracts` той же версии, файлом того же релиза с линии 0.7; тег `contracts/vX.Y.Z` релиз ставит сам (R83; четвёртая поправка 2026-11-02 к R83). С линии 0.5 тот же пакет несёт и типы элемента `<novatrail-canvas>`, `@altnovatrail/spec/canvas` (R74). Версии модулей в `go.mod`, пакеты npm и подмодуль двигают вместе, одним переходом на тег, и исключают из Dependabot (R64, R73).
- **Без циклов** — ни при сборке, ни по сети.
- **Библиотеки не зависят от сервисов, сервисы не зависят друг от друга при сборке.** Между собой сервисы говорят по сети, по контрактам из `spec`.
- **Сервис — только там, где нужен отдельный процесс.** В первом срезе сервис один — `api`. `tutor` — библиотека в его процессе; сервисом он станет, когда у него появится второй потребитель (R15).
- **Библиотеки чистые.**
  - `learner-model`, `engine` и `module-kit` — вычисления без ввода-вывода, как `domain/` в canvas-api. Поэтому их можно гонять на стенде на тысячах виртуальных учеников, а при нужде — исполнять на устройстве.
  - CLI `module-kit` только читает и пишет файлы модуля.
  - `tutor` — библиотека с одним видом ввода-вывода: запросами к поставщикам ИИ.
- **Сборка, сеть и CI — разные связи.**
  - Зависимость при сборке — импорт кода по версии.
  - Сетевая зависимость — вызов API по контракту.
  - Инструмент CI — программа, которую CI берёт по точному тегу.

  Поэтому стенд `sim` может проверять `learner-model` и `engine`, хотя сам их импортирует: CI библиотеки берёт `sim` по тегу и подставляет код pull request через `go.work`, а другую библиотеку — коммитом из файла гейта `sim`. Цикла здесь нет (R103).
- **Один образец репозитория.** Новый репозиторий начинается с заготовки `spec` — devcontainer, CLAUDE.md, AGENTS.md, RUN.md и документы (раздел 2.2, R21). Общие проверки CI из `.github` у него с первого дня, ещё до кода (R30); justfile, проверки языка и подписанные релизы приходят с кодом, по образцу canvas-api. Отличия от образца записываются, как в R46 canvas-api.
- **Довод R13 canvas-api.** Там клиент и API жили в одном репозитории, потому что «API и клиент меняются вместе, одним pull request». Здесь этот довод снимают версионируемые контракты в `spec`: сначала новый контракт, потом сервис, потом клиент. Цена — несколько pull request вместо одного; её принимаем ради узкого контекста ИИ-агентов и независимых релизов (R10).

### 2.2. Как заводить репозиторий

Новый репозиторий собирается из заготовки `repo-template/` в `spec` (R21).

1. Имя — из таблицы; репозиторий — публичный (R18). Лицензия — Apache-2.0, у кода и у содержания (R12, R20).
2. `just new-repo <имя> <вид> <карточка>` — например, `just new-repo learner-model go 3.8` — собирает рабочую копию в `.repos/<имя>` из файлов последнего релиза `spec`, старшего тега вида `vX.Y.Z`. Тег должен быть уже на GitHub: подмодуль берётся оттуда, и рецепт сверяет, что там это тот же коммит. Релиз с тегом выходит сам, после зелёного CI на `main` (R31). Вид — `go`, `typescript` или `docs`, карточка — номер раздела architecture 3. В копии:
   - `README.md` (en) — значки статуса первого дня (раздел 2.3), назначение, этап и ссылка на `spec`;
   - `CLAUDE.md` (en) — роль компонента и его место в платформе, свои документы, окружение и строка `@spec/RULES.md`. Общие правила — один файл `RULES.md` в `spec`, и его импортирует CLAUDE.md каждого репозитория: только devcontainer, точные версии, языки, никаких данных учеников и секретов, Apache-2.0, ссылки и работа между репозиториями;
   - `AGENTS.md` и `LICENSE` — те же, что в `spec`;
   - `docs/architecture.md` (ru) — назначение и границы из карточки и подраздел на каждый её пункт «Решить при детализации»;
   - `docs/decisions.md` (ru) — пустой журнал со своей нумерацией: «Следующий номер — R01». Другие репозитории цитируют его записи как «R03 api»;
   - `RUN.md` (ru) — план работ по образцу RUN.md `spec` (R19). Первый эпик — «Детализация»: по задаче на пункт «Решить при детализации», пункты, которые порознь не решить, — одной задачей, последняя задача — «Итог детализации»;
   - `.devcontainer/` — тот же, что у `spec`, со своим именем контейнера и сети и с тем, что добавляет вид репозитория (`repo-template/kinds.json`): расширения и настройки VS Code и строки в конце стадии `toolchain`. Вид `go` добавляет расширение Go, а вид `typescript` — расширение Biome, Biome форматтером TypeScript по умолчанию и браузер для тестов — Chrome Headless Shell из образа Playwright по тегу и digest и его системные библиотеки из снимка Ubuntu (R79); `NOVATRAIL_DEVCONTAINER=1`. Решения, на которые ссылается его Dockerfile, — решения `spec`, и в копии они с суффиксом: `(R34 spec)` (В11 `canvas`). Тома входа Claude Code, Codex и gh — общие на все контейнеры NovaTrail. Go в стадии `toolchain` уже есть: `spec` проверяет им свой модуль Go (R64), а у компонента им собирают и проверяют его код на Go. Он приходит с Dockerfile в копию любого вида, а в копии без кода на Go не используется: комментарии Dockerfile написаны так, чтобы читаться верно и в `spec`, и в копии (В8 `module-kit`). buf приходит так же: в `spec` им проверяются контракты, а в копии без контрактов он не используется (R83). Другие инструменты кода добавляются по точным версиям, когда начнётся код;
   - `spec/` — git-подмодуль на том же теге; если клон пришёл без него, контейнер достаёт его при старте. Всё добавлено в индекс, коммита нет.
3. Исполнитель заполняет пометки `FILL` по карточке компонента. `just new-repo-check <имя>` проверяет, что от заготовки ничего не осталось, а документы копии проходят проверку документов репозитория (R32). В самом репозитории её запускает `just -f spec/justfile docs-check-repo`.
4. `gh repo create altnovatrail/<имя> --public` — после подтверждения автора. Сразу за ним — `gh repo edit altnovatrail/<имя> --delete-branch-on-merge`: ветка pull request удаляется после слияния. Так настроены все репозитории организации с 2026-10-19, но новый репозиторий эту настройку сам не получает. Первый коммит и push — автора. Числовой ID нового репозитория — `gh api repos/altnovatrail/<имя> --jq .id` — та же задача `spec` вносит в `tools/release/repositories.mjs`: без него `release-verify` не примет файлов его релизов, ведь подпись сверяется с ID, а не только с адресом (R77, поправка 2026-11-01).
5. CI — общие проверки из `.github` и Dependabot, ещё до кода (R30; RUN.md, T16); проверки языка — с первым кодом репозитория. Что код добавляет к вызывающим файлам — job языка, вход CodeQL, экосистему Dependabot, релиз, — пишет сессия самого репозитория по architecture 3.3 .github, а проверки в ruleset ставит автор (поправка 2026-10-21 к R30).
6. Вопрос, который касается нескольких репозиториев, записывается в реестр `spec`: О-, П- или Т-. Сессия в другом репозитории `spec` не правит, а передаёт такой вопрос автору через таблицу 3 своего RUN.md с пометкой «в реестр spec» (RULES.md, раздел «Across repositories»).

### 2.3. Значки README

README каждого репозитория начинается значками статуса, как у MathTrail (R48):
- первая строка — CI, Release, CodeQL, номер релиза, язык, покрытие, OpenSSF Best Practices, OpenSSF Scorecard и лицензия;
- вторая, после пустой строки, — пять мер SonarCloud: code smells, reliability, security, maintainability и vulnerabilities.

Значок стоит, только когда есть то, о чём он говорит: без «no releases», «not found» и «unknown».
- **С первого дня** — CI, CodeQL, Scorecard, лицензия и меры SonarCloud. Их несёт заготовка, `repo-template/files/README.md`, с именем репозитория. Отвечают они, когда репозиторий заведён до конца: с общими проверками (раздел 2.2, пункт 5), проектом SonarCloud (R30) и первым прогоном Scorecard.
- **С первым релизом** — Release и номер релиза.
- **С первым кодом** — язык: у Go — версия из `go.mod`, у TypeScript — версия `typescript` из devDependencies `package.json`. У `spec` значка языка нет: его код — инструменты проверок в `tools/` и модуль Go, обёртка над файлами формата и их типами (R64, R72), а не код платформы.
- **С первой загрузкой покрытия в Codecov** — покрытие (RUN.md, T40).
- **С уровнем passing** — OpenSSF Best Practices, по ID проекта на bestpractices.dev (RUN.md, T41). Ответы на критерии лежат в файле `.bestpractices.json` в корне репозитория, по-английски: сайт предлагает их в анкете, а сохраняет их автор (поправка 2026-10-26 к R48). Изменённый ответ сайт из файла сам не берёт. Его приносит ссылка на анкету с изменёнными полями и `overrides` по ним: её строит из файла сессия репозитория, а сохраняет автор (поправка 2026-10-27 к R48).

## 3. Схема зависимостей

От `spec` зависят все, поэтому эти стрелки не нарисованы. Стрелка означает «зависит от». Сплошная — импорт при сборке, пунктир — инструмент CI по точному тегу или выкладка.

```mermaid
flowchart LR
    api["api"] --> tutor["tutor"]
    api --> kit["module-kit"]
    api --> eng["engine"]
    api --> lm["learner-model"]
    eng --> lm
    sim["sim"] --> eng
    sim --> lm
    tutor -->|"eval-раннер"| kit
    app["app"] --> canvas["canvas"]
    app --> smap["skill-map"]
    mods["modules"] -.->|"инструменты CI"| kit
    mods -.-> sim
    mods -.->|"с этапа 2"| tutor
    canvas -.->|"CI страницы образцов: релиз"| mods
    canvas -.->|"CI страницы образцов"| kit
    infra["infra"] -.->|"выкатывает релизы"| api
    infra -.-> app
    reg["module-registry, этап 4"] --> kit
    pipe["module-pipeline, этап 4"] --> kit
    pipe --> tutor
    site["site, этап 3"] --> smap
    wt["widget-template, этап 4"]
```

- Не нарисованы и связи `canvas` и `tutor`, по той же причине, что гейт `sim` ниже: они берут релизы друг друга как инструменты CI. CI `tutor` — синтетические образцы `canvas` (R38), CI `canvas` — открытые виды задач замера `tutor`, пока у `modules` нет содержания (поправка 2026-10-21 к R25). Цикла при сборке нет: каждая сторона берёт уже вышедший релиз другой по точному тегу, а первым выходит релиз `tutor` (R38).
- Гейт `sim` для `learner-model` и `engine` не нарисован, хотя это тоже инструмент CI. Вместе с импортом `sim → engine` такая стрелка читалась бы как цикл, а цикла нет (раздел 1, Т-16).
- Общие проверки CI из `.github` берут все репозитории (R30); эти стрелки тоже не нарисованы.
- CI `spec` проверяет примеры модулей обычным валидатором JSON Schema, а не `module-kit`: иначе `spec` зависел бы от того, кто зависит от него. Вектор правила части он проверяет схемой и правилами YAML, а само правило — CI `module-kit` (R45). Правила YAML и правила всего модуля — раскладку, ID в именах файлов и сигнатуры медиафайлов — `format-check` проверяет сам и сам строит открытый вид, с T29 — и вердикты векторов вердикта, кроме тех, что условию даёт Starlark, с T30 — ловушки, которые в них называют неверные значения, и что проверка утечки находит в текстах векторов утечки, с T31 — и правило `lesson.no-leaks` на уроках, а с T34 — ярусы и пакет модуля, его канонический вид и дайджесты: это вторая реализация рядом с `module-kit`, и векторы сверяют обе (R46, R51, R56, R57, R58, R62).
- В схеме из диалога с Gemini реестр и конвейер зависели друг от друга. Здесь цикла нет: конвейер публикует через API реестра, а реестр о конвейере не знает.
- `widget-template` ни от кого, кроме `spec`, не зависит: протокол виджета задан в `spec`, а сторона приложения — в `canvas`.

## 4. Потоки между репозиториями

Потоки во время работы платформы — в architecture 4. Здесь — как изменения проходят между репозиториями.

**От автора к ученику:**
1. Модуль лежит в `modules`: YAML, медиа, eval-набор.
2. CI проверяет его:
   - `module-kit` — схему, граф без циклов, ссылки, медиафайлы, ключи, утечки в текстах автора, которые ученик видит до решения, — и в текстах урока, который называет задачу (R57; R58);
   - `sim` — если изменилось то, что стенд читает из пакета, — на пакете pull request, с инвариантами и абсолютными порогами, без полос; с первого тега `sim`: до него гейта нет (R76; R103). Pull request, который меняет тег `sim`, гоняет все графы;
   - с этапа 2 — eval-раннер `tutor` на eval-наборе модуля.
3. На релизе `module-kit` собирает пакет — канонический вид для сервера, часть для устройства и опись с их дайджестами, без eval-набора (R62), — и индекс модулей: из индекса прошлого релиза, с записью каждой опубликованной версии и отметками о снятии (R63). Общий workflow релиза из `.github` подписывает их (R17).
4. `api` берёт пакеты по индексу релиза `modules`, который закрепляет его конфигурация — тег релиза и дайджест индекса, а дайджесты пакетов называет индекс (R63; R07 api); попытка хранит дайджест своего пакета — дайджест его описи (R62).
5. `app` получает от `api` открытый вид задачи — без ключа, решения и ловушек, без навыков, полосы и сложности, без приёмов, случая попроще и фраз-утечек (R57). Ключ остаётся на сервере, решение приходит после верного ответа (R05), а навыки, полосу и сложность читает только сервер (R51). Открытый вид урока приходит без его навыков и возрастных категорий (R58). Открытые виды паспорта, графа навыков, каталога приёмов и шагов решения `app` получает по дайджесту пакета — попытки, прохождения урока или текущей версии подключённого модуля — и кеширует по нему, а медиафайлы — из части пакета для устройства, которую раздаёт `api` (R62 и поправка 2026-11-04 к нему; R99).

Ключи открытых модулей публичны, как и сами модули. R05 не охраняет тайну, а лишь не держит ключ в приложении ученика.

**CI алгоритмов:**
- каждое изменение `learner-model` или `engine` прогоняется на стенде `sim`, на виртуальных учениках разных популяций (concepts 15). CI библиотеки берёт `sim` по точному тегу и SHA его коммита, своим job, и пишет `go.work` на лету, не коммитя его: `sim`, код pull request и другую библиотеку — коммитом из файла гейта `sim`. Гейт идёт на каждом pull request и каждом коммите `main` и держит мерж (R103);
- первая версия каждой библиотеки — до гейта: её проверяют свои тесты, а `sim` ставит на ней стенд и пишет критерий до первого кандидата — первого изменения после неё (R103);
- критерий записан до первого прогона кандидата (R163 standalone);
- изменение, которое ухудшает критерий, не сливается;
- порядок релизов (R103): изменение, которое ломает API стенда или двигает числа, сначала записывается в `sim` на коммите своего pull request, выходит тег `sim`, pull request библиотеки поднимает тег и сливается, а после релиза библиотеки `sim` поднимает `go.mod`. Пара «порог „освоено“ и цель коридора» и изменение `learner-model`, которое ломает API `engine`, идут одним тегом `sim`: файл гейта называет оба коммита, `learner-model` сливается, когда pull request `engine` прошёл ревью, а `api` переходит на обе версии вместе. Релиз `sim` выходит сам после зелёного CI на `main`, а тег у вызывающих поднимает их сессия.

**Смена модели ИИ:**
- новую модель для возможности ИИ допускают, когда она проходит eval-набор возможности и eval-наборы всех опубликованных модулей с этой возможностью;
- порядок (В9 `modules`; R04 modules): `tutor` выпускает тег, где модель в списке допущенных, когда она прошла eval-набор возможности в CI `tutor`; pull request `modules` переходит на этот тег, и eval-раннер гоняет eval-наборы всех модулей — они лежат в git `modules`, вне пакета и файлов релиза (R62); `api` переходит на такой тег `tutor` только после мержа этого pull request. Если он красный, `tutor` выпускает следующий тег без модели, а `api` остаётся на прежнем: откат — только вперёд (Т-19). Что `api` ждёт `modules`, держит ревью pull request `api`;
- ложные тревоги считаются по вердикту: наблюдение модели проходит через `module-kit`, как в работе платформы (R04). У оценки по рубрике вердикта нет, и её мерят ложные тревоги на выполненных критериях и согласие с людьми (R71). Что раннер отдаёт — отчёт без содержания работ, по которому считаются меры, — и что лежит в eval-наборе модуля, пишет протокол eval, а для допуска годится только отчёт с вердиктами `module-kit` ([текст контрактов](../contracts/README.md), разделы 13 и 14; R95).

**Новая версия формата модуля** (R44). Зависимости при сборке и инструменты CI каждый берёт по точной версии, поэтому шаг не ломает тех, кто ещё не перешёл. А `api` и `app` говорят по сети и, пока формат — v0, выходят вместе:
1. `spec` — новая версия формата и тем же pull request новая линия; иначе `release-version` его не пропустит. Первый релиз линии выпускает версию формата файлом релиза и версией модуля Go (R64).
2. То, что читает модули в CI `modules`, переходит на новый тег — подмодулем и модулем Go `spec` вместе: `module-kit` и, с этапа 2, eval-раннер `tutor`. Если изменился открытый вид, `canvas` выпускает пакет с новыми типами (R36).
3. `modules` — одним pull request: новые теги `module-kit` и `tutor` в CI, паспорта и содержание всех модулей. `sim` в нём не гоняется: пакета новой версии он на прежнем теге не прочтёт. Граф в переходе не меняют — это держит ревью `modules` (R03 modules), — а меняют его отдельным pull request после шага 4.
4. `sim` переходит на новый тег и на пакеты из нового релиза `modules`, а `modules` берёт в CI новый тег `sim`. `learner-model` и `engine` берут новый `sim` своим переходом: свой гейт они держат на прежнем теге.
5. `api` берёт новый `module-kit` и новые пакеты, а если изменился открытый вид, вместе с ним выходит `app` с новым `canvas` — одним списком точных версий (Т-19). CI `canvas` берёт новый релиз `modules` и новый тег `module-kit`.

Пока формат — v0, читается только текущая версия, и модули переходят все сразу; так же — на v1, ведь v0 с выходом v1 из окна уходит. С v2 окно — текущая мажорная версия и предыдущая — даёт модулям переходить по одному, а `api` и `app` — порознь.

**Новая версия таблицы допуска** (R96) — короче: таблицу читает одна функция допуска `tutor`, а зовёт её `api` в своём процессе.
1. `spec` — новая версия таблицы и тем же pull request новая линия, а её строка поставщика в privacy 5.3 сверена заново. Первый релиз линии выпускает таблицу файлом релиза и версией модуля Go (R64).
2. `tutor` переходит на новый тег — подмодулем и модулем Go `spec` вместе — и выпускает релиз: его функция читает таблицу из `spec.Admission`, а тесты гоняют её векторы.
3. `api` берёт новый релиз `tutor` и выкатывается. Если новая версия добавила факт развёртывания, оператор заявляет его в файле фактов `api` — только когда факт держится. Пока шаг 3 не прошёл, работает прежняя таблица: срочно закрыть ИИ платформы оператор может сам, сняв факт.

Zip модуля `contracts` проверяет `just go-check`, а новый мажорный пакет без новой линии `release-version` не пропускает (RUN.md, T55).
- `RULES.md` — общие правила всех репозиториев NovaTrail; его импортирует CLAUDE.md каждого из них (R21).
- `repo-template/` — заготовка нового репозитория, а `tools/new-repo/` — рецепты `just new-repo` и `just new-repo-check`, которые её собирают и проверяют (раздел 2.2).
- Позже — нормативные части; они выходят тегами `spec`, а часть со своей версией — ещё и файлом его релиза, `<часть>-<версия>.tar.gz`, и в модуле Go (R64):
  - схемы формата модуля в папке `format/` — JSON Schema 2020-12 (R45), — его примеры и тест-векторы (R42); пакет модуля (R62) и индекс модулей (R63);
  - контракты API — protobuf и buf (R11) в `contracts/` (R83): между `app` и `api` — и в нём список кодов причин движка, `ReasonCode` (R29; R100); наблюдение — общий тип `tutor`, `module-kit` и eval, пакет `novatrail.observation.v1` (R86); файл образца протокола eval с разметкой, правила, которые одни у устройства и раннера, с их тест-векторами, eval-наборы и отчёт раннера — пакет `novatrail.eval.v1` (R93; R94; R95);
  - протокол виджета (R16) и протокол eval (R15);
  - возраст цифрового согласия по странам — с источниками и датой прочтения (privacy 3);
  - формат выгрузки (R09);
  - руководства для авторов.

  Нормативные тексты для авторов — формат модуля, протокол виджета и руководства — на английском и вне `docs/` (R42). У формата модуля своя версия, MAJOR.MINOR, а не тег `spec`: новая версия формата открывает новую линию `spec` (R44), и так же — новая версия таблицы допуска (R96).
- Примеры — фрагменты модулей для тестов схем, в `format/examples/`: верный проходит свою схему, а неверный первой строкой называет ошибку, которую должен дать (R45). Пример целого модуля — папка, разложенная как модуль (R46). CI `spec` проверяет их обычным валидатором JSON Schema, `ajv`, рецептом `just format-check` (раздел 3).

Чего в `spec` нет: кода сервисов и библиотек платформы, содержания модулей, данных учеников. Пакет Go `spec` — не библиотека платформы: он только встраивает файлы формата, чтобы код взял их по тегу (R64), а пакеты `types/` несут только типы и константы, без кода (R72), и пакет npm `@altnovatrail/spec` — одни объявления (R73). Код, который buf генерирует по контрактам API, — тоже не библиотека платформы: сообщения и заглушки сервисов Connect, без логики, во вложенном модуле Go `contracts` и в пакете npm `@altnovatrail/contracts` (R83).

2. **.github** — общие проверки, до первого репозитория с кодом. Общие workflow для кода приходят с кодом, на котором проверяются (R03 .github): обёртка Go и релиз — с первым кодом `module-kit`, обёртка TypeScript — с первым кодом на TypeScript, у `canvas`.
3. **modules и module-kit:**
   - порт эталонных задач standalone с ловушками — 705 на коммите 89986bc — и 33 шаблонов с решателями (R05 modules). Сначала — первая пачка олимпиадной математики: 20–30 задач на три полосы, без шаблонов и решателей, уроками; паспорт называет в аудитории и `adult`. Остальной порт — после неё (R76);

   Так формат v0 сразу проверяется на двух предметах (R08).
4. **learner-model, engine и sim** — вместе: стенду нужны и модель, и правило выбора. Стенд и критерий появляются до первого кандидата. Отправная модель — модель standalone с уровнем на модуль (concepts 11).

Остальные замеры чтения ИИ — по видам канвы и ответа, для Т-23 и О-8 — эпик E4 `tutor` (поправка 2026-10-26 к R43).
