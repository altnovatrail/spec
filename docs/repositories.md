## 1. Principles

- **`spec` is the only shared dependency.** It holds the vocabulary, the formats and the contracts. The other repositories take it at an exact tag version (R10): the documents and rules as the git submodule `spec/` at the tag, the code as release files of the same tag (R21, R64). Go code takes the tag as the version of the Go module `github.com/altnovatrail/spec` — with the format `spec.Format` and its types, the packages `types/formatv0` and `types/formatv0/open` (R72), and from line 0.8 also with the admission table `spec.Admission` and its types `types/admissionv0` (R96) —, any other code as a signed release file, `format-<version>.tar.gz` and `admission-<version>.tar.gz`. TypeScript code takes the format's types as the npm package `@altnovatrail/spec` of the same version as the tag, without `v`, — as a file of the same release from line 0.4 (R73). The code of the API contracts is its own: in Go, the nested module `github.com/altnovatrail/spec/contracts` at the tag `contracts/vX.Y.Z` with the number of the `spec` tag, in TypeScript, the npm package `@altnovatrail/contracts` of the same version, as a file of the same release from line 0.7; the release sets the tag `contracts/vX.Y.Z` itself (R83; the fourth 2026-11-02 amendment to R83). From line 0.5 the same package also carries the types of the element `<novatrail-canvas>`, `@altnovatrail/spec/canvas` (R74). The module versions in `go.mod`, the npm packages and the submodule are moved together, in one move to a tag, and are excluded from Dependabot (R64, R73).
- **No cycles** — neither in the build nor over the network.
- **Libraries do not depend on services, services do not depend on each other in the build.** Services talk to each other over the network, by the contracts from `spec`.
- **A service only where a separate process is needed.** In the first slice there is one service, `api`. `tutor` is a library in its process; it becomes a service when it gets a second consumer (R15).
- **Libraries are pure.**
  - `learner-model`, `engine` and `module-kit` are computations without input and output, like `domain/` in canvas-api. So they can be run on the simulator over thousands of virtual learners and, when needed, executed on the device.
  - The CLI of `module-kit` only reads and writes the files of a module.
  - `tutor` is a library with one kind of input and output: requests to AI providers.
- **Build, network and CI are different links.**
  - A build dependency is an import of code by version.
  - A network dependency is a call of an API by contract.
  - A CI tool is a program that CI takes at an exact tag.

  So the simulator `sim` can check `learner-model` and `engine`, though it imports them itself: the CI of a library takes `sim` at a tag and substitutes the pull request's code through `go.work`, and the other library by a commit from the gate file of `sim`. There is no cycle here (R103).
- **One pattern of a repository.** A new repository starts from the template of `spec` — the devcontainer, CLAUDE.md, AGENTS.md, RUN.md and the documents (section 2.2, R21). It has the shared CI checks from `.github` from day one, even before code (R30); the justfile, the language checks and the signed releases come with code, after the pattern of canvas-api. Differences from the pattern are recorded, as in R46 canvas-api.
- **The argument of R13 canvas-api.** There the client and the API lived in one repository, because «API и клиент меняются вместе, одним pull request». Here the versioned contracts in `spec` remove this argument: first the new contract, then the service, then the client. The price is several pull requests instead of one; we accept it for the narrow context of AI agents and independent releases (R10).

### 2.2. How to set up a repository

A new repository is assembled from the template `repo-template/` in `spec` (R21).

1. The name comes from the table; the repository is public (R18). The license is Apache-2.0, for code and for content (R12, R20).
2. `just new-repo <name> <kind> <card>` — for example, `just new-repo learner-model go 3.8` — assembles a working copy in `.repos/<name>` from the files of the latest release of `spec`, the highest tag of the form `vX.Y.Z`. The tag must already be on GitHub: the submodule is taken from there, and the recipe checks that it is the same commit there. A release with its tag comes out by itself, after CI is green on `main` (R31). The kind is `go`, `typescript` or `docs`, the card is the number of a section of architecture 3. In the copy:
   - `README.md` (en) — the day-one status badges (section 2.3), the purpose, the stage and a link to `spec`;
   - `CLAUDE.md` (en) — the component's role and its place in the platform, its own documents, the environment and the line `@spec/RULES.md`. The shared rules are one file, `RULES.md` in `spec`, and the CLAUDE.md of every repository imports it: devcontainer only, exact versions, languages, no learners' data and no secrets, Apache-2.0, citations and work across repositories;
   - `AGENTS.md` and `LICENSE` — the same as in `spec`;
   - `docs/architecture.md` (en) — the purpose and the bounds from the card and a subsection for each of its items "To decide when detailed";
   - `docs/decisions.md` (en) — an empty log with its own numbering: "Next number — R01". Other repositories cite its entries as "R03 api";
   - `docs/sources.md` (en) — the records of external facts, empty: a provider's terms, a price, a law, a library's documentation — with the source, the date read and the quote, and a claim of `docs/architecture.md` or of the log cites the record — `sources 1.1` (RULES.md, The bar). `docs/architecture.md` has no section "Sources" of its own. The results of measurements go to `docs/measurements.md`, which the first measurement starts, not to `docs/architecture.md`; the pattern is [sources.md](sources.md) and [measurements.md](measurements.md) of `spec` (R143);
   - `RUN.md` (ru) — the work plan after the pattern of the RUN.md of `spec` (R19). The first epic is «Детализация»: a task for each item "To decide when detailed", the items that cannot be decided apart as one task, and the last task «Итог детализации». Its rule 4 lets the executor run a task's checks without the author, by R146: the path in the browser with Playwright in the devcontainer, the calls of AI on the stub of `tutor`, and a real call only where the task checks the model's words, under the provider's spending limit and the cap the task names, with «Сделано» naming what was spent. A repository made before T146 takes the rule into its own RUN.md with its move to a tag: a move to a tag does not rewrite RUN.md;
   - `DEBT.md` (ru) — table 4 of the work plan, the technical debt, empty: «следующий — Д1» (R19);
   - `docs-budgets.json` — `{}`: the repository's documents keep within the budgets of size of the block `repository` of `spec`'s `tools/docs-check/budgets.json`, and the file names what differs; without it `docs-check-repo` does not measure (R145). Its RUN.md measures the sessions' tokens at the archive of each epic (measurements 1.9);
   - `.claude/settings.json` — the Claude Code project settings: the session hook `spec/tools/session/`, compaction at 400 thousand, the claude.ai connectors off, and `claudeMdExcludes` loads neither the CLAUDE.md nor the part rules of the `spec` submodule (R143). A kind adds its own keys to them, with the key `claude` in `repo-template/kinds.json`. The kind `go` adds the marketplace `novatrail` from `spec/claude-plugins/` and the plugin `gopls-lsp`: the session gets gopls diagnostics after each edit of Go code (the 2026-11-12 amendment to R143; sources 2.7). The plugin loads from the submodule in place, without installation, when the repository's folder is trusted, and comes with a move to a tag; in a cloud session the language server does not start;
   - `.devcontainer/` — the same as that of `spec`, with its own names of the container and the network and with what the repository's kind adds (`repo-template/kinds.json`): VS Code extensions and settings, lines at the end of the `toolchain` stage and, from the kind's folder, lines of the `devcontainer` stage with the files the image copies. The kind `go` adds the Go extension with settings that keep it from installing its own tools, and gopls from the lock file `repo-template/kinds/go/gopls/`, built in the `devcontainer` stage at the version `GOPLS_VERSION` (R102); a move to a tag takes `.devcontainer/` from what the recipe builds and brings the repository's differences in again, so gopls comes with it. `.devcontainer/gopls/` is a Go module that no code reads, and the repository's Go checks do not list it. The kind `typescript` adds the Biome extension, Biome as the default TypeScript formatter and browsers for tests, one for each engine CI checks — Chrome Headless Shell, WebKit and Firefox from the Playwright image by tag and digest, and their system libraries and Playwright's fonts from the Ubuntu snapshot (R79 and its 2026-11-13 amendment; the builds' licenses — the 2026-11-13 amendment to R12); `NOVATRAIL_DEVCONTAINER=1`. The decisions its Dockerfile cites are decisions of `spec`, and in the copy they carry the suffix: `(R34 spec)` (В11 `canvas`). The sign-in volumes of Claude Code, Codex and gh are shared by all NovaTrail containers. Go is already in the `toolchain` stage: `spec` checks its Go module with it (R64), and a component builds and checks its Go code with it. It comes with the Dockerfile into a copy of any kind, and in a copy without Go code it is not used: the comments of the Dockerfile are written to read right both in `spec` and in a copy (В8 `module-kit`). buf comes the same way: in `spec` it checks the contracts, and in a copy without contracts it is not used (R83). Other code tools are added at exact versions when code begins;
   - `spec/` — the git submodule at the same tag; if a clone came without it, the container fetches it at start. Everything is added to the index, there is no commit.
3. The executor fills the `FILL` marks from the component card. `just new-repo-check <name>` checks that nothing of the template is left and that the copy's documents pass the repository's documents check (R32). In the repository itself it is run by `just -f spec/justfile docs-check-repo`.
4. `gh repo create altnovatrail/<name> --public` — after the author confirms. Right after it, `gh repo edit altnovatrail/<name> --delete-branch-on-merge`: a pull request's branch is deleted after the merge. All repositories of the organization are set so since 2026-10-19, but a new repository does not get this setting by itself. The first commit and push are the author's. The new repository's numeric ID — `gh api repos/altnovatrail/<name> --jq .id` — the same task of `spec` adds to `tools/release/repositories.mjs`: without it `release-verify` accepts no files of its releases, since the signature is checked against the ID, not only the address (R77, the 2026-11-01 amendment).
5. CI — the shared checks from `.github` and Dependabot, even before code (R30; RUN.md, T16); the language checks come with the repository's first code. What code adds to the calling files — the language job, the CodeQL input, the Dependabot ecosystem, the release — is written by the repository's own session by architecture 3.3 .github, and the author puts the checks into the ruleset (the 2026-10-21 amendment to R30).
6. A question that concerns several repositories is written into the register of `spec`: О-, П- or Т-. A session in another repository does not edit `spec`, but passes such a question to the author through table 3 of its RUN.md with the mark «в реестр spec» (RULES.md, the section "Across repositories").

## 4. Flows between repositories

The flows while the platform works are in architecture 4. Here is how changes pass between repositories.

**From the author to the learner:**
1. A module lies in `modules`: YAML, media, an eval set.
2. CI checks it:
   - `module-kit` — the schema, a graph without cycles, the references, the media files, the keys, the leaks in the author's texts that the learner sees before solving, — and in the texts of a lesson that names the task (R57; R58);
   - `sim` — if what the simulator reads from the package changed — on the pull request's package, with invariants and absolute thresholds, without bands; from the first tag of `sim`: before it there is no gate (R76; R103). A pull request that changes the tag of `sim` runs all the graphs;
   - from stage 2, the eval runner of `tutor` on the module's eval set.
3. On release, `module-kit` builds the package — the canonical view for the server, the device part and the inventory with their digests, without the eval set (R62), — and the module index: from the index of the previous release, with an entry for each published version and the marks of withdrawal (R63). The shared release workflow from `.github` signs them (R17).
4. `api` takes the packages by the index of a release of `modules` that its configuration pins — the release's tag and the index's digest, and the index names the packages' digests (R63; R07 api); an attempt stores the digest of its package, the digest of its inventory (R62).
5. `app` gets from `api` the open view of a task — without the key, the solution and the traps, without the skills, the band and the difficulty, without the techniques, the simpler case and the leak phrases (R57). The key stays on the server, the solution comes after a correct answer (R05), and the skills, the band and the difficulty only the server reads (R51). The open view of a lesson comes without its skills and age categories (R58). The open views of the manifest, the skill graph, the technique catalog and the solving steps `app` gets by the package digest — of an attempt, a lesson run or the current version of a connected module — and caches by it, and the media files from the device part of the package, which `api` serves (R62 and the 2026-11-04 amendment to it; R99).

The keys of open modules are public, as are the modules themselves. R05 guards no secret, it only keeps the key out of the learner's application.

**The CI of the algorithms:**
- every change of `learner-model` or `engine` is run on the simulator `sim`, on virtual learners of different populations (concepts 15). The CI of a library takes `sim` at an exact tag and the SHA of its commit, in a job of its own, and writes `go.work` on the fly, without committing it: `sim`, the pull request's code and the other library by a commit from the gate file of `sim`. The gate runs on every pull request and every commit of `main` and holds the merge (R103);
- the first version of each library comes before the gate: its own tests check it, and `sim` sets up the simulator on it and writes the criterion before the first candidate, the first change after it (R103);
- the criterion is written before the first run of a candidate (R163 standalone);
- a change that worsens the criterion is not merged;
- the order of releases (R103): a change that breaks the simulator's API or moves the numbers is first written into `sim` at the commit of its pull request, a tag of `sim` comes out, the library's pull request raises the tag and is merged, and after the library's release `sim` raises `go.mod`. The pair "the threshold 'mastered' and the corridor's target" and a change of `learner-model` that breaks the API of `engine` go in one tag of `sim`: the gate file names both commits, `learner-model` is merged when the pull request of `engine` has passed review, and `api` moves to both versions together. The release of `sim` comes out by itself after CI is green on `main`, and the callers' tag is raised by their session.

**A change of AI model:**
- a new model for an AI capability is admitted when it passes the capability eval set and the eval sets of all published modules with this capability;
- the order (В9 `modules`; R04 modules): `tutor` releases a tag where the model is in the list of admitted ones once it has passed the capability eval set in the CI of `tutor`; a pull request of `modules` moves to this tag, and the eval runner runs the eval sets of all modules — they lie in the git of `modules`, outside the package and the release files (R62); `api` moves to such a tag of `tutor` only after this pull request is merged. If it is red, `tutor` releases the next tag without the model, and `api` stays on the former one: rollback is only forward (Т-19). That `api` waits for `modules` is held by the review of the pull request of `api`;
- false alarms are counted by verdict: the model's observation passes through `module-kit`, as in the platform's work (R04). An assessment by rubric has no verdict, and it is measured by the false alarms on met criteria and by agreement with people (R71). What the runner gives — a report without the content of the works, by which the measures are counted — and what lies in a module's eval set is written by the eval protocol, and only a report with the verdicts of `module-kit` is fit for admission ([the contracts text](../contracts/README.md), sections 13 and 14; R95).

**A new module format version** (R44). Each takes build dependencies and CI tools at an exact version, so a step does not break those who have not moved yet. But `api` and `app` talk over the network and, while the format is v0, come out together:
1. `spec` — the new format version and, in the same pull request, a new line; otherwise `release-version` will not let it pass. The first release of the line releases the format version as a release file and a version of the Go module (R64).
2. What reads modules in the CI of `modules` moves to the new tag — the submodule and the Go module of `spec` together: `module-kit` and, from stage 2, the eval runner of `tutor`. If the open view changed, `canvas` releases a package with the new types (R36).
3. `modules` — in one pull request: the new tags of `module-kit` and `tutor` in CI, the manifests and the content of all modules. `sim` is not run in it: at its former tag it will not read a package of the new version. The move changes nothing of what the simulator reads from the package — neither the graph nor the tasks' bindings — except the very writing in the new format version: the review of `modules` holds this (R03 modules; the 2026-11-07 amendment to R103), and that is changed in a separate pull request after step 4.
4. `sim` moves to the new tag and to the packages from the new release of `modules`, and `modules` takes the new tag of `sim` in CI. `learner-model` and `engine` take the new `sim` in a move of their own: they hold their gate at the former tag.
5. `api` takes the new `module-kit` and the new packages, and if the open view changed, `app` comes out with it, with the new `canvas` — in one list of exact versions (Т-19). The CI of `canvas` takes the new release of `modules` and the new tag of `module-kit`.

While the format is v0, only the current version is read, and the modules all move at once; the same on v1, since v0 leaves the window when v1 comes out. From v2 the window — the current major version and the previous one — lets the modules move one by one, and `api` and `app` apart.

**A new version of the admission table** (R96) is shorter: one admission function of `tutor` reads the table, and `api` calls it in its process.
1. `spec` — the new version of the table and, in the same pull request, a new line, and its provider's row in privacy 5.3 checked anew. The first release of the line releases the table as a release file and a version of the Go module (R64).
2. `tutor` moves to the new tag — the submodule and the Go module of `spec` together — and makes a release: its function reads the table from `spec.Admission`, and the tests run its vectors.
3. `api` takes the new release of `tutor` and is rolled out. If the new version added a deployment fact, the operator declares it in the facts file of `api` — only when the fact holds. Until step 3 has passed, the former table works: the operator can close platform AI urgently by themselves, by removing the fact.

**A new version of the deployment configuration** (R85): `app` and the rollout of `infra` move to it together: `app` rejects an unknown field, and the rollout a build of another version.
1. `spec` — the new version of the part `deployment/` and, in the same pull request, a new line. The first release of the line releases the part as a release file and a version of the Go module (R64).
2. `app` moves to the new tag and releases a build: it carries a copy of the new schema, and the tests run the reading vectors.
3. `infra` moves to the same tag, writes the file of the new version and rolls out the new build together with it, in one rollout list (R106). Until step 3 has passed, the former build is rolled out with the former file.

**A new version of a legal text** (R130) is not a new version of the part: the next tag of `spec` carries it. `api` moves to it and is rolled out — then `app` gets the new text —, the build of the samples page of `canvas` puts in the new set from the release file, and the organizer takes the new form. A new version of the part `legal/` itself goes as the deployment configuration's does: a new line, and the readers move to it in tasks of their own.

**A new entry of the table of the age of digital consent** (R134) is not a new version of the part: the next tag of `spec` carries it, and `api`, moving to it, computes the category by the new entry. The age and the day of an entry that has come out do not change: a country's new age is a new entry. A new version of the part `consent-age/` itself — a new ISO 3166-1 code or a new rule — goes as the legal texts' does: a new line, and the readers move to it in tasks of their own.
