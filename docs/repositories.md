## 1. Принципы

- **`spec` — единственная общая зависимость.** В нём словарь, форматы и контракты. Остальные репозитории берут его по точной версии тега (R10): документы и правила — git-подмодулем `spec/` на теге, код — файлами релиза на том же теге (R21, R64). Код на Go берёт тег как версию модуля Go `github.com/altnovatrail/spec` — с форматом `spec.Format` и его типами, пакетами `types/formatv0` и `types/formatv0/open` (R72), а с линии 0.8 и с таблицей допуска `spec.Admission` и её типами `types/admissionv0` (R96), — любой другой код — подписанный файл релиза, `format-<версия>.tar.gz` и `admission-<версия>.tar.gz`. Код на TypeScript берёт типы формата пакетом npm `@altnovatrail/spec` той же версии, что тег, без `v`, — файлом того же релиза с линии 0.4 (R73). Код контрактов API — свой: на Go — вложенный модуль `github.com/altnovatrail/spec/contracts` по тегу `contracts/vX.Y.Z` с номером тега `spec`, на TypeScript — пакет npm `@altnovatrail/contracts` той же версии, файлом того же релиза с линии 0.7; тег `contracts/vX.Y.Z` релиз ставит сам (R83; четвёртая поправка 2026-11-02 к R83). С линии 0.5 тот же пакет несёт и типы элемента `<novatrail-canvas>`, `@altnovatrail/spec/canvas` (R74). Версии модулей в `go.mod`, пакеты npm и подмодуль двигают вместе, одним переходом на тег, и исключают из Dependabot (R64, R73).
- **Без циклов** — ни при сборке, ни по сети.
- **Библиотеки не зависят от сервисов, сервисы не зависят друг от друга при сборке.** Между собой сервисы говорят по сети, по контрактам из `spec`.
- **Сервис — только там, где нужен отдельный процесс.** В первом срезе сервис один — `api`. `tutor` — библиотека в его процессе; сервисом он станет, когда у него появится второй потребитель (R15).
- **Библиотеки чистые.**
  - `learner-model`, `engine` и `module-kit` — вычисления без ввода-вывода, как `domain/` в canvas-api. Поэтому их можно гонять на стенде на тысячах виртуальных учеников, а при нужде — исполнять на устройстве.
  - CLI `module-kit` только читает и пишет файлы модуля.
  - `tutor` — библиотека с одним видом ввода-вывода: запросами к поставщикам ИИ.
- **Сборка, сеть и CI — разные связи.**
  - Зависимость при сборке — импорт кода по версии.
  - Сетевая зависимость — вызов API по контракту.
  - Инструмент CI — программа, которую CI берёт по точному тегу.

  Поэтому стенд `sim` может проверять `learner-model` и `engine`, хотя сам их импортирует: CI библиотеки берёт `sim` по тегу и подставляет код pull request через `go.work`, а другую библиотеку — коммитом из файла гейта `sim`. Цикла здесь нет (R103).
- **Один образец репозитория.** Новый репозиторий начинается с заготовки `spec` — devcontainer, CLAUDE.md, AGENTS.md, RUN.md и документы (раздел 2.2, R21). Общие проверки CI из `.github` у него с первого дня, ещё до кода (R30); justfile, проверки языка и подписанные релизы приходят с кодом, по образцу canvas-api. Отличия от образца записываются, как в R46 canvas-api.
- **Довод R13 canvas-api.** Там клиент и API жили в одном репозитории, потому что «API и клиент меняются вместе, одним pull request». Здесь этот довод снимают версионируемые контракты в `spec`: сначала новый контракт, потом сервис, потом клиент. Цена — несколько pull request вместо одного; её принимаем ради узкого контекста ИИ-агентов и независимых релизов (R10).

### 2.2. Как заводить репозиторий

Новый репозиторий собирается из заготовки `repo-template/` в `spec` (R21).

1. Имя — из таблицы; репозиторий — публичный (R18). Лицензия — Apache-2.0, у кода и у содержания (R12, R20).
2. `just new-repo <имя> <вид> <карточка>` — например, `just new-repo learner-model go 3.8` — собирает рабочую копию в `.repos/<имя>` из файлов последнего релиза `spec`, старшего тега вида `vX.Y.Z`. Тег должен быть уже на GitHub: подмодуль берётся оттуда, и рецепт сверяет, что там это тот же коммит. Релиз с тегом выходит сам, после зелёного CI на `main` (R31). Вид — `go`, `typescript` или `docs`, карточка — номер раздела architecture 3. В копии:
   - `README.md` (en) — значки статуса первого дня (раздел 2.3), назначение, этап и ссылка на `spec`;
   - `CLAUDE.md` (en) — роль компонента и его место в платформе, свои документы, окружение и строка `@spec/RULES.md`. Общие правила — один файл `RULES.md` в `spec`, и его импортирует CLAUDE.md каждого репозитория: только devcontainer, точные версии, языки, никаких данных учеников и секретов, Apache-2.0, ссылки и работа между репозиториями;
   - `AGENTS.md` и `LICENSE` — те же, что в `spec`;
   - `docs/architecture.md` (ru) — назначение и границы из карточки и подраздел на каждый её пункт «Решить при детализации»;
   - `docs/decisions.md` (ru) — пустой журнал со своей нумерацией: «Следующий номер — R01». Другие репозитории цитируют его записи как «R03 api»;
   - `RUN.md` (ru) — план работ по образцу RUN.md `spec` (R19). Первый эпик — «Детализация»: по задаче на пункт «Решить при детализации», пункты, которые порознь не решить, — одной задачей, последняя задача — «Итог детализации»;
   - `.devcontainer/` — тот же, что у `spec`, со своим именем контейнера и сети и с тем, что добавляет вид репозитория (`repo-template/kinds.json`): расширения и настройки VS Code, строки в конце стадии `toolchain` и, из папки вида, строки стадии `devcontainer` с файлами, которые копирует образ. Вид `go` добавляет расширение Go с настройками, которые не дают ему ставить свои инструменты, и gopls из lock-файла `repo-template/kinds/go/gopls/`, собранный в стадии `devcontainer` версией `GOPLS_VERSION` (R102); переход на тег берёт `.devcontainer/` из того, что строит рецепт, и вносит отличия репозитория заново, так что gopls приходит с ним. `.devcontainer/gopls/` — модуль Go, который не читает ни один код, и проверки Go репозитория его не перечисляют. Вид `typescript` — расширение Biome, Biome форматтером TypeScript по умолчанию и браузер для тестов — Chrome Headless Shell из образа Playwright по тегу и digest и его системные библиотеки из снимка Ubuntu (R79); `NOVATRAIL_DEVCONTAINER=1`. Решения, на которые ссылается его Dockerfile, — решения `spec`, и в копии они с суффиксом: `(R34 spec)` (В11 `canvas`). Тома входа Claude Code, Codex и gh — общие на все контейнеры NovaTrail. Go в стадии `toolchain` уже есть: `spec` проверяет им свой модуль Go (R64), а у компонента им собирают и проверяют его код на Go. Он приходит с Dockerfile в копию любого вида, а в копии без кода на Go не используется: комментарии Dockerfile написаны так, чтобы читаться верно и в `spec`, и в копии (В8 `module-kit`). buf приходит так же: в `spec` им проверяются контракты, а в копии без контрактов он не используется (R83). Другие инструменты кода добавляются по точным версиям, когда начнётся код;
   - `spec/` — git-подмодуль на том же теге; если клон пришёл без него, контейнер достаёт его при старте. Всё добавлено в индекс, коммита нет.
3. Исполнитель заполняет пометки `FILL` по карточке компонента. `just new-repo-check <имя>` проверяет, что от заготовки ничего не осталось, а документы копии проходят проверку документов репозитория (R32). В самом репозитории её запускает `just -f spec/justfile docs-check-repo`.
4. `gh repo create altnovatrail/<имя> --public` — после подтверждения автора. Сразу за ним — `gh repo edit altnovatrail/<имя> --delete-branch-on-merge`: ветка pull request удаляется после слияния. Так настроены все репозитории организации с 2026-10-19, но новый репозиторий эту настройку сам не получает. Первый коммит и push — автора. Числовой ID нового репозитория — `gh api repos/altnovatrail/<имя> --jq .id` — та же задача `spec` вносит в `tools/release/repositories.mjs`: без него `release-verify` не примет файлов его релизов, ведь подпись сверяется с ID, а не только с адресом (R77, поправка 2026-11-01).
5. CI — общие проверки из `.github` и Dependabot, ещё до кода (R30; RUN.md, T16); проверки языка — с первым кодом репозитория. Что код добавляет к вызывающим файлам — job языка, вход CodeQL, экосистему Dependabot, релиз, — пишет сессия самого репозитория по architecture 3.3 .github, а проверки в ruleset ставит автор (поправка 2026-10-21 к R30).
6. Вопрос, который касается нескольких репозиториев, записывается в реестр `spec`: О-, П- или Т-. Сессия в другом репозитории `spec` не правит, а передаёт такой вопрос автору через таблицу 3 своего RUN.md с пометкой «в реестр spec» (RULES.md, раздел «Across repositories»).

### 2.3. Значки README

README каждого репозитория начинается значками статуса, как у MathTrail (R48):
- первая строка — CI, Release, CodeQL, номер релиза, язык, покрытие, OpenSSF Best Practices, OpenSSF Scorecard и лицензия;
- вторая, после пустой строки, — пять мер SonarCloud: code smells, reliability, security, maintainability и vulnerabilities.

Значок стоит, только когда есть то, о чём он говорит: без «no releases», «not found» и «unknown».
- **С первого дня** — CI, CodeQL, Scorecard, лицензия и меры SonarCloud. Их несёт заготовка, `repo-template/files/README.md`, с именем репозитория. Отвечают они, когда репозиторий заведён до конца: с общими проверками (раздел 2.2, пункт 5), проектом SonarCloud (R30) и первым прогоном Scorecard.
- **С первым релизом** — Release и номер релиза.
- **С первым кодом** — язык: у Go — версия из `go.mod`, у TypeScript — версия `typescript` из devDependencies `package.json`. У `spec` значка языка нет: его код — инструменты проверок в `tools/` и модуль Go, обёртка над файлами формата и их типами (R64, R72), а не код платформы.
- **С первой загрузкой покрытия в Codecov** — покрытие (RUN.md, T40).
- **С уровнем passing** — OpenSSF Best Practices, по ID проекта на bestpractices.dev (RUN.md, T41). Ответы на критерии лежат в файле `.bestpractices.json` в корне репозитория, по-английски: сайт предлагает их в анкете, а сохраняет их автор (поправка 2026-10-26 к R48). Изменённый ответ сайт из файла сам не берёт. Его приносит ссылка на анкету с изменёнными полями и `overrides` по ним: её строит из файла сессия репозитория, а сохраняет автор (поправка 2026-10-27 к R48).

## 3. Схема зависимостей

От `spec` зависят все, поэтому эти стрелки не нарисованы. Стрелка означает «зависит от». Сплошная — импорт при сборке, пунктир — инструмент CI по точному тегу или выкладка.

```mermaid
flowchart LR
    api["api"] --> tutor["tutor"]
    api --> kit["module-kit"]
    api --> eng["engine"]
    api --> lm["learner-model"]
    eng --> lm
    sim["sim"] --> eng
    sim --> lm
    tutor -->|"eval-раннер"| kit
    app["app"] --> canvas["canvas"]
    app --> smap["skill-map"]
    mods["modules"] -.->|"инструменты CI"| kit
    mods -.-> sim
    mods -.->|"с этапа 2"| tutor
    canvas -.->|"CI страницы образцов: релиз"| mods
    canvas -.->|"CI страницы образцов"| kit
    infra["infra"] -.->|"выкатывает релизы"| api
    infra -.-> app
    reg["module-registry, этап 4"] --> kit
    pipe["module-pipeline, этап 4"] --> kit
    pipe --> tutor
    site["site, этап 3"] --> smap
    wt["widget-template, этап 4"]
```

- Не нарисованы и связи `canvas` и `tutor`, по той же причине, что гейт `sim` ниже: они берут релизы друг друга как инструменты CI. CI `tutor` — синтетические образцы `canvas` (R38), CI `canvas` — открытые виды задач замера `tutor`, пока у `modules` нет содержания (поправка 2026-10-21 к R25). Цикла при сборке нет: каждая сторона берёт уже вышедший релиз другой по точному тегу, а первым выходит релиз `tutor` (R38).
- Гейт `sim` для `learner-model` и `engine` не нарисован, хотя это тоже инструмент CI. Вместе с импортом `sim → engine` такая стрелка читалась бы как цикл, а цикла нет (раздел 1, Т-16).
- Общие проверки CI из `.github` берут все репозитории (R30); эти стрелки тоже не нарисованы.
- CI `spec` проверяет примеры модулей обычным валидатором JSON Schema, а не `module-kit`: иначе `spec` зависел бы от того, кто зависит от него. Вектор правила части он проверяет схемой и правилами YAML, а само правило — CI `module-kit` (R45). Правила YAML и правила всего модуля — раскладку, ID в именах файлов и сигнатуры медиафайлов — `format-check` проверяет сам и сам строит открытый вид, с T29 — и вердикты векторов вердикта, кроме тех, что условию даёт Starlark, с T30 — ловушки, которые в них называют неверные значения, и что проверка утечки находит в текстах векторов утечки, с T31 — и правило `lesson.no-leaks` на уроках, а с T34 — ярусы и пакет модуля, его канонический вид и дайджесты: это вторая реализация рядом с `module-kit`, и векторы сверяют обе (R46, R51, R56, R57, R58, R62).
- В схеме из диалога с Gemini реестр и конвейер зависели друг от друга. Здесь цикла нет: конвейер публикует через API реестра, а реестр о конвейере не знает.
- `widget-template` ни от кого, кроме `spec`, не зависит: протокол виджета задан в `spec`, а сторона приложения — в `canvas`.

## 4. Потоки между репозиториями

Потоки во время работы платформы — в architecture 4. Здесь — как изменения проходят между репозиториями.

**От автора к ученику:**
1. Модуль лежит в `modules`: YAML, медиа, eval-набор.
2. CI проверяет его:
   - `module-kit` — схему, граф без циклов, ссылки, медиафайлы, ключи, утечки в текстах автора, которые ученик видит до решения, — и в текстах урока, который называет задачу (R57; R58);
   - `sim` — если изменилось то, что стенд читает из пакета, — на пакете pull request, с инвариантами и абсолютными порогами, без полос; с первого тега `sim`: до него гейта нет (R76; R103). Pull request, который меняет тег `sim`, гоняет все графы;
   - с этапа 2 — eval-раннер `tutor` на eval-наборе модуля.
3. На релизе `module-kit` собирает пакет — канонический вид для сервера, часть для устройства и опись с их дайджестами, без eval-набора (R62), — и индекс модулей: из индекса прошлого релиза, с записью каждой опубликованной версии и отметками о снятии (R63). Общий workflow релиза из `.github` подписывает их (R17).
4. `api` берёт пакеты по индексу релиза `modules`, который закрепляет его конфигурация — тег релиза и дайджест индекса, а дайджесты пакетов называет индекс (R63; R07 api); попытка хранит дайджест своего пакета — дайджест его описи (R62).
5. `app` получает от `api` открытый вид задачи — без ключа, решения и ловушек, без навыков, полосы и сложности, без приёмов, случая попроще и фраз-утечек (R57). Ключ остаётся на сервере, решение приходит после верного ответа (R05), а навыки, полосу и сложность читает только сервер (R51). Открытый вид урока приходит без его навыков и возрастных категорий (R58). Открытые виды паспорта, графа навыков, каталога приёмов и шагов решения `app` получает по дайджесту пакета — попытки, прохождения урока или текущей версии подключённого модуля — и кеширует по нему, а медиафайлы — из части пакета для устройства, которую раздаёт `api` (R62 и поправка 2026-11-04 к нему; R99).

Ключи открытых модулей публичны, как и сами модули. R05 не охраняет тайну, а лишь не держит ключ в приложении ученика.

**CI алгоритмов:**
- каждое изменение `learner-model` или `engine` прогоняется на стенде `sim`, на виртуальных учениках разных популяций (concepts 15). CI библиотеки берёт `sim` по точному тегу и SHA его коммита, своим job, и пишет `go.work` на лету, не коммитя его: `sim`, код pull request и другую библиотеку — коммитом из файла гейта `sim`. Гейт идёт на каждом pull request и каждом коммите `main` и держит мерж (R103);
- первая версия каждой библиотеки — до гейта: её проверяют свои тесты, а `sim` ставит на ней стенд и пишет критерий до первого кандидата — первого изменения после неё (R103);
- критерий записан до первого прогона кандидата (R163 standalone);
- изменение, которое ухудшает критерий, не сливается;
- порядок релизов (R103): изменение, которое ломает API стенда или двигает числа, сначала записывается в `sim` на коммите своего pull request, выходит тег `sim`, pull request библиотеки поднимает тег и сливается, а после релиза библиотеки `sim` поднимает `go.mod`. Пара «порог „освоено“ и цель коридора» и изменение `learner-model`, которое ломает API `engine`, идут одним тегом `sim`: файл гейта называет оба коммита, `learner-model` сливается, когда pull request `engine` прошёл ревью, а `api` переходит на обе версии вместе. Релиз `sim` выходит сам после зелёного CI на `main`, а тег у вызывающих поднимает их сессия.

**Смена модели ИИ:**
- новую модель для возможности ИИ допускают, когда она проходит eval-набор возможности и eval-наборы всех опубликованных модулей с этой возможностью;
- порядок (В9 `modules`; R04 modules): `tutor` выпускает тег, где модель в списке допущенных, когда она прошла eval-набор возможности в CI `tutor`; pull request `modules` переходит на этот тег, и eval-раннер гоняет eval-наборы всех модулей — они лежат в git `modules`, вне пакета и файлов релиза (R62); `api` переходит на такой тег `tutor` только после мержа этого pull request. Если он красный, `tutor` выпускает следующий тег без модели, а `api` остаётся на прежнем: откат — только вперёд (Т-19). Что `api` ждёт `modules`, держит ревью pull request `api`;
- ложные тревоги считаются по вердикту: наблюдение модели проходит через `module-kit`, как в работе платформы (R04). У оценки по рубрике вердикта нет, и её мерят ложные тревоги на выполненных критериях и согласие с людьми (R71). Что раннер отдаёт — отчёт без содержания работ, по которому считаются меры, — и что лежит в eval-наборе модуля, пишет протокол eval, а для допуска годится только отчёт с вердиктами `module-kit` ([текст контрактов](../contracts/README.md), разделы 13 и 14; R95).

**Новая версия формата модуля** (R44). Зависимости при сборке и инструменты CI каждый берёт по точной версии, поэтому шаг не ломает тех, кто ещё не перешёл. А `api` и `app` говорят по сети и, пока формат — v0, выходят вместе:
1. `spec` — новая версия формата и тем же pull request новая линия; иначе `release-version` его не пропустит. Первый релиз линии выпускает версию формата файлом релиза и версией модуля Go (R64).
2. То, что читает модули в CI `modules`, переходит на новый тег — подмодулем и модулем Go `spec` вместе: `module-kit` и, с этапа 2, eval-раннер `tutor`. Если изменился открытый вид, `canvas` выпускает пакет с новыми типами (R36).
3. `modules` — одним pull request: новые теги `module-kit` и `tutor` в CI, паспорта и содержание всех модулей. `sim` в нём не гоняется: пакета новой версии он на прежнем теге не прочтёт. В переходе не меняют ничего из того, что стенд читает из пакета, — ни граф, ни привязки задач, — кроме самой записи в новой версии формата: это держит ревью `modules` (R03 modules; поправка 2026-11-07 к R103), а меняют это отдельным pull request после шага 4.
4. `sim` переходит на новый тег и на пакеты из нового релиза `modules`, а `modules` берёт в CI новый тег `sim`. `learner-model` и `engine` берут новый `sim` своим переходом: свой гейт они держат на прежнем теге.
5. `api` берёт новый `module-kit` и новые пакеты, а если изменился открытый вид, вместе с ним выходит `app` с новым `canvas` — одним списком точных версий (Т-19). CI `canvas` берёт новый релиз `modules` и новый тег `module-kit`.

Пока формат — v0, читается только текущая версия, и модули переходят все сразу; так же — на v1, ведь v0 с выходом v1 из окна уходит. С v2 окно — текущая мажорная версия и предыдущая — даёт модулям переходить по одному, а `api` и `app` — порознь.

**Новая версия таблицы допуска** (R96) — короче: таблицу читает одна функция допуска `tutor`, а зовёт её `api` в своём процессе.
1. `spec` — новая версия таблицы и тем же pull request новая линия, а её строка поставщика в privacy 5.3 сверена заново. Первый релиз линии выпускает таблицу файлом релиза и версией модуля Go (R64).
2. `tutor` переходит на новый тег — подмодулем и модулем Go `spec` вместе — и выпускает релиз: его функция читает таблицу из `spec.Admission`, а тесты гоняют её векторы.
3. `api` берёт новый релиз `tutor` и выкатывается. Если новая версия добавила факт развёртывания, оператор заявляет его в файле фактов `api` — только когда факт держится. Пока шаг 3 не прошёл, работает прежняя таблица: срочно закрыть ИИ платформы оператор может сам, сняв факт.

**Новая версия конфигурации развёртывания** (R85) — `app` и выкатка `infra` переходят на неё вместе: `app` отвергает незнакомое поле, а выкатка — сборку другой версии.
1. `spec` — новая версия части `deployment/` и тем же pull request новая линия. Первый релиз линии выпускает часть файлом релиза и версией модуля Go (R64).
2. `app` переходит на новый тег и выпускает сборку: она несёт копию новой схемы, а тесты гоняют векторы чтения.
3. `infra` переходит на тот же тег, пишет файл новой версии и выкатывает новую сборку вместе с ним, одним списком выкатки (R106). Пока шаг 3 не прошёл, выкатывается прежняя сборка с прежним файлом.

**Новая версия юридического текста** (R130) — не новая версия части: её несёт следующий тег `spec`. `api` переходит на него и выкатывается — тогда `app` получает новый текст, — сборка страницы образцов `canvas` кладёт новый набор из файла релиза, а организатор берёт новую форму. Новая версия самой части `legal/` идёт, как у конфигурации развёртывания: новая линия, и читатели переходят на неё своими задачами.

**Новая запись таблицы возраста цифрового согласия** (R134) — не новая версия части: её несёт следующий тег `spec`, и `api`, переходя на него, вычисляет категорию по новой записи. Возраст и день записи, которая вышла, не меняются: новый возраст страны — новая запись. Новая версия самой части `consent-age/` — новый код ISO 3166-1 или новое правило — идёт, как у юридических текстов: новая линия, и читатели переходят на неё своими задачами.

  - формат выгрузки (R09);

Пример целого модуля — папка, разложенная как модуль (R46). CI `spec` проверяет их обычным валидатором JSON Schema, `ajv`, рецептом `just format-check` (раздел 3).

Чего в `spec` нет: кода сервисов и библиотек платформы, содержания модулей, данных учеников. Пакет Go `spec` — не библиотека платформы: он только встраивает файлы формата, чтобы код взял их по тегу (R64), а пакеты `types/` несут только типы и константы, без кода (R72), и пакет npm `@altnovatrail/spec` — одни объявления (R73). Код, который buf генерирует по контрактам API, — тоже не библиотека платформы: сообщения и заглушки сервисов Connect, без логики, во вложенном модуле Go `contracts` и в пакете npm `@altnovatrail/contracts` (R83).

## 6. Порядок появления

1. **spec** — словарь, решения, приватность, архитектура; затем формат модуля v0, пакет, наблюдение и протокол eval.
2. **.github** — общие проверки, до первого репозитория с кодом. Общие workflow для кода приходят с кодом, на котором проверяются (R03 .github): обёртка Go и релиз — с первым кодом `module-kit`, обёртка TypeScript — с первым кодом на TypeScript, у `canvas`.
3. **modules и module-kit:**
   - порт эталонных задач standalone с ловушками — 753: первая пачка на коммите 89986bc, остальные 726 на 42b4408 — и шаблоны с решателями: из 39 шаблонов standalone перенесено 19, а остальные названы с причиной (R05 с поправкой 2026-11-08 и R22 modules); шесть, чей решатель читает картинку, ждут картинок экземпляров формата 0.4 (R108). Сначала — первая пачка олимпиадной математики: 20–30 задач на три полосы, без шаблонов и решателей, уроками; паспорт называет в аудитории и `adult`. Остальной порт — после неё (R76): его сделал эпик E3 `modules`, 2026-11-08 (закрытая строка 3.7 [COORDINATION.md](../COORDINATION.md));
   - небольшие наборы школьной математики 3 класса и коротких сочинений на английском (R41);
   - CLI `module-kit` проверяет модули и собирает пакеты и индекс, а общий workflow релиза подписывает их (R17).

   Так формат v0 сразу проверяется на двух предметах (R08).
4. **learner-model, engine и sim** — вместе: стенду нужны и модель, и правило выбора. Стенд и критерий появляются до первого кандидата. Отправная модель — модель standalone с уровнем на модуль (concepts 11).
5. **tutor и canvas** — первый код этапа 2. У `tutor` это доска проверки: автор решает задачи доски, модели Claude, которые он выбирает, читают и оценивают его работу, а автор отмечает, права ли каждая (R43). Какие это задачи и сколько их, говорит architecture 3.3 tutor. За доской шёл замер хода письма, только на моделях Claude: он сделан 2026-10-26 и пользы хода письма не показал (R52). Остальные замеры чтения ИИ — по видам канвы и ответа, для Т-23 и О-8 — эпик E4 `tutor` (поправка 2026-10-26 к R43). Он сделан 2026-10-28 на синтетике и трёх листах автора: по его выводам решены Т-23, Т-33, О-8 и О-22 и высота цифры по умолчанию (R67–R69, R71; поправка 2026-10-28 к R51), а пороги и цели повторяются на образцах взрослых добровольцев (П-16).
   - Сначала узнать, хорошо ли ИИ читает работу, потом строить остальное (R60 canvas-api).
   - Листы для замера хода письма дал `tutor`: лист 1 автор написал на доске, а 39 нарисовал код (R26 tutor). Образцы взрослых добровольцев, в том числе подражающих детскому почерку, делаются на странице образцов `canvas` (П-16; поправка 2026-10-26 к R25).
   - Образцы детей — только с отдельным согласием (П-10).
   - Замер `tutor` автор начал раньше этого пункта, 2026-10-20, параллельно пунктам 3 и 4 (R01 tutor). 2026-10-22 автор отложил его ради доски (R19 tutor), 2026-10-23 вернул — только на моделях Claude (R21 tutor), — а 2026-10-26 он сделан (R27 tutor).
   - Код `canvas` тоже идёт раньше пунктов 3 и 4, эпиком E2 рядом с детализацией (R02 canvas). Первым идёт лист для рукописи — элемент `<novatrail-canvas>` (R17 canvas), — а страница образцов, синтетические образцы и сборка, которая открывается из файла, ждут, пока замеру не понадобятся образцы добровольцев или детей: это эпик E5 `canvas` (поправки 2026-10-22 и 2026-10-26 к R43). Задачи замера, пока у `modules` и `module-kit` нет кода, сборка страницы берёт из релиза `tutor` (поправка 2026-10-21 к R25), а он ждёт в отложенном эпике E3 `tutor`.
6. **api, app, skill-map и infra** — первый срез с учеником. До первого ребёнка — согласие родителя и договоры с поставщиками ИИ (П-1, П-3). Регион данных — до первого развёртывания (П-11).
   - Первое приложение — первая сборка `app` с `api`, на которой автор сам решает задачи в браузере, локально: с рукописью, уроками и движком, со входом, без детей и без развёртывания (R76).
7. **site** — к бете, этап 3. **module-registry, module-pipeline и widget-template** — с третьим модулем и сторонними авторами, после формата v1 (этап 4; R08; product 11).

Репозиторий можно завести раньше, чем начнётся его код: детализация начинается с документов (раздел 2.2).

По этому порядку работу других репозиториев ведёт сквозной план [COORDINATION.md](../COORDINATION.md): какая задача какого репозитория какую ждёт, со ссылками на их RUN.md (R76).

## 9. Сессии Claude Code

Как меряется расход сессий Claude Code в репозиториях NovaTrail и с чем сравнивают свои числа задачи эпика E10 (RUN.md, T118–T126). Цифры здесь — только суммы. Текста расшифровок нет ни здесь, ни в выводе рецепта: в расшифровках бывает всё, что вводил автор.

### 9.1. Замер

`just tokens-report` в `spec`, а в другом репозитории `just -f spec/justfile tokens-report`, читает расшифровки Claude Code этой машины для того репозитория git, из которого его запустили, и печатает числа по сессиям и в сумме. Код — `tools/tokens/`, тесты — `just tokens-test`, на синтетических расшифровках.

- **Где расшифровки.** Сессия пишется в `<config>/projects/<папка>/<сессия>.jsonl`, её субагенты — в `<config>/projects/<папка>/<сессия>/subagents/agent-<id>.jsonl`. `<config>` — `$CLAUDE_CONFIG_DIR`, в devcontainer это `/home/vscode/.claude` на томе `novatrail-claude`, а без переменной — `~/.claude`.
  - `<папка>` — путь корня git, где каждый знак, кроме латинской буквы и цифры, заменён на «-»: `/workspaces/spec` — `-workspaces-spec`, `/workspaces/.github` — `-workspaces--github`.
  - Сессии копий в `.repos/` начинаются в `spec` и считаются за ним.
  - Облачная сессия держит расшифровку не на этой машине, и рецепт её не видит.
  - Флаг `--project <папка>` задаёт папку явно.
- **Вызов модели** — сообщение модели, один раз по его `id`: расшифровка повторяет сообщение и его `usage` в записи на каждый блок. Поля кеша у повторов совпадают, а `output_tokens` растёт, и берётся наибольший. В расшифровках `spec` до начала T118, 2026-11-11T03:59:01Z, — 74 455 записей сообщений, из них 32 465 вызовов, и у 6 330 вывод различался.
  - Ошибки API (модель `<synthetic>`) не считаются.
  - Субагенты считаются за своей сессией, но отдельной колонкой.
  - Контекст вызова — некешированный ввод, чтение из кеша и запись в кеш, на 5 минут и на час; стоимость — по ценам раздела 9.2.
  - Сверка — собственная оценка Claude Code в записях `cost-state`. За всё время `spec` до 2026-11-11T03:59:01Z это $2 860,07 против $2 841,86 по ценам раздела 9.2.
- **Что вошло между вызовами** — результаты инструментов, слова автора, напоминания, вложения — измерено, а не прикинуто по длине.
  - Прирост контекста — контекст вызова минус контекст прошлого вызова и его вывод. Он делится между вошедшим пропорционально знакам.
  - Вывод модели — своя группа.
  - Вложение считается по тому, что оно отрисовало в контекст (поле `rendered`). Снимок системного промпта — только в начале сессии, а записи без отрисовки — отложенные инструменты, сброшенное рассуждение — не считаются.
  - Начало сессии, начало субагента и то, что оставило сжатие, входят целиком — контекстом первого вызова.
  - Сессия, продолженная в новой расшифровке, копирует в неё свою историю, а её уже посчитала прежняя расшифровка. Скопированное отбрасывается, а история входит целиком, группой «history of a resumed session». В расшифровках `spec` до T118 таких нет.
- **«Несёт»** — токены вошедшего, умноженные на число вызовов той же расшифровки, в контексте которых оно лежит, до сжатия. Это то, во что вошедшее обходится через кеш: расход растёт с длиной сессии, а не с одним чтением.
  - Сумма по группам почти равна сумме контекстов всех вызовов: за всё время `spec` — 7 638 млн из 7 649 млн.
  - Недостача — там, где прирост меньше нуля, а в окне `--since` — ещё и то, что вошло до его начала.
- **Группы:**
  - по инструменту или виду;
  - по файлу:
    - у Read, Edit, Write, NotebookEdit, Grep и Glob — путь из вызова; у Read отдельно считается, сколько чтений частичных (`offset`, `limit`, `pages`);
    - у Bash — файлы, которые команда называет и которые есть на диске сейчас, не больше десяти; результат делится между ними поровну. Относительный путь читается от папки, куда перед ним перешли `cd` или `git -C` той же команды, а иначе — от корня репозитория: там начинается каждая команда сессии. Это «команда называет», а не обязательно «читает»: `git add RUN.md` тоже даёт `RUN.md`;
  - по программе Bash — первое слово после `cd`, скобки подоболочки, присвоений и `timeout` с его флагами, а у `just`, `gh`, `git`, `npm`, `npx`, `node`, `go` и `buf` — ещё и второе, после флагов, что идут до него: `git -C .repos/app log` — это `git log`.

  Путь печатается от корня репозитория или от `~`. ID сессии в пути печатается как `<session>`, имя файла с выводом, сохранённым из контекста, — как `*`.
- **Начало сессии** — медиана контекста первого вызова и его состав в среднем на сессию: системный промпт, файлы CLAUDE.md, RULES.md и MEMORY.md, список навыков, инструкции MCP и другие вложения. Их знаки переводятся в токены по отношению знаков к токенам всего, что вошло между вызовами за тот же период. «Остаток» — то, чего в расшифровке нет: описания инструментов.
- **Чего не видит** — вызовов `claude -p --no-session-persistence`: у них нет расшифровки. Так зовёт модель graphify (раздел 9.4).
- **Что печатается** — только числа, пути, имена инструментов, вложений и программ, ID сессий и первый номер задачи `T…` из первой реплики автора. Программа или второе слово, которые не похожи на имя, печатаются как `other`.
- **Флаги:**
  - `--since` и `--until` — дата или время ISO 8601. Время без пояса считается в UTC, `--until` не включается, а дата значит начало суток;
  - `--project` — папка расшифровок другого проекта: имя под `<config>/projects`, которое начинается с «-» и потому пишется через «=» (`--project=-workspaces-app`), или путь к ней. Пути печатаются от папки, где начиналось большинство её сессий;
  - `--top` — длина списков, по умолчанию 20;
  - `--json` — те же числа в JSON, для сравнения линий.

### 9.2. Веса

Цены — [страница цен Anthropic](https://platform.claude.com/docs/en/about-claude/pricing), прочитано 2026-11-11. Строки таблицы: «Claude Opus 5.5 | $4 / MTok | $5 / MTok | $8 / MTok | $0.20 / MTok | $20 / MTok» и «Claude Haiku 4.5 | $1 / MTok | $1.25 / MTok | $2 / MTok | $0.10 / MTok | $5 / MTok». Столбцы — ввод, запись в кеш на 5 минут, на час, чтение из кеша и вывод. Там же: «Cache hits and refreshes on Claude Opus 5.5 and Claude Sonnet 5.5 are priced at 0.05x the base input price».

- Длинный контекст цены не меняет: «Claude 4.6 and later models (except Claude Haiku 5.5)… include the full 1M token context window at standard pricing».
- У быстрого режима свои цены, и вызов в нём рецепт считает вызовом без цены. В расшифровках `spec` таких нет: у всех `speed` — `standard`.

Цены — в `tools/tokens/prices.mjs`; новая модель или новая цена — правка и там, и здесь. Как расход идёт в лимиты подписки, Anthropic не публикует (Т-39). Поэтому замер взвешивает вызов по этим ценам, а на пробе T119 вес один раз сверяется с долей лимита из `/usage` (R142).

### 9.4. Средства карты кода

Средства, которые дают агенту карту кода вместо чтения файлов, разобраны по первоисточникам и пробой на `tutor` и `spec` (RUN.md, T119). Всё прочитано 2026-11-11.

**По первоисточникам:**

- **Языковой сервер в Claude Code** — плагины `gopls-lsp` и `typescript-lsp` из `claude-plugins-official`.
  - Что даёт ([Code intelligence](https://code.claude.com/docs/en/plugins/code-intelligence.md)): «gives Claude the live diagnostics and go-to-definition that your editor has… and finds definitions and references by symbol instead of by text search». Инструмент `LSP` — «jump to definitions, find references, report type errors and warnings» ([Tools reference](https://code.claude.com/docs/en/tools-reference.md)).
  - Сервер ставится отдельно: «It doesn't include the language server. Install the language server binary first».
  - Диагностика после каждой правки сама идёт в контекст: «each time Claude edits or writes a file the server handles, Claude gets the errors and warnings the server reports».
  - В облачной сессии не работает: «In cloud sessions, Claude Code doesn't start plugin language servers».
  - Об экономии токенов страница не говорит ничего.
  - Документов не читает: только код, для которого есть сервер.
  - Содержимое никуда, кроме модели сессии, не уходит.
  - gopls — BSD-3-Clause, и он уже есть в devcontainer у репозиториев Go (R102). Для TypeScript нужен `typescript-language-server`, пакет npm.
- **Статья [arXiv 2608.13568](https://arxiv.org/abs/2608.13568)** — P. Xu, 29 июня 2026, предварительное исследование на репозиториях Python и TypeScript; Claude Opus 4.8, Sonnet 4.6 и Haiku 4.5.
  - Главное: «The answer is conditional and usually negative. On symbol-named localization the LSP costs tokens (+6% to +118%) and the agent ignores it when free. On reference-completeness it buys precision but not token savings… it saves tokens only for the weakest model».
  - На переименованиях по многим файлам: «grep solves multi-file renames perfectly, a location-only LSP fails three-quarters of them by missing a call site».
- **Serena** ([oraios/serena `v2.1.0`](https://github.com/oraios/serena/blob/v2.1.0/README.md)) — сервер MCP поверх языковых серверов: «semantic code retrieval, editing, refactoring and debugging tools… operating at the symbol level».
  - Языков больше 40, среди них Go, TypeScript и Markdown, но как языковые серверы, а не чтение текста.
  - Лицензия ([LICENSE](https://github.com/oraios/serena/blob/v2.1.0/LICENSE)): «SolidLSP under the MIT License and the Serena application under GPL-3.0-or-later», так что пакет `serena-agent` в целом — GPL-3.0-or-later. По R12 он допустим только как средство разработки, которое не поставляется, и только именованным исключением.
  - Python `>=3.11, <3.15`, ставится через `uv tool install -p 3.13 serena-agent`. Языковые серверы скачивает сама — «downloads or installs certain language server dependencies on demand», с закреплёнными версиями и сверкой хеша ([security](https://github.com/oraios/serena/blob/v2.1.0/docs/02-usage/070_security.md)).
  - Пишет `.serena/` в репозиторий (настройки проекта и «memories») и `~/.serena/`.
  - Содержимое по умолчанию остаётся на машине; токены считает локально.
  - Чисел экономии нет.
- **graphify** ([Graphify-Labs/graphify `v0.9.106`](https://github.com/Graphify-Labs/graphify/blob/v0.9.106/README.md)) — граф знаний проекта: «maps your entire project (code, docs, PDFs, images, videos) into a knowledge graph you can query instead of grepping».
  - Код разбирает локально, по tree-sitter, около 40 языков, Go и TypeScript среди них: «Code files: processed locally via tree-sitter. Nothing leaves your machine».
  - Документы читает модель: «Docs, PDFs, images: sent to your AI assistant for semantic extraction (via the `/graphify` skill, using whatever model your IDE session runs)». Без навыка — через `claude` CLI по подписке или по ключу API другого поставщика.
  - О цене документов: «semantic extraction of docs, papers and images runs the model over every file, which can cost minutes and tens of thousands of tokens» ([skill.md](https://github.com/Graphify-Labs/graphify/blob/v0.9.106/graphify/skill.md)).
  - Лицензия — Apache-2.0 ([LICENSE](https://github.com/Graphify-Labs/graphify/blob/v0.9.106/LICENSE)); Python `>=3.10,<3.15`, пакет PyPI `graphifyy`.
  - Пишет `graphify-out/` (граф, отчёт, кеш). Команда `graphify claude install` дописывает раздел в CLAUDE.md и ставит хуки PreToolUse на Bash, Grep, Read и Glob в `.claude/settings.json`. Обновление — `graphify update` (код, без модели), `watch` и git-хуки.
  - Числа самого проекта: «71.5x fewer tokens per query» на корпусе из 52 файлов и «~1x» на малой библиотеке ([how-it-works](https://github.com/Graphify-Labs/graphify/blob/v0.9.106/docs/how-it-works.md)).
- **Индекс по эмбеддингам** — [claude-context](https://github.com/zilliztech/claude-context), MIT, Node.js.
  - «Languages: TypeScript, JavaScript, Python, Java, C++, C#, Go, Rust, PHP, Ruby, Swift, Kotlin, Scala, Markdown».
  - Эмбеддинги — «OpenAI, VoyageAI, Ollama, Gemini», а индекс лежит в базе векторов Milvus или Zilliz Cloud. Значит, текст репозитория уходит поставщику эмбеддингов по своему ключу, если не поднимать Ollama локально.

- **Упаковщик** — [repomix](https://github.com/yamadashy/repomix), MIT, `v1.19.0`: весь репозиторий одним файлом. Агенту, который читает по нужде, это противоположно: такой файл весь едет в контексте.
- **Структурный поиск** — [ast-grep](https://github.com/ast-grep/ast-grep), MIT, `0.51.2`, бинарник Rust: поиск по AST кода, а не по Markdown. Его сервер MCP помечен «experimental».
- **Карта в духе aider** — [aider](https://aider.chat/docs/repomap.html): «a concise map of your whole git repository that includes the most important classes and functions along with their types and call signatures», по умолчанию «1k tokens». Сервера MCP от самого aider нет, а сторонний RepoMapper без версий не читает Markdown.

В пробу пошли языковой сервер, Serena и graphify. Индекс по эмбеддингам — нет: текст уходит поставщику эмбеддингов, а это новый получатель данных, которого privacy не называет, и ключ. Упаковщик, ast-grep и карта aider тоже не пошли: они либо противоречат чтению по нужде, либо не читают документов, либо не готовы.
