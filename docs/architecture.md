## 1. Principles

- **The boundary of R03 runs along the code.**
  - Everything that calls a model is in `tutor`. A model that would read the work on the device is its code too: its weights, eval and admission are with `tutor`, and the verdict is with `module-kit` (R66). In the first slice there is no such reading.
  - The verdict is given by `module-kit`, the learner model is computed by `learner-model`, the next lesson or task is chosen by `engine`. None of these libraries calls a model.
  - CI of `api` checks the full list of dependencies: the SDKs of AI providers get into the build only through `tutor` (R15).
- **Of the platform's parts, only `api` stores learners' data on the server.**
  - `tutor` stores nothing. The types of its requests have no fields for the learner's and account's identifiers, so AI sees the work but does not know whose it is (R15; privacy 1, 5.1).
  - Outside the platform, part of the data is held by the sign-in service, the AI providers and, from stage 3, payment (section 5).
- **A separate process only where it is needed.** In the first slice there is one service, `api`; `tutor`, `module-kit`, `learner-model` and `engine` are libraries in its process. `tutor` will become a service when it gets a second consumer (R15).
- **The key of an unsolved task is only on the server.** The app gets the task's open view (R05). The open view is built by `module-kit` by the marks `x-open` in the format's schemas: a field without the mark is closed, so a new field of the format is closed until it is explicitly opened (R45).
- **Reproducibility** (R03):
  - an attempt stores the digest of its module package, the module format version, the version of `module-kit` and the seed. A package digest is the digest of its inventory, and it depends only on the module's files and the format version of its manifest ([format text](../format/README.md), section 25; R62). A module is checked and executed by the format version that its manifest names, and a new format version does not change its verdict until the author moves the module to it (R44);
  - an engine choice stores what its replay by the evidence log needs: the versions of `engine` and `learner-model`; the package digests, and which of them are the engine's modules, connected and suitable for the learner; the seed, empty, since the engine takes no randomness, as the version of `engine` in the record shows; the reason code; the release of `modules`, by whose index the withdrawal marks are known; the number of the last evidence it was made by; the time of the choice, for which the model computed retention and the review date; the grade by which the model computed the starting point of modules without evidence; whether the pool was limited to tasks without AI; the skill chosen on the skill map; the age category of the profile, by which `api` selected the pool and the lessons. The category changes at the yearly refinement and at a change of country, and the connections at any time, and the digests also name the modules of the log, which only `learner-model` gets: so the record keeps them (R80, R107; R04 and R08 learner-model; concepts 12). The summary of issues, the lesson runs and closed attempts with a rubric the engine saw, and the last attempt and its outcome the replay derives from the records of choices and attempts before the time of the choice: once written, they do not change (R104, R107);
  - a verdict is repeated by the stored observation, a choice by the evidence log (R80); both without AI. A verdict of a task from paper is repeated only within its attempt: once it ends, `api` keeps nothing of it (R162; privacy 4.1);
  - the generator of randomness and the derivation of seeds are set by `spec`, with test vectors: PCG, as in Go's `math/rand/v2`, and places of randomness, as at standalone's simulator ([format text](../format/README.md), section 22; R59). An instance of a task template is repeated by the attempt's package and seed: it is chosen by one number of the place `template`, the task's ID, `instance` ([format text](../format/README.md), section 23; R60).
- **Our own parts of the interface are assembled at build time, others' code runs only in an iframe sandbox** (R16, section 6).
- **No clusters, queues or event bus of our own** (R11). The parts talk by synchronous requests by the contracts from `spec`: `app` with `api` by Connect, with unary calls, and the code of the contracts comes from the releases of `spec` (R83). Background work is Cloud Run jobs on a schedule, as in canvas-api.
- **Logs without direct identifiers, IP addresses and content** (R09; privacy 4).
  - Cloud Run itself writes request logs with the standard field `httpRequest`, and it has `remoteIp`, the client's IP address. canvas-api recorded the same about the logs of Cloud Run and Firebase Hosting (privacy 4 canvas-api).
  - COPPA counts an IP address among persistent identifiers, that is, among personal information (16 CFR 312.2).
  - So the request logs are excluded in Cloud Logging by the filter of each sink: Google accepts the record and discards it before storage (R07 infra), — and the logs' region is `us-east4`, as for the whole platform (R109).
  - The hosting of `app`, Firebase Hosting, and the sign-in service, Firebase Auth, store IP addresses in their logs themselves, for several months and several weeks; `infra` does not turn on the export of the Hosting logs to Cloud Logging (R06 infra; section 3.12; R128).

  Sources: sources 3.1, 4.1, 4.2 and 4.4.

## 3. Components

Each component has a card: what it does and does not do, its data and links, its repository and stage (product 11). The items "To decide when detailed" are what the work in its repository begins with (repositories 2.2). A question that concerns several repositories is in the registers of `spec`, and the card refers to it.

A repository's detailing may name items beyond its card or skip one of them; the card follows it by a row «в реестр spec» of the repository's table 3 once the decision is made, not in advance.

### 3.2. canvas — canvases

- **Does:**
  - canvas kinds (concepts 8); in the first slice, the handwriting sheet and the workbook (product 10; R41). A workbook is a page of 1000 × 1400 units, like a sheet, without a grid: the item lines with boxes are put on the template layer by its layout, by the task and its own table of widths, not by the device's font (R34–R36 canvas). A task from paper is solved on a sheet whose grid the learner turns by the bar's last button — dots as it comes, lines, blank, squares, round (R88 canvas) —, with the task's crop over it as tracing paper in place of the template: the learner moves it by its grip "Move the task", hides and shows it by the button atop the tools, and writes on it as on the sheet (concepts 8; R90; R162);
  - layers: the template, the widget, the demo, the learner's work, the tutor's layer. On the demo layer is the demo of a lesson's worked example: its parts open one at a time and hide all at once, and a picture in a sheet area stands at the size of the area. From format 0.4 an example stands on a workbook too: the example's lines by the page layout, and a part of the demo fills a box with its value (R111). On the sheet and on the workbook of an example the learner does not write (R58). The parts are opened one at a time and the whole demo is hidden by the learner with the element's buttons, "Next" and "Demo" (R42 canvas). An example has no bar: "Next" and "Demo" stand in a glass row at the element's bottom, and after them the named slot `actions`, where `app` puts its "Continue"; the row's accessibility is the element's (R36);
  - tools; the eraser removes a stroke whole, and the hand, the element's own tool on every sheet the learner writes on and not the format's, moves the sheet under any pointer (R88 canvas). The tool panel is the vertical glass bar of the interface mockup, in the style properties that `app` sets, as it sets `--novatrail-canvas-*` (R17 app) — the accent of the tool in use and of the focus ring `--novatrail-canvas-accent`, the glass `--novatrail-canvas-glass`, `--novatrail-canvas-top`, the offset of the band in whose middle the bar stands, and `--novatrail-canvas-pad-top` and `--novatrail-canvas-pad-bottom`, how far the bars of `app` float over the element's top and bottom —, and its accessibility stays the element's (R36, R148). On a phone the bar stays at the left edge (R90, R148). The sheet goes past the task's page, which stands at its left, right as far as the ink and one view more, and down as far and two views more; "Zoom in" and "Zoom out" of the bar step the page's zoom of it by quarters from 50 % to 200 %, and a pinch of two fingers sets it; the hand, two fingers, the wheel and the keys move it (R73 canvas).   - the capture of strokes with time and pressure;
  - the display of the module's content: the task statement, above the handwriting sheet and above the workbook page (R23 and R34 canvas; R51), but not while the element has the attribute `statement-hidden`, by which `app` draws it as its card (section 3.1; R161), and media; there are no formulas in the statement of format v0. ### 3.4. Module widgets

- **What it is:** interactive components of a module on the canvas, the module author's code (concepts 8).
- **How they work** (R16):
  - in an iframe sandbox without `allow-same-origin`, on a separate registrable domain. Together with `allow-scripts` it would let a page of the same origin remove the sandbox (sources 5.1);
  - CSP does not let the widget's code go to the network: only the bundle itself is loaded;
  - the widget talks with the app only by the protocol from `spec`;
  - the bundle is signed and pinned by hash in the module package, and the package is pinned to the attempt;

  - to children, only widgets that passed review (О-9).
- **Stage 4.** In the first slice there are no widgets: none of its three modules needs them (R41). There is no binding of a slot to the widget's state in format v0: it will come with the widget protocol, as a minor version (R51). The template for authors is `widget-template` (section 3.13).
- **To decide when detailed**, in epic E5 of the plan (`run/EPICS.md`):
  - the widget protocol. What it has to decide beyond R16 is by the author's analysis (sources 8.4). The app's side of the protocol is the widget host of `canvas`, which `app` builds into itself (section 3.2); "`app`" below is it (В22 `canvas`):
    - the channel. The HTML Standard says to check the sender of a message by origin, and a widget without `allow-same-origin` has an opaque origin, serialized as "null". A comparison of `event.source` with the iframe's window does not tell documents apart: an iframe has one window, and at a navigation only the document behind it changes. So the analysis advises a `MessageChannel` port: `app` passes it to the widget once, at the first load of the iframe, and then listens only to it, and a document to which the widget navigated later never got this port (sources 5.2). How `app` notices such a navigation is decided by the protocol;
    - the version of the state in each message of the widget: `app` knows to which version the verdict and the tutor's words belong, and a mark on a part of the widget that has changed since then it does not draw, like a mark of a sheet whose strokes were erased (architecture 3.2 canvas);
    - the parts of the widget for marks: the tutor's layer lies over the widget (concepts 8), so the widget names its parts and their boxes, and a mark holds on to a part, as on a sheet it holds on to strokes;
    - the widget reports the learner's state and events, not a verdict. Whether it is correct is decided by `module-kit` (concepts 9.2), and by which state — the one the widget reported or the one repeated on the server by the seed and the events — is decided by Т-24. The widget's seed is its own, not the attempt's seed: the attempt's seed does not go to the device, and how the widget gets its own is decided by the widget protocol (R59);
    - the tests of conformance to the protocol are in `spec`, beside the protocol, like the verdict vectors, and in its releases by the same path as the format's files: as a release file of their own and in the Go module (R64). They are for both sides of the protocol: both the widget and the widget host of `canvas` pass them, each in its own CI (В22 `canvas`). Tests of one side hold only that side: a host that diverged from the test one would break widgets that passed the tests, and nobody would notice. The test host is in the development environment of `widget-template` (section 3.13); whether `canvas` itself will be it, epic E5 will decide together with `widget-template`, and the condition for the host does not change from that. A widget conforms to the protocol if it passes the tests, and the library for authors is a convenience, not a condition;
  - whether the state the widget reports can be trusted (Т-24);
  - the withdrawal of a version of a widget that turned out harmful. A withdrawn version of a module withdraws the bundles of its widgets too: the device no longer loads them, and the reason "dangerous bundle" will come as a minor version of the format together with the widget protocol (R63).

### 3.8. learner-model and engine

- **learner-model** — the estimate of knowing skills by evidence (concepts 11):
  - the starting point is the model of standalone: the Rasch model with a guessing floor, an Elo update, a cautious "mastered" (standalone: SPEC 2, R187);
  - the level is per module: each of the learner's modules has its own, on the scale of that module's bands, and the correction for the topic from standalone is the skill's: the estimate of knowing a skill is the module's level plus the skill's correction. Modules are linked only by an anchor skill, and the model has no subject (R03 learner-model);
  - "mastered" comes with a mastery band: the highest of the bands where the skill is taught at which the cautious estimate holds the threshold "mastered". The threshold is a constant of `learner-model`; a new target of the corridor of `engine` is a new constant of the model, and both changes pass `sim` in one run (R23);
  - forgetting is the skill's retention: without practice the estimate does not change, but the retention fades, and with it the probability of a correct answer; spaced practice grows the skill's stability. The module's level forgets too, at the next evidence: after a pause of the module of at least 14 days since the last practice of any of its skills, the weight of the module's answers, if above 20, falls to 20 before the step, so the answers after the break move the level more, and every skill of the module is less certain — "mastered" comes later and the review date nearer; a reading changes nothing (R04 learner-model). Time does not take "mastered" away but gives a review date — when the cautious probability with retention falls below the same threshold. The law and the constants are one for all modules (R04 learner-model). The retention and the probabilities with it at the current time and the review date the model computes at reading and does not write to the cache (R80; R08 api);
  - the weights of evidence (R06 learner-model): into the step goes the first verdict of each item, and help — a rung of the ladder before it, a technique on request, an already seen solution — only keeps "mastered" from being set; a leading question on request, which evidence from format 0.4 carries as its own field, is help, like a technique on request (R108; R21 learner-model), and the check kind `time` is a free answer, without guessing (R19 learner-model); each of N answers of one attempt weighs 1/(1 + (N − 1)/3); a key from the author, a solver or an adult weighs 1, a key or skills from AI weigh 0. An answer by a second way in a slot with a number — by the keyboard or by digit buttons — weighs as an answer in handwriting, and a submission whose verdict the learner saw the model always counts (О-25);
  - a probe, a repeat of a task, "mastered" and traps (R06 learner-model): the model does not recognize a probe and gives no rise for it — a probe weighs as any task, and returning a skill from a pause by its correct answer is a rule of `engine`. A repeat of a task, not a template, whose solution has already gone to the device is help: the answer goes into the estimate and the stability, but does not set "mastered". "Mastered" is set and removed by evidence: it is removed by two pieces of evidence in a row where the skill has fewer than half correct. The skill holds each trap the program found, with the number of pieces of evidence and the time of the last one, and which are frequent the reader chooses;
  - the transfer by the table of correspondence of old skill IDs to new ones after a major version of a module — `retired_skills`: the evidence of a retired skill goes to each skill that replaced it — each replacement gets the retired skill's share whole, and "mastered" the replacement derives anew from the transferred evidence (R49; R08 learner-model). `learner-model` transfers by the log and the graphs of the current versions of the log's modules, which `api` gives (R08 api). A module's skill that is in neither `skills` nor `retired_skills` of the current version goes to no skill, without an error; an anchor skill goes as it is if the dictionary of some format version in the window of `api` knows it, and otherwise to none; the skills of a trap by the same rules. The recomputation opens no packages of earlier versions (R80);
  - the evidence of attempts on a version withdrawn because of a wrong key, `wrong_key`, no longer goes into the model: `api` cuts it off before giving the log, and the model is recomputed by the evidence log (R63; R80);
  - an anchor skill of the shared taxonomy is by its ID, `core.<name>`, not by the full one. Whether the learner knows it `learner-model` decides by the skills that teach it, in the learner's modules (R50; R07 learner-model): "knows" is "mastered" on at least one such skill in any module whose graph came; "does not know" only by the engine's modules where the skills with a verdict that teach it are not mastered or still without evidence; otherwise "unknown" — nobody to teach it, or only skills without a verdict teach it. Each state the model gives with a reason and the skills that teach it, and forgetting does not remove knowing (concepts 4). It computes them at reading, and the inputs of reading are the cache, the graphs, the time, the grade and the IDs of the engine's modules — connected and suitable for the learner (R07, R08 learner-model);
  - the rules in place of calibration (R157): the starting point is a band below the difficulty band of the learner's grade — a band's width below on the module's scale, below the lowest band too —; the adult's correction, a fact of the evidence log that `api` appends, moves the module's level a band easier or harder in one step; three failures in a row of the module — a failure as `learner-model` defines it by its evidence — lower the level by a band. `sim` checks them in a short run (section 3.9);
  - the hardness of a task is by its band and its difficulty from 1 to 5 within the band; how far apart the bands are and where a learner outside the bands starts is R03 learner-model (R51). Guessing is the item's, by its slots: an item is correct only when each slot is correct, and to guess it is to guess each one. For a choice it is 1/k by the number of the slot's options, of the binding `choice` or of the check itself, for a free answer about zero; the numbers are `learner-model`'s (concepts 11; R03 learner-model);
  - the build (R09, R10 learner-model): the same bits on any build of one version, WebAssembly too, and the build for the device as it is; the code is only Go's standard library, and exp and log are its own, in the package `detmath`; CI checks this.
- **engine** — the choice of the next lesson or task (concepts 12): prerequisites, the success corridor (R23), repetition, reason codes. The detailing is decided (R107): the core of the rule — the rule of standalone on the module's skills, with the corridor, the prerequisites and the queue — is R03 engine; several modules in turn, anchor skills, a skill from the map and what the engine does not read are R04 engine; lessons are R05 engine; repetition is R06 engine; reason codes, the rule without randomness and the repeat of a choice are R07 engine; the types are R09 engine; the build for the device is R10 engine. For the time of the choice the model gives it the probability of a correct answer of an item with retention — for the corridor —, the estimate of a skill with uncertainty and retention, and for a mastered skill also "mastered" with the mastery band, the cautious probability with retention and the review date, with the mark "already" if the threshold does not hold even without forgetting. "Time to review" is a time of choice no earlier than the date, and whether to return a mastered skill into the rotation, when to give a skill whose date has come, how many repetitions a day and how they share the queue is the engine's rule (R23; R04 learner-model). A task template for the engine is one task, whichever instance comes up: a repeat of a template gives a new seed of the attempt and, most likely, other numbers (R60). A prerequisite from another module is an anchor skill, and an anchor skill "unknown" does not hold a lesson back (concepts 4). The order of lessons is set by the skill graph, and where it gives no order, the engine's rule chooses. In a lesson whose skills are not all with a verdict, the engine adds nothing and skips nothing (R58). A lesson goes for the learner as a lesson run (concepts 5), and at the engine's input are the profile's runs: the lesson, its skills, the end reason — an open one has none — and the time of the end; the places of finished segments the rule does not read (R09 engine). The skills of the lesson of an open run on an earlier package come translated by `retired_skills` of the current version by the same rule as evidence (R80). Inside a lesson the engine is not called: it does not reorder segments, and a call at each segment would decide nothing. `api` calls it when a run has ended and when the learner asks for something else, and the choice may also be the continuation of an open run (R13 api). An attempt at a task with a rubric gives no evidence (О-17), and from the learner model the engine cannot learn which essays have already been written. So `api` also gives it the attempts at tasks with a rubric closed by "Done" — the task's ID and the time of closing, without the marks of criteria: by them the engine keeps the author's order for skills with a rubric outside a lesson too, and reads no other close reasons (concepts 4; R09 engine). The time of practice from the model is not the time of issue: a task issued without evidence gives no practice. So `api` also gives the engine a summary of issues from the records of choices and attempts that it keeps anyway: for a skill, the time of the last issue, and the issue of a lesson is the issue of each of its skills, and, if the last closed attempt of the skill was a probe or a repetition, its result on the skill — as facts: how many items where the skill is primary got a first verdict, how many of them "correct" and whether the solution was shown; for a module, the number of choices, of a task and of a lesson separately; for a task, when its solution last went to the device (R82). By it the rule keeps the queue, the course of a probe and of repetition, the return of a skill from a pause by a correct answer of a probe or of a repetition and the pause before a task with a seen solution, and "failure" and "correct" by the facts it computes itself, not `api`; the types of the summary are its own and simple, like the types of the graph (R09 engine; R107). In the trial series of a module the engine does not work through an error and gives no probes (SPEC 3.2 standalone, step 1), and the series is a state of the model: `Read` gives for a module whether its trial series has ended and whether its last evidence was still in it — the second is needed so that the error of the series' last answer is not worked through (R104). The rule "open" of the skill map (R03 skill-map) the engine takes as an input: for a skill that the map opened and the learner chose, it gives a lesson or a task on it if the pool and the lessons hold at least one, and the reachability for "My subjects" may be its own (R104). The list of reason codes is a contract in `spec`, the enumeration `ReasonCode` ([contracts text](../contracts/README.md), section 15; R29; R100): a branch of the rule that is not in it `engine` asks for with a row «в реестр spec». The value `REASON_CODE_ROTATION`, "in rotation", means: a skill already issued earlier comes again in rotation, though it does not suit the queue — all the reachable ones are mastered and no dates have come, no skill is reachable, or a mastered skill whose recommended task went above the mastery band (R07 engine; R107). The generator of randomness and the derivation of seeds are from `spec`, shared with `module-kit` and `sim` (R27), and the engine's rule needs no randomness: it breaks each tie by the order of the graph or by ID, and it has no seed of the choice. Should a new version need it, it will have its own seed of the choice and its own names of places (R59; R07 engine). Repetition is a turn of the engine, once in three choices of a module, and the rule does not read the daily goal or the age category: the pool and the lessons by category `api` has already selected (R04, R06 engine; R107). The build (R10 engine): the same choice and the same code on any build of one version, WebAssembly too, only Go's standard library and `learner-model`, and CI checks this, as for `learner-model`.
- **Common:**
  - pure computations without input and output: the time comes from outside, and neither takes randomness — neither `learner-model` (R09 learner-model) nor `engine` (R07 engine) —, and no seed comes to them (R59; R107);
  - the types of the graph are their own and simple, not from `module-kit`; so the libraries can be built for the device too (Т-10). `learner-model` defines them, and `engine` takes them from it (R28). The graph is per module: the module's full ID, the bands in order with IDs and grades, the skills and `retired_skills`; for a skill, the full ID, the assessability, `teaches`, the bands where it is taught, the prerequisites and the tier from `skill_tiers`. The bands where a skill is taught are derived by a function of `learner-model` from the skills and the descriptions of the module's tasks, which `api` and `sim` give. The description of a task is one for evidence and for a candidate task from the engine's pool: the ID of the task or template, the band by place and ID, the difficulty, the primary and supporting skills, the provenance of the key and the tags, the items with skills and slots. For the engine's rules the graph and the description of a task cover everything, and the traps of items by `trap_values` are with its candidate; lessons, the pool, runs, the summary of issues and the choice are types of `engine` (R10 learner-model; R09 engine);
  - each change passes the simulator `sim` by a criterion written down before the candidate's first run (R163 standalone; R103).
- **Do not:** do not read module packages or the database: the graph and the evidence `api` passes to them. The pool of tasks, the lessons, the lesson runs and the closed attempts at tasks with a rubric are also set for the engine by `api`: with AI closed, they hold only tasks that are checked without AI, and lessons only of such tasks, and the engine does not know the reason (concepts 12).
- **Repositories and stage:** `learner-model` and `engine`, stage 1.
- **To decide when detailed:** everything is decided (R107; R03–R10, R19 and R21 learner-model; R03–R10 engine); the weights of evidence and knowing an anchor skill are in the items above.
  - Repetition (R06 engine; R04 learner-model): a task on a mastered skill whose date has come, on the module's turn of repetition — once in three of its choices —, and, when the new, the author's order and the queue have nothing to give, outside the turn too; the rule does not read the daily goal (R107). What each library decides next is in its `docs/architecture.md`.
  - An anchor skill in `engine` (R04 engine; concepts 4): "does not know" holds a skill back even when there is no evidence yet, except for a cycle of prerequisites between modules — a strongly connected component of the skill graph of the engine's modules, which the format does not see (R50) —, and an anchor that nothing teaches; a skill with its own evidence stays open when knowing goes away.
  - Evidence (R08 learner-model; R80; R82) holds the facts of an attempt, not the model's conclusions — everything R82 names and everything the model reads —, and no segment of a lesson: a segment does not change the weights. Its fields:
    - for an attempt: the task, the task's band and the start band — by place and ID —, the difficulty, the skills, the provenance of the key and the tags, the outcome (concepts 11), the time of the last action in whole seconds of UTC, a technique at a step and on request, from format 0.4 a leading question on request as its own field (R21 learner-model), the number of "explain differently", whether the solution went to the device;

The form only grows: an earlier version reads a new one, skipping what it does not know, so a rollback of `api` — only forward, with the earlier code (R106) — does not break the log. ### 3.9. sim — the learner simulator

- **Does:**
  - runs `learner-model` and `engine` on thousands of virtual learners of different populations (concepts 15);
  - holds the criteria and the tolerance bands;
  - serves as the CI gate of the libraries and of `modules` (repositories 4; R103).
- **Data:** module packages — data pinned by version. It reads their server part, `server.json`, by the types of the canonical view from `spec` — `formatv0.CanonicalView` of the Go module `spec` (R72) —, without `module-kit` (R62), in the same window of module format versions as `module-kit` (R44). The seeds of virtual learners it derives with the generator from `spec`, not by a scheme of its own (R27). The function `seeded` of the simulator of standalone is a particular case of the derivation of `spec`: the place of the main seed with the names "experiment, unit, assignment", so the simulator's numbers are kept. The normal and the exponential distributions are not part of the format, and `sim` is responsible for their portability (R59). The gate's bands lie in `sim`, in the gate file: it names the commits of `learner-model` and `engine`, the release of `modules` — by the tag and the digest of the index — and the packages by digests. Synthetic packages `sim` has only for its code and tests, not for judging candidates (R103). There are no data of live learners.
- **Does not:** does not change the algorithms, only measures them.
- **Limit:** an anchor skill that no module of the learner teaches the simulator's truth counts as known, and knowledge of an anchor outside the platform enters it only as a shift of the skills that teach it (the population `A-unpractised`, the measure `M9` of architecture 3.5 sim). ## 4. Flows

### 4.1. Checking a handwritten answer

`tutor` is a library in the process of `api`. On the diagram it is drawn separately, so that the boundary of R03 is visible. Reading and the analysis are two calls (R67). Reading handwriting is also two readers of one provider (R68): on the diagram they are one arrow "request". In the reading mode `single` there is one reader, and nothing to join.

```mermaid
sequenceDiagram
    participant A as app
    participant P as api
    participant T as tutor
    participant M as AI provider
    A->>P: submission — a crop of the work
    P->>T: reading handwriting — the work, the open view, the age category, the AI route
    T->>T: admission — the route is allowed, the model is among the admitted
    T->>M: request without identifiers
    M-->>T: the model's answer
    T-->>P: the observations of two readers, or of one in single
    Note over P: module-kit — one observation from two, or the one in single, and the verdict by the key and the provenance
    P-->>A: "Not yet. Read: 6"
    A->>P: with the tutor's panel open, or when it opens — the tutor's words: the work once more and the number of the incorrect answer
    Note over P: hint ladder — which rung
    P->>T: analysis of the course of solution and a hint — the work, the key and the solution of the task, the trap, the rung, the task's past questions, the presentation style, the explanation language, the age category, the AI route
    T->>T: admission
    T->>M: request without identifiers
    M-->>T: the model's answer
    T-->>P: the tutor's question
    Note over P: leak check and form check, otherwise the fallback text
    P-->>A: the question and the marks on the tutor's layer
    Note over A,P: at the end of the attempt — evidence into learner-model. Outside a lesson and at the end of a lesson run engine chooses the next lesson or task and writes the reason code, and the choice — without the code — comes in the same answer, and in a lesson the next segment goes
```

- Reading and the analysis are different AI capabilities: the analysis sees the key, reading does not (section 3.6; R67). The observations of two readers `module-kit` joins into one, and a slot that they read differently is ambiguous in it: the verdict is "unreadable" (R68; R86). In the reading mode `single` the one reader's observation gets the verdict as it is (R68).
- The presentation style on the diagram and below is only what of it changes the words: voicing does not go into the AI call, nor does the solving mode (privacy 4; О-23).
- The work is read only on the learner's action — on "Check"; "Step done" in format v0 does not read the work, and on a pause AI is not called (R69). `module-kit` gives the verdict by the observation as a whole, not by lines while they come (R54).
- Evidence is the result of an attempt, not of a separate submission (concepts 11).
- A failure of AI or an exhausted quota is a neutral phrase, not "not yet" (R04).
- The server does not store the picture, so for the analysis the application sends the work once more (R09). It asks for the tutor's words only while the tutor's panel is open, or once when it opens; with the panel closed, "Check" ends at the verdict (R148).
- **A hint on request** sends no work and does not call reading (R69). Hint with the tutor's panel closed opens it, and the opening asks the rung's words of the last wrong answer, when they were not asked, as on the diagram, with the work (R148). Before the first incorrect answer it gives "givens and unknown" and the task's technique, after it the words of the current rung once more, without AI. "Explain differently" is the same call of a hint as on the diagram, but without the work: the key and the solution of the task, the trap of the rung's slot, the rung, the task's past questions, the presentation style, the explanation language, the age category and the AI route — once per rung. The past questions of the same task each call of the attempt's words gets, so as not to repeat them (R82; privacy 4).
- On a workbook the work is the crops of the filled boxes with their places, without the item's text, and the place in the observation is the answer slot (R53).
- **A task with a rubric** is also two calls, but other ones: reading an essay and the assessment by the rubric (R75). An item with a rubric has no verdict: instead of `module-kit` and the hint ladder, an assessment and feedback.
  1. `app` sends the work — a crop of the handwriting sheet.
  2. `api` calls reading the essay — with the same as reading handwriting gets: the work, the open view, the age category and the AI route. The sheet is read by one reader (R68), without the rubric, and `api` gets the observation — the text, as it is written.
  3. `api` calls the assessment by the rubric — with the read text, the task statement as the topic, the rubric's criteria in order, the presentation style, the explanation language, the age category and the AI route. There is no picture, key or solution of the task in it. The model gives for each criterion a justification and whether it is met, and one feedback on the whole essay.
  4. The feedback passes the leak check and the rule of feedback (R70) and goes to the device.

  An essay that is unreadable does not reach the assessment, and the learner sees a request to rewrite the sheet, as at "unreadable" (concepts 9.1). An item with a rubric has no verdict: the submission ends with "unreadable", and only its time is recorded (R87; R14 and R15 api). The attempt is open for rewriting, and the learner's "Done" ends it.

### 4.2. An answer by typing, choice, edit or widget state

AI is not needed here: `app` sends the value, and `module-kit` compares it with the key or the predicate (concepts 9.2). The mode without AI (О-5) works the same way, and so does the platform with no AI provider at all — for example, self-hosting without agreements with providers.

### 4.3. Own key

- A key exists only for the owner profile of the category `adult` (R04 api; О-4). On the device it lies only if the key's owner decided so on this device, and otherwise in the tab's memory while their profile is open; there is no encryption in the browser, and `app` says so plainly (R84; R08 app).
- The key and its provider come with each request of the owner profile that calls AI: with the work for reading, with the rung's words, with the correct answer words and with "explain differently", which sends no work (section 4.1). A provider without a key `app` names at the start of the attempt, and with each request whose answer or refusal may give an engine choice, so that the choice goes by the same route (R84; R99). In `api` and `tutor` the key lives only in the request's memory — not in the database and not in the logs (privacy 5.2); with a profile of another category `api` does not accept it.
- On connection `api` checks the key through `tutor` with a request without the learner's content, `CheckOwnKey`: the key is accepted, wrong, the key has no rights, or the provider is closed for the profile; the providers open to an own key `ListOwnKeyProviders` names, by what `tutor` admits for at least one kind of call of `api` (R98; R72 api). A provider's refusal by a limit is "limit reached" with a cause (R55 tutor), a refusal of the key is an outcome of its own, and neither moves the call to platform AI without an action of the key's owner (privacy 5.1, 5.2).
- The admission function lets it through only if the provider's terms allow it for the learner's age category (privacy 5.3) — by the cell of the admission table: for an own key only the category `adult` is open, without deployment facts (R96). The recommendation of О-4 is an own key only for 18+.
- The model is only from the admitted ones: an own key does not open a model without eval (R07).

### 4.4. From the author to the learner

Module → CI of `modules` (`module-kit`, `sim`; from stage 2 eval) → package → `api` pins it to the attempt → `app` gets the open view. In detail — repositories 4.

### 4.5. Export and deletion

- **The export is assembled by `app`.**
  - Strokes, artifacts and tasks from paper lie on the device, and `api` gives its own part, which holds the open attempts of tasks from paper without their key (R135).
  - Works from other devices are exported from them, but for the stored works: while the storage of works is on, `api` keeps the last work each device put, its part of the export names them, and `app` writes each into the export beside that part, by `GetWork`, one at a time, so that no answer is larger than a work (R113; R151).
  - The export format is open, in `spec`: [the part `export/`](../export/README.md) — a ZIP of JSON files, where the manifest, the device's files, the stored works and the pages from paper are written by `app`, and `api.zip` is the part of `api`, byte for byte; the evidence log, the state and the observation are the JSON of their protobuf messages with their own `.proto` (R09, R135).
  - There is no own key in the export: the export is learners' data, and the key is a secret of the key's owner (R84; privacy 5.2).
- **Deletion is confirmed by a fresh sign-in.**
  - `api` deletes the data from the database and deletes the account at the sign-in service. Without a fresh sign-in the deletion gets the refusal "fresh sign-in needed", `CAUSE_FRESH_SIGN_IN_NEEDED` (R98; [contracts text](../contracts/README.md), section 15).
  - The connection "Sign in with Google" in the owner's Google account is not removed by the deletion at the sign-in service. After the answer "deleted" `app` removes it: it revokes the Google access token of the fresh sign-in at `https://oauth2.googleapis.com/revoke`, and `api` does not get this token (R144; sources 4.6). While `app` has no deletion screen, the connection stays, and the owner removes it themselves on the page of Google's connected apps.
  - A deleted profile other devices erase by the account's list of profiles, which `app` reads at start.
  - Other devices erase their data at the next call to `api` while their ID token lives — about an hour after the deletion: it answers that the account is gone, `CAUSE_ACCOUNT_GONE`. The revocation of tokens does not put out earlier ID tokens — "existing ID tokens may remain active until their natural expiration (one hour)" (the Firebase Admin SDK for Go v4.22.0, `auth/user_mgt.go`, read by `api` 2026-11-02; sources 11.1 api). Later the sign-in service on the device signs out by itself, and the data are erased at the next sign-in on it: a new sign-in gives a new UID without an account of `api`, and "no access", when the device's register holds an account, `app` reads as the sign-in of another account. A device that is not opened keeps them until the browser or an adult erases them (R20, R21 api; architecture 3.10 api).
- **Honest retention periods** name the backups of the database, the sign-in service, the logs of the platform and of AI providers, and other devices (privacy 1).
- **What remains of consent** after deletion is R117.

### 4.6. A change of AI model and a change of algorithm

- A new model for an AI capability is admitted when it passes the capability eval set and the eval sets of all the published modules with this capability. False alarms are counted by the verdict, through `module-kit` (repositories 4): by the runner's report — a message of the eval protocol without the content of works —, and for admission only a report with the verdicts of `module-kit` will do ([contracts text](../contracts/README.md), section 14; R95; R07). The assessment by a rubric has no verdict, and it is measured by false alarms on met criteria, and the second measure is agreement with people and kappa per criterion (R71). A model on the device is admitted the same way (R66). The eval sets of modules lie in the git of `modules`, outside the package and the release files (R62; R03 modules), and meet the runner in CI of `modules`: a model is admitted when the pull request of `modules` is merged that moves to the tag of `tutor` with it in the list of admitted models and runs the eval sets of all modules. The order is repositories 4 (R04 modules).
- eval at a provider beyond OpenAI and Anthropic goes by its terms: Together, Cerebras and Fireworks forbid benchmarking, and SambaNova forbids publishing its results without its consent (R65; privacy 5.3).
- A change of `learner-model` or `engine` passes `sim` by a criterion written down in advance (repositories 4).
- A change of the rule of `engine` does not rewrite the reason codes saved with the choices and does not change the meaning of a code. A new branch of the rule comes with a new code, and the code of a branch that the engine removed stays in the list and is no longer given ([contracts text](../contracts/README.md), section 15; R100).

## 6. Interface: packages and the iframe sandbox

- **Micro-frontends.** The author wanted «микрофронтенды в своих репозиториях», "micro-frontends in their own repositories". In NovaTrail these are the UI packages — `canvas` and `skill-map`: parts of the interface in their own repositories, with their own releases.
  - `app` builds them by exact version into one application (R16).
  - During development `app` connects working copies of the packages, and only exact versions go into a release.
- **Why without loading at run time** (R16):
  - With exact versions `app` would pin the version of each part anyway, so there would be no independent deployment.
  - The cost would remain: diverging versions, duplicates of the framework, more complex CSP, cache and offline.
- **How the packages join the application** — as web components, with data types from the releases of `spec` (R36): the packages have several consumers, and the framework of each is decided by its repository. The packages come out in npm, in the scope `@altnovatrail` (R37).
- **Foreign code** is only the widgets of modules, and only in the iframe sandbox (section 3.4).
  - Shadow DOM is not a means of protection: it isolates styles and the DOM tree, but not code (sources 5.3).
  - So a module is not embedded into the page as a web component through `<script src>`, as Gemini proposed (R16).
- **The second consumer of a package** — for example, the site or a card of the MCP channel — gets a second build of the same package. So the chat widget of standalone is built: one HTML page in an iframe of the host.
- **Icons** — one set of the Iconify catalog, Material Symbols, for all UI packages (R78).

## 7. What the architecture does not have

- Its own clusters, queues and event bus (R11).
- A service per area: without queues that is a distributed monolith of synchronous chains (R15).
- Pictures and sound that go for checking, and own keys, on the server (R09; R84).
- A real-time channel in the first slice (Т-25).
- Mailings and notifications: an adult's contacts are needed only for the sign-in and the subscription (privacy 1).
- An operator's console as a separate application: in the first slice it is the commands and jobs of `api`.
