## 1. Principles

- **The boundary of R03 runs along the code.**
  - Everything that calls a model is in `tutor`. A model that would read the work on the device is its code too: its weights, eval and admission are with `tutor`, and the verdict is with `module-kit` (R66). In the first slice there is no such reading.
  - The verdict is given by `module-kit`, the learner model is computed by `learner-model`, the next lesson or task is chosen by `engine`. None of these libraries calls a model.
  - CI of `api` checks the full list of dependencies: the SDKs of AI providers get into the build only through `tutor` (R15).
- **Of the platform's parts, only `api` stores learners' data on the server.**
  - `tutor` stores nothing. The types of its requests have no fields for the learner's and account's identifiers, so AI sees the work but does not know whose it is (R15; privacy 1, 5.1).
  - Outside the platform, part of the data is held by the sign-in service, the AI providers and, from stage 3, payment (section 5).
- **A separate process only where it is needed.** In the first slice there is one service, `api`; `tutor`, `module-kit`, `learner-model` and `engine` are libraries in its process. `tutor` will become a service when it gets a second consumer (R15).
- **The key of an unsolved task is only on the server.** The app gets the task's open view (R05). The open view is built by `module-kit` by the marks `x-open` in the format's schemas: a field without the mark is closed, so a new field of the format is closed until it is explicitly opened (R45).
- **Reproducibility** (R03):
  - an attempt stores the digest of its module package, the module format version, the version of `module-kit` and the seed. A package digest is the digest of its inventory, and it depends only on the module's files and the format version of its manifest ([format text](../format/README.md), section 25; R62). A module is checked and executed by the format version that its manifest names, and a new format version does not change its verdict until the author moves the module to it (R44);
  - an engine choice stores the versions of `engine` and `learner-model`, the package digests, the seed and the reason code, and also the release of `modules`, the number of the last evidence of the log by which it was made, the time of the choice, the grade by which the model computed the starting point of modules without evidence, and whether the pool was limited to tasks without AI: without them a replay by the log does not know which prefix of the log to take, which withdrawal marks were in effect then, for what time the model computed retention and the review date, by which grade — the starting point of modules without evidence, which lesson runs and closed attempts of tasks with a rubric the engine saw — their reason and end time, once written, do not change, — and from which pool it chose (R80; В4, В14, В15 and В18 `api`; R04 and R08 learner-model; concepts 12). The summary of issues the replay assembles anew from the records of choices and attempts before this choice: once written, they do not change (R104). The choice also stores the skill chosen on the skill map — it holds until the learner asks for something else, and the record carries it into the next one, — the age category of the profile at the time of the choice, by which `api` selected the pool and the lessons, and a mark of which of the digests are the engine's modules, connected and suitable for the learner: the category changes at the yearly refinement and at a change of country, the connections at any time, and the digests also name the modules of the log, which only `learner-model` gets. The seed is empty while the engine takes no randomness, and it takes none: that this is so is seen from the version of `engine` in the same record. The last attempt and its outcome the replay derives from the records of choices and attempts before the time of the choice (R107);
  - a verdict is repeated by the stored observation, a choice by the evidence log (R80); both without AI;
  - the generator of randomness and the derivation of seeds are set by `spec`, with test vectors: PCG, as in Go's `math/rand/v2`, and places of randomness, as at standalone's simulator ([format text](../format/README.md), section 22; R59; Т-18 closed). An instance of a task template is repeated by the attempt's package and seed: it is chosen by one number of the place `template`, the task's ID, `instance` ([format text](../format/README.md), section 23; R60).
- **Our own parts of the interface are assembled at build time, others' code runs only in an iframe sandbox** (R16, section 6).
- **No clusters, queues or event bus of our own** (R11). The parts talk by synchronous requests by the contracts from `spec`: `app` with `api` by Connect, with unary calls, and the code of the contracts comes from the releases of `spec` (R83). Background work is Cloud Run jobs on a schedule, as in canvas-api.
- **Logs without direct identifiers, IP addresses and content** (R09; privacy 4).
  - Cloud Run itself writes request logs with the standard field `httpRequest`, and it has `remoteIp`, the client's IP address. canvas-api recorded the same about the logs of Cloud Run and Firebase Hosting (privacy 4 canvas-api).
  - COPPA counts an IP address among persistent identifiers, that is, among personal information (16 CFR 312.2).
  - So the request logs are excluded in Cloud Logging by the filter of each sink: Google accepts the record and discards it before storage (R07 infra), — and the logs' region is `us-east4`, as for the whole platform (R109).
  - The hosting of `app`, Firebase Hosting, and the sign-in service, Firebase Auth, store IP addresses in their logs themselves, for several months and several weeks; `infra` does not turn on the export of the Hosting logs to Cloud Logging (R06 infra; section 3.12; П-9).

  Sources: sources 3.1, 4.1, 4.2 and 4.4.

## 3. Components

Each component has a card: what it does and does not do, its data and links, its repository and stage (product 11). The items "To decide when detailed" are what the work in its repository begins with (repositories 2.2). A question that concerns several repositories is in the registers of `spec`, and the card refers to it.

The task that set up a repository (RUN.md, T04–T14) could name items of detailing beyond the card, and could skip an item of the card. The card is corrected for this by the repository's own «Итог детализации», by a row of its table 3 «в реестр spec», when the decision has already been made, and not in advance.

### 3.1. app — the learner's and adult's app

- **Does:**
  - the shell: sign-in through the sign-in service, the choice of the learner on a shared device, the start of work — age, country, consent; the learner's grade — when the module manifest names grades (R49);
  - three entries into the app: "My subjects", "Skill map" and, later, "A task from my paper" (product 4);
  - the lesson player and the task screen: the canvas, answer slots, the choice of an option, the tutor's panel with the solving steps and hints, the conversation line. The conversation line of the first slice is buttons of requests, a hint and "explain differently" (R82), without the learner's own text: own text comes later, as a capability of `tutor` of its own (product 10; В40 `app`). The text of an item of a handwriting sheet `app` shows together with the options of `choice`, beside the sheet, not on it; the item line of a workbook is shown by the canvas (R32 and R34 canvas). The task's skills, band and difficulty are not in its open view (R51), nor are its techniques, traps, simpler case, leak phrase and solution (R57);
  - a lesson by its open view: the segments in the author's order, explanations — and the numbers of a numbered list in them are drawn by `app` (R111), — worked examples, whose demo the learner opens one part at a time and may hide, and the lesson's tasks, which `api` gives. The lesson's skills and age categories are not in the open view (R58);
  - progress and the skill map;
  - the section for adults behind a PIN: profiles, tariff, own key, settings, export and deletion;
  - the disclosure that the learner talks with AI, not with a person (privacy 5.3; П-15);
  - before sending a work that goes to AI whole, a reminder not to write names, and to a learner under 18, at work with a rubric and in the section "Help", open to them from any screen, where to turn if something is wrong: to an adult and to the helplines of their country, by name and number, without links, by a list with a date of checking (R127);
  - voicing of the tutor's words and the module's open texts by the device's speech synthesis, in a voice that it names itself, by the rule of Т-13. Whether voicing is on and its speed are in the presentation style of the learner's profile, and the voice by language and the adult's permission on Android and Linux are on the device (R07 app; О-23);
  - the interface in `en` and `ru`: the learner's interface language is a field of their profile, which the adult sets, and the screens before the choice of the learner and the section for adults are in the device's language (R92). Translations follow the shared rules of the UI packages, and the words that more than one package shows follow the table of words in section 6 (R91);
  - legal pages and consents: the texts from `api`, by the method `LegalService.GetLegalTexts`, as its own pages, without external links, and for a consent, its gist in the screen's language beside the English text (R115, R116, R130);
  - accessibility by the standard of the UI packages, WCAG 2.2 AA with 2.5.5 and 2.3.3 (R90). What `app` and the packages do not meet yet, `app` names on the page "Accessibility", among the legal pages (section 3.13; R11 app).
- **Does not:**
  - does not get the key, the solution and the traps of an unsolved task, and its technique only from `api`, at the step that gives it, or at the learner's request, and the task's leading question also from `api`, on request (R57; R108);
  - does not give a verdict;
  - does not call AI providers;
  - does not send strokes and the whole photo to the server, but for a stored work, while the storage of the profile's works is on (R113).
- **Data and links:**
  - on the device: strokes with time and pressure, artifacts, and the own key only for an owner profile of the category `adult` and only by its choice on this device, otherwise in the tab's memory. `app` sends the key with each request of this profile that calls AI (R84; R08 app). Also the context of each submission: on a handwriting sheet, where the crop lies on the sheet, its integers, the group boxes of the stroke groups, the table "group label → stroke IDs" and the submission's digest, and on a workbook, the table "box → stroke IDs" and the digest. The canvas gives it together with the work, and `app` holds it as it is: by the digest the canvas accepts the context back (R36);
  - talks with the sign-in service and with `api` by the contract `novatrail.api.v1`: the check of an attempt is `AttemptService` (R97), the account and profiles are `AccountService`, and by the list of profiles and the refusal "account gone" `app` erases what lies on the device (R98); the path from a module to a task is `PackageService`, `ModuleService`, `LearningService` and `ProgressService`: open views by package digest, the catalog and the connected modules, the engine choice, the start and the open attempt, lessons by runs, the skill map and the adult's progress (R99); the stored works are `WorkService`: `app` puts a work at each submission and when the attempt closes, while the storage is on, and takes it back on another device and into the export (R113, the 2026-11-13 amendment);
  - reads the deployment configuration at each start from `/deployment.json` at the root of its origin, beside the signed build but not in it, and checks it strictly, before the first request to the network. The file's format is the part of `spec` `deployment/` with its own version, and version 1 is the format of R09 app: `format`, `api` and `signIn` ([the part's text](../deployment/README.md); R85 with the amendments of 2026-11-08 and 2026-11-09).   - gets the task's open view from `api` and reads it by the types from the releases of `spec` (R36), of the module format versions in the window. The TypeScript types are the npm package `@altnovatrail/spec`, `@altnovatrail/spec/formatv0/open`, by an exact version in `devDependencies`, and `api` reads the same view by the Go types `types/formatv0/open` (R72, R73). ### 3.2. canvas — canvases

- **Does:**
  - canvas kinds (concepts 8); in the first slice, the handwriting sheet and the workbook (product 10; R41). A workbook is a page of 1000 × 1400 units, like a sheet, without a grid: the item lines with boxes are put on the template layer by its layout, by the task and its own table of widths, not by the device's font (R34–R36 canvas);
  - layers: the template, the widget, the demo, the learner's work, the tutor's layer. On the demo layer is the demo of a lesson's worked example: its parts open one at a time and hide all at once, and a picture in a sheet area stands at the size of the area. From format 0.4 an example stands on a workbook too: the example's lines by the page layout, and a part of the demo fills a box with its value (R111). On the sheet and on the workbook of an example the learner does not write (R58). The parts are opened one at a time and the whole demo is hidden by the learner with the element's buttons, "Next" and "Demo" (R42 canvas);
  - tools; the eraser removes a stroke whole;
  - the capture of strokes with time and pressure;
  - the display of the module's content: the task statement, above the handwriting sheet and above the workbook page (R23 and R34 canvas; R51), and media; there are no formulas in the statement of format v0. The text of a sheet's item and the options of `choice` are shown by `app`, and the item line of a workbook by the canvas (R32 and R34 canvas);
  - the crop of the work for the check: on a handwriting sheet, only the visible strokes of the sheet of 1000 × 1400 logical units (R06 canvas), and on a workbook, a crop of each filled box by its strokes; the draft — writing outside the boxes — does not go (R34, R37 and R38 canvas; R53);
  - the tutor's marks, tied to the learner's strokes (R43 canvas-api). On a workbook a mark stands on an answer slot by place and holds on to the strokes of its box (R39 canvas);
  - the samples page, a separate build of `canvas` for eval samples (R25):
    - a sample is made by the same canvas as the learners have, and is saved as a file on the device. The file's format is the eval protocol: the message `Sample` of the package `novatrail.eval.v1`, one JSON per sample, without pressure, and for an eval-set sample, with the license in the file ([contracts text](../contracts/README.md), section 11; R93). It is written by `canvas` with the contract's code from `@altnovatrail/contracts`, and checked by a recipe of `spec` through the submodule, `just -f spec/justfile sample-check` ([contracts text](../contracts/README.md), section 11; RUN.md, T72). The groups, crops and box table of a sample follow the rules that are the same for the device and the runner, and the crops are drawn by the strokes that the file holds, for the final geometry too ([contracts text](../contracts/README.md), section 12; R94);
    - an adult's sample has two purposes, and it is chosen on the page itself: a measurement sample goes to the measurement organizer, outside git, and an eval-set sample to the eval-set organizer, and it is they who add it to `modules`, by a pull request from a branch of the repository (R04 modules; the 2026-11-02 amendment to R25). The volunteers' consent is П-16;
    - the page takes no consent: it shows the purpose's notice and writes the version of the text set into the file, and the written consent is a signed form that the organizer accepts outside the page. The sets `measure` and `eval-set` are in force, and the page opens the volunteers' measurement and the eval set, and the child sample session is closed until the set `child-sample` is in force (R139, R141; RUN.md, T117; R11 and R72 canvas);
    - a child sample is with a separate consent (П-10) and without a pull request: it does not get into the repositories, and the file goes to the operator's closed bucket, to the measurement organizer, for 2 years from the session (R125; П-10 and П-12 closed);
    - nothing goes to the platform's server;
    - for the first measurement on the volunteers' samples, without hosting: the build is downloaded from the release of `canvas` and opened on a computer and on Android; on an iPad, only from hosting: the page will move to Firebase Hosting as a separate site with its own origin when the author so decides: the analysis is done, Google is a processor for Hosting, and it keeps IP addresses "a few months" (the second 2026-11-08 amendment to R25; R128), and until then the page says that it cannot be opened here (the 2026-11-08 amendment to R25); and the tasks and media files are put into it at build time from the release of `modules`. Until the build has moved to `modules` — by a task of `canvas` of its own, Д4 of its RUN.md, — the measurement tasks come from the release of `tutor`: the file of open views, since its v0.1.1, `canvas` keeps as a copy in the tree, which CI checks by the recipe `release-verify` on every pull request, and the build of the page and the synthetic data read it without the network (the 2026-10-21 amendment to R25; the amendment of T21 to R08 canvas; the `canvas` row В73);
  - later, the widget host: the app's side of the widget protocol. It passes the tests of conformance to the protocol, as the widget does (section 3.4).
- **Does not:** does not know accounts, `api` or subjects. The tutor's layer does not change the learner's work (R05).
- **Data and links:**
  - it has no data of its own: the submission context is held by `app` (R36);
  - enters its consumer as a web component, one element `<novatrail-canvas>` for all canvas kinds. The element gives the writing history by the property `history` and the event `historychange` and takes it by the same property, and the work for the check by the method `exportWork()`: on a sheet, the PNG of the crop and the submission context, on a workbook, the crops of the filled boxes with their places and the workbook's context, and which boxes are filled is told by the property `filled`. The module manifest of the task it takes by the property `manifest`, and the files of the pictures of the task and the example by the function `media`, which for a link to a picture gives a promise of a `Blob`: the canvas does not go to the network. The commands `undo()` and `clear()` are called by its own buttons, and they are not part of the agreement (the 2026-11-02 amendment to R36). The tutor's marks it takes by the property `marks`, together with the context of their submission and after `task` and `history` (R26 canvas). The learner's change of tool it announces by the event `toolchange`, and the language of its buttons' captions it takes from its attribute `lang` (R36). Instead of a task it takes by the property `workedExample` a worked example of a lesson, and how far the learner has gone through its demo it gives by the property `demoState` and the event `demochange`. `app` keeps this state and returns it by the same property, and gives each segment of a lesson a new element. On a sheet `filled` says whether a slot `anywhere` or `sheet` has a stroke (the second 2026-11-01 amendment to R36). The types of this agreement are `@altnovatrail/spec/canvas` from line 0.5: `CanvasElement` and the types of its events, of the writing history, the work, the submission context and the state of the demo. `spec` writes them by hand (R74). The types of the marks are there too: `Marks`, `Mark` and `Anchor`, and the kind and place of a mark are checked against the message `Mark` of the contract `novatrail.api.v1` (R97; the second 2026-11-03 amendment to R74). An empty box of a workbook the mark circles by itself (R97), and `canvas` takes this by its move to the tag (RUN.md, Д50). The element in `HTMLElementTagNameMap` and its events in `GlobalEventHandlersEventMap` are put by the package `canvas`. ### 3.4. Module widgets

- **To decide when detailed**, in epic E5 of RUN.md:
  - the widget protocol. What it has to decide beyond R16 is by the author's analysis of 2026-10-21 (sources 8.4). The app's side of the protocol is the widget host of `canvas`, which `app` builds into itself (section 3.2); "`app`" below is it (В22 `canvas`):
    - the channel. The HTML Standard says to check the sender of a message by origin, and a widget without `allow-same-origin` has an opaque origin, serialized as "null". A comparison of `event.source` with the iframe's window does not tell documents apart: an iframe has one window, and at a navigation only the document behind it changes. So the analysis advises a `MessageChannel` port: `app` passes it to the widget once, at the first load of the iframe, and then listens only to it, and a document to which the widget navigated later never got this port (sources 5.2). How `app` notices such a navigation is decided by the protocol;
    - the version of the state in each message of the widget: `app` knows to which version the verdict and the tutor's words belong, and a mark on a part of the widget that has changed since then it does not draw, like a mark of a sheet whose strokes were erased (architecture 3.2 canvas);

    - the widget reports the learner's state and events, not a verdict. Whether it is correct is decided by `module-kit` (concepts 9.2), and by which state — the one the widget reported or the one repeated on the server by the seed and the events — is decided by Т-24. The widget's seed is its own, not the attempt's seed: the attempt's seed does not go to the device, and how the widget gets its own is decided by the widget protocol (R59);
    - the tests of conformance to the protocol are in `spec`, beside the protocol, like the verdict vectors, and in its releases by the same path as the format's files: as a release file of their own and in the Go module (R64). They are for both sides of the protocol: both the widget and the widget host of `canvas` pass them, each in its own CI (В22 `canvas`). Tests of one side hold only that side: a host that diverged from the test one would break widgets that passed the tests, and nobody would notice. The threshold is a constant of `learner-model`; a new target of the corridor of `engine` is a new constant of the model, and both changes pass `sim` in one run (the 2026-11-02 amendment to R23);
  - forgetting is the skill's retention: without practice the estimate does not change, but the retention fades, and with it the probability of a correct answer; spaced practice grows the skill's stability. Time does not take "mastered" away but gives a review date — when the cautious probability with retention falls below the same threshold. The law and the constants are one for all modules (R04 learner-model). The retention and the probabilities with it at the current time and the review date the model computes at reading and does not write to the cache (R80; R08 api);
  - the weights of evidence — decided by R06 learner-model: into the step goes the first verdict of each item, and help — a rung of the ladder before it, a technique on request, an already seen solution — only keeps "mastered" from being set; a leading question on request, which evidence from format 0.4 carries as its own field, is help, like a technique on request (R108; R21 learner-model), and the check kind `time` is a free answer, without guessing (R19 learner-model); each of N answers of one attempt weighs 1/(1 + (N − 1)/3); a key from the author, a solver or an adult weighs 1, a key or skills from AI weigh 0. An answer by a second way in a slot with a number — by the keyboard or by digit buttons — weighs as an answer in handwriting, and a submission whose verdict the learner saw the model always counts (О-25; В23 `learner-model`);
  - a probe, a repeat of a task, "mastered" and traps (R06 learner-model): the model does not recognize a probe and gives no rise for it — a probe weighs as any task, and returning a skill from a pause by its correct answer is a rule of `engine`. A repeat of a task, not a template, whose solution has already gone to the device is help: the answer goes into the estimate and the stability, but does not set "mastered". "Mastered" is set and removed by evidence: it is removed by two pieces of evidence in a row where the skill has fewer than half correct. The skill holds each trap the program found, with the number of pieces of evidence and the time of the last one, and which are frequent the reader chooses;

A module's skill that is in neither `skills` nor `retired_skills` of the current version goes to no skill, without an error; an anchor skill goes as it is if the dictionary of some format version in the window of `api` knows it, and otherwise to none; the skills of a trap by the same rules. The recomputation opens no packages of earlier versions (the 2026-11-02 amendment to R80);

It computes them at reading, and the inputs of reading are the cache, the graphs, the time, the grade and the IDs of the engine's modules — connected and suitable for the learner (R07, R08 learner-model);

Guessing is the item's, by its slots: an item is correct only when each slot is correct, and to guess it is to guess each one. For a choice it is 1/k by the number of the slot's options, of the binding `choice` or of the check itself, for a free answer about zero; the numbers are `learner-model`'s (concepts 11; R03 learner-model);

The generator of randomness and the derivation of seeds are from `spec`, shared with `module-kit` and `sim` (R27), and the engine's rule needs no randomness: it breaks each tie by the order of the graph or by ID, and it has no seed of the choice. Repetition is a turn of the engine, once in three choices of a module, and the rule does not read the daily goal or the age category: the pool and the lessons by category `api` has already selected (R04, R06 engine; R107). The build — decided by R10 engine: the same choice and the same code on any build of one version, WebAssembly too, only Go's standard library and `learner-model`, and CI checks this from the first code, as for `learner-model`.

### 3.9. sim — the learner simulator

- **Does:**
  - runs `learner-model` and `engine` on thousands of virtual learners of different populations (concepts 15);
  - holds the criteria and the tolerance bands;
  - serves as the CI gate of the libraries and of `modules` (repositories 4; R103).
- **Data:** module packages — data pinned by version. It reads their server part, `server.json`, by the types of the canonical view from `spec` — `formatv0.CanonicalView` of the Go module `spec` (R72) —, without `module-kit` (R62), in the same window of module format versions as `module-kit` (R44). The seeds of virtual learners it derives with the generator from `spec`, not by a scheme of its own (R27). The function `seeded` of the simulator of standalone is a particular case of the derivation of `spec`: the place of the main seed with the names "experiment, unit, assignment", so the simulator's numbers are kept. The normal and the exponential distributions are not part of the format, and `sim` is responsible for their portability (R59). The gate's bands lie in `sim`, in the gate file: it names the commits of `learner-model` and `engine`, the release of `modules` — by the tag and the digest of the index — and the packages by digests. Synthetic packages `sim` has only for its code and tests, not for judging candidates (R103). There are no data of live learners.
- **Does not:** does not change the algorithms, only measures them.
- **Limit:** an anchor skill that no module of the learner teaches the simulator's truth counts as known, and knowledge of an anchor outside the platform enters it only as a shift of the skills that teach it (the population `A-unpractised`, the measure `M9` of architecture 3.5 sim). A learner of olympiad maths alone who does not know the anchor the simulator does not see. This does not hinder the rule of `engine` — it has no check of the anchor (the 2026-11-11 amendment to R04 engine) —, but a candidate with a check of the anchor or with proposing a module needs, before judging, a population of olympiad maths alone where the learner does not know the anchor, and a measure that reads it: the criterion comes before the first candidate (R103; `engine` row В37).
- **Example:** `tools/learners` and `docs/learners.md` in standalone.
- **Repository and stage:** `sim`, stage 1. A release of `sim` comes out by itself after green CI on `main`, and the first tag after the first versions of `learner-model` and `engine`, which before it are checked by their own tests (R103).
- **To decide when detailed:** everything is decided (R03–R05 sim): populations of virtual learners with a calendar and forgetting; two criteria, of the model and of the engine, on a common basis — with measures of forgetting, of the weights of evidence and of a false "knows", the gate's bands and pinned seeds; the gate in CI of `modules` — everything the simulator reads from a package (R103). Beyond the card's items, the detailing decided how CI of the libraries takes the simulator, and the order of releases (R103).

## 4. Flows

### 4.1. Checking a handwritten answer

`tutor` is a library in the process of `api`. On the diagram it is drawn separately, so that the boundary of R03 is visible. Reading and the analysis are two calls (R67). Reading handwriting is also two readers of one provider (R68): on the diagram they are one arrow "request".

```mermaid
sequenceDiagram
    participant A as app
    participant P as api
    participant T as tutor
    participant M as AI provider
    A->>P: submission — a crop of the work
    P->>T: reading handwriting — the work, the open view, the age category, the AI route
    T->>T: admission — the route is allowed, the model is among the admitted
    T->>M: request without identifiers
    M-->>T: the model's answer
    T-->>P: the observations of two readers
    Note over P: module-kit — one observation from two and the verdict by the key and the provenance
    P-->>A: "Not yet. Read: 6"
    A->>P: the tutor's words — the work once more and the number of the incorrect answer
    Note over P: hint ladder — which rung
    P->>T: analysis of the course of solution and a hint — the work, the key and the solution of the task, the trap, the rung, the task's past questions, the presentation style, the explanation language, the age category, the AI route
    T->>T: admission
    T->>M: request without identifiers
    M-->>T: the model's answer
    T-->>P: the tutor's question
    Note over P: leak check and form check, otherwise the fallback text
    P-->>A: the question and the marks on the tutor's layer
    Note over A,P: at the end of the attempt — evidence into learner-model. Outside a lesson and at the end of a lesson run engine chooses the next lesson or task and writes the reason code, and the choice — without the code — comes in the same answer, and in a lesson the next segment goes
```

- Reading and the analysis are different AI capabilities: the analysis sees the key, reading does not (section 3.6; R67). The observations of two readers `module-kit` joins into one, and a slot that they read differently is ambiguous in it: the verdict is "unreadable" (R68; R86).
- The presentation style on the diagram and below is only what of it changes the words: voicing does not go into the AI call, nor does the solving mode (privacy 4; О-23).
- The work is read only on the learner's action — on "Check"; "Step done" in format v0 does not read the work (the 2026-11-02 amendment to R69), and on a pause AI is not called (R69). `module-kit` gives the verdict by the observation as a whole, not by lines while they come (the 2026-10-28 amendment to R54).
- Evidence is the result of an attempt, not of a separate submission (concepts 11).
- A failure of AI or an exhausted quota is a neutral phrase, not "not yet" (R04).
- The server does not store the picture, so for the analysis the application sends the work once more (R09).
- **A hint on request** sends no work and does not call reading (R69). Before the first incorrect answer it gives "givens and unknown" and the task's technique, after it the words of the current rung once more, without AI. "Explain differently" is the same call of a hint as on the diagram, but without the work: the key and the solution of the task, the trap of the rung's slot, the rung, the task's past questions, the presentation style, the explanation language, the age category and the AI route — once per rung. The past questions of the same task each call of the attempt's words gets, so as not to repeat them (R82; privacy 4).
- On a workbook the work is the crops of the filled boxes with their places, without the item's text, and the place in the observation is the answer slot (the 2026-10-27 and 2026-10-28 amendments to R53).
- **A task with a rubric** is also two calls, but other ones: reading an essay and the assessment by the rubric (R75). An item with a rubric has no verdict: instead of `module-kit` and the hint ladder, an assessment and feedback.
  1. `app` sends the work — a crop of the handwriting sheet.
  2. `api` calls reading the essay — with the same as reading handwriting gets: the work, the open view, the age category and the AI route. The sheet is read by one reader (the second 2026-11-01 amendment to R68), without the rubric, and `api` gets the observation — the text, as it is written.
  3. `api` calls the assessment by the rubric — with the read text, the task statement as the topic, the rubric's criteria in order, the presentation style, the explanation language, the age category and the AI route. There is no picture, key or solution of the task in it. The model gives for each criterion a justification and whether it is met, and one feedback on the whole essay.
  4. The feedback passes the leak check and the rule of feedback (R70) and goes to the device.

  An essay that is unreadable does not reach the assessment, and the learner sees a request to rewrite the sheet, as at "unreadable" (concepts 9.1). An item with a rubric has no verdict: the submission ends with "unreadable", and only its time is recorded (R87; R14 and R15 api). The attempt is open for rewriting, and the learner's "Done" ends it.

### 4.2. An answer by typing, choice, edit or widget state

AI is not needed here: `app` sends the value, and `module-kit` compares it with the key or the predicate (concepts 9.2). The mode without AI (О-5) works the same way, and so does the platform with no AI provider at all — for example, self-hosting without agreements with providers.

### 4.3. Own key

- A key exists only for the owner profile of the category `adult` (R04 api; О-4). On the device it lies only if the key's owner decided so on this device, and otherwise in the tab's memory while their profile is open; there is no encryption in the browser, and `app` says so plainly (R84; R08 app).
- The key and its provider come with each request of the owner profile that calls AI: with the work for reading, with the rung's words, with the correct answer words and with "explain differently", which sends no work (section 4.1). A provider without a key `app` names at the start of the attempt, and with each request whose answer or refusal may give an engine choice, so that the choice goes by the same route (the 2026-11-12 amendments in T143 to R84 and R99). In `api` and `tutor` the key lives only in the request's memory — not in the database and not in the logs (privacy 5.2); with a profile of another category `api` does not accept it.
- On connection `api` checks the key through `tutor` with a request without the learner's content, `CheckOwnKey`: the key is accepted, wrong, the key has no rights, or the provider is closed for the profile; the providers open to an own key the admission function names, `ListOwnKeyProviders` (R98). A provider's refusal by a limit is "limit reached" with a cause (R55 tutor), a refusal of the key is an outcome of its own, and neither moves the call to platform AI without an action of the key's owner (privacy 5.1, 5.2).
- The admission function lets it through only if the provider's terms allow it for the learner's age category (privacy 5.3) — by the cell of the admission table: for an own key only the category `adult` is open, without deployment facts (R96). The recommendation of О-4 is an own key only for 18+.
- The model is only from the admitted ones: an own key does not open a model without eval (R07).

### 4.4. From the author to the learner

Module → CI of `modules` (`module-kit`, `sim`; from stage 2 eval) → package → `api` pins it to the attempt → `app` gets the open view. In detail — repositories 4.

### 4.5. Export and deletion

- **The export is assembled by `app`.**
  - Strokes, artifacts and tasks from paper lie on the device, and `api` gives its own part.
  - Works from other devices are exported from them, but for the stored works: while the storage of works is on, `api` keeps the last work each device put, and its part of the export carries them (R113; R135, the 2026-11-13 amendment).
  - The export format is open, in `spec`: [the part `export/`](../export/README.md) — a ZIP of JSON files, where the manifest and the device's files are written by `app`, and `api.zip` is the part of `api`, byte for byte; the evidence log, the state and the observation are the JSON of their protobuf messages with their own `.proto` (R09, R135).
  - There is no own key in the export: the export is learners' data, and the key is a secret of the key's owner (R84; privacy 5.2).
- **Deletion is confirmed by a fresh sign-in.**
  - `api` deletes the data from the database and deletes the account at the sign-in service. Without a fresh sign-in the deletion gets the refusal "fresh sign-in needed", `CAUSE_FRESH_SIGN_IN_NEEDED` (R98; [contracts text](../contracts/README.md), section 15).
  - The connection "Sign in with Google" in the owner's Google account is not removed by the deletion at the sign-in service. After the answer "deleted" `app` removes it: it revokes the Google access token of the fresh sign-in at `https://oauth2.googleapis.com/revoke`, and `api` does not get this token (R144; sources 4.6). While `app` has no deletion screen, the connection stays, and the owner removes it themselves on the page of Google's connected apps (DEBT.md, Д221).
  - A deleted profile other devices erase by the account's list of profiles, which `app` reads at start.
  - Other devices erase their data at the next call to `api` while their ID token lives — about an hour after the deletion: it answers that the account is gone, `CAUSE_ACCOUNT_GONE`. The revocation of tokens does not put out earlier ID tokens — "existing ID tokens may remain active until their natural expiration (one hour)" (the Firebase Admin SDK for Go v4.22.0, `auth/user_mgt.go`, read by `api` 2026-11-02; architecture 4 api). Later the sign-in service on the device signs out by itself, and the data are erased at the next sign-in on it: a new sign-in gives a new UID without an account of `api`, and "no access", when the device's register holds an account, `app` reads as the sign-in of another account (RUN.md, Д89). A device that is not opened keeps them until the browser or an adult erases them (R20, R21 api; architecture 3.10 api).
- **Honest retention periods** name the backups of the database, the sign-in service, the logs of the platform and of AI providers, and other devices (privacy 1).
- **What remains of consent** after deletion is П-14.

### 4.6. A change of AI model and a change of algorithm

- A new model for an AI capability is admitted when it passes the capability eval set and the eval sets of all the published modules with this capability. False alarms are counted by the verdict, through `module-kit` (repositories 4): by the runner's report — a message of the eval protocol without the content of works —, and for admission only a report with the verdicts of `module-kit` will do ([contracts text](../contracts/README.md), section 14; R95; the 2026-11-03 amendment to R07). The assessment by a rubric has no verdict, and it is measured by false alarms on met criteria, and the second measure is agreement with people and kappa per criterion (R71). A model on the device is admitted the same way (R66). The eval sets of modules lie in the git of `modules`, outside the package and the release files (R62; R03 modules), and meet the runner in CI of `modules`: a model is admitted when the pull request of `modules` is merged that moves to the tag of `tutor` with it in the list of admitted models and runs the eval sets of all modules. The order is repositories 4 (В9 `modules`; R04 modules).
- eval at a provider beyond OpenAI and Anthropic goes by its terms: Together, Cerebras and Fireworks forbid benchmarking, and SambaNova forbids publishing its results without its consent (R65; privacy 5.3).
- A change of `learner-model` or `engine` passes `sim` by a criterion written down in advance (repositories 4).
- A change of the rule of `engine` does not rewrite the reason codes saved with the choices and does not change the meaning of a code. A new branch of the rule comes with a new code, and the code of a branch that the engine removed stays in the list and is no longer given ([contracts text](../contracts/README.md), section 15; R100).

## 6. Interface: packages and the iframe sandbox

- **Micro-frontends.** The author wanted «микрофронтенды в своих репозиториях», "micro-frontends in their own repositories". In NovaTrail these are the UI packages — `canvas` and `skill-map`: parts of the interface in their own repositories, with their own releases.
  - `app` builds them by exact version into one application (R16).
  - During development `app` connects working copies of the packages, and only exact versions go into a release.
- **Why without loading at run time** (R16):
  - With exact versions `app` would pin the version of each part anyway, so there would be no independent deployment.
  - The cost would remain: diverging versions, duplicates of the framework, more complex CSP, cache and offline.
- **How the packages join the application** — as web components, with data types from the releases of `spec` (R36): the packages have several consumers, and the framework of each is decided by its repository. The packages come out in npm, in the scope `@altnovatrail` (R37).
- **Foreign code** is only the widgets of modules, and only in the iframe sandbox (section 3.4).
  - Shadow DOM is not a means of protection: it isolates styles and the DOM tree, but not code (sources 5.3).
  - So a module is not embedded into the page as a web component through `<script src>`, as Gemini proposed (R16).
- **The second consumer of a package** — for example, the site or a card of the MCP channel — gets a second build of the same package. So the chat widget of standalone is built: one HTML page in an iframe of the host.
- **Icons** — one set of the Iconify catalog, Material Symbols, for all UI packages (R78).
  - Each package takes the set's package `@iconify-json/material-symbols` itself, by exact version, and builds in at build time only its own icons: `canvas` and `skill-map` from `devDependencies`, and `app` from `dependencies` (the 2026-11-02 amendment to R39). At run time there is not one request to the Iconify API.
  - An icon's name is `material-symbols:<base>-outline-rounded`. The selected option of a choice and a mode turned on are the same icon with a fill, `material-symbols:<base>-rounded`.
  - One value is one icon, and one icon is one value. The table below names the buttons of the row of `canvas` — the task screen of `app` shows them — and the values that more than one package needs. A new value enters it as a row «в реестр spec». An icon for a value that only it has a package chooses from the set itself, but not from those in the table; if it already stands at another package for another value, both values enter the table.

## 7. What the architecture does not have

- Its own clusters, queues and event bus (R11).
- A service per area: without queues that is a distributed monolith of synchronous chains (R15).
- Pictures and sound that go for checking, and own keys, on the server (R09; R84).
- A real-time channel in the first slice (Т-25).
- Mailings and notifications: an adult's contacts are needed only for the sign-in and the subscription (privacy 1).
- An operator's console as a separate application: in the first slice it is the commands and jobs of `api`.
