## 1. Принципы

- **Граница R03 проходит по коду.**
  - Всё, что обращается к модели, — в `tutor`. Модель, которая читала бы работу на устройстве, — тоже его код: её веса, eval и допуск — у `tutor`, а вердикт — у `module-kit` (R66). В первом срезе такого чтения нет.
  - Вердикт выносит `module-kit`, модель ученика считает `learner-model`, следующий урок или задачу выбирает `engine`. Ни одна из этих библиотек модель не вызывает.
  - CI `api` проверяет полный список зависимостей: SDK поставщиков ИИ попадают в сборку только через `tutor` (R15).
- **Из частей платформы данные учеников на сервере хранит только `api`.**
  - `tutor` ничего не хранит. В типах его запросов нет полей для идентификаторов ученика и аккаунта, поэтому ИИ видит работу, но не знает чью (R15; privacy 1, 5.1).
  - Вне платформы часть данных держат сервис входа, поставщики ИИ и, с этапа 3, оплата (раздел 5).
- **Отдельный процесс — только там, где он нужен.** В первом срезе сервис один — `api`; `tutor`, `module-kit`, `learner-model` и `engine` — библиотеки в его процессе. `tutor` станет сервисом, когда у него появится второй потребитель (R15).
- **Ключ нерешённой задачи — только на сервере.** Приложение получает открытый вид задачи (R05). Открытый вид строит `module-kit` по пометкам `x-open` в схемах формата: поле без пометки закрыто, так что новое поле формата закрыто, пока его явно не открыли (R45).
- **Воспроизводимость** (R03):
  - попытка хранит дайджест своего пакета модуля, версию формата модуля, версию `module-kit` и зерно. Дайджест пакета — дайджест его описи, и он зависит только от файлов модуля и версии формата его паспорта ([текст формата](../format/README.md), раздел 25; R62). Модуль проверяется и исполняется по версии формата, которую называет его паспорт, и новая версия формата не меняет его вердикта, пока автор не переведёт модуль на неё (R44);
  - выбор движка хранит версии `engine` и `learner-model`, дайджесты пакетов, зерно и код причины, а ещё релиз `modules`, номер последнего свидетельства журнала, по которому он сделан, время выбора, класс, по которому модель считала отправную точку модулей без свидетельств, и был ли пул ограничен задачами без ИИ: без них повтор по журналу не знает, какой префикс журнала брать, какие отметки о снятии тогда действовали, на какое время модель считала удержание и срок повторения, по какому классу — отправную точку модулей без свидетельств, какие прохождения уроков и закрытые попытки задач с рубрикой видел движок — их причина и время конца, раз записаны, не меняются, — и из какого пула он выбирал (R80; В4, В14, В15 и В18 `api`; R04 и R08 learner-model; concepts 12);
  - вердикт повторяется по сохранённому наблюдению, выбор — по журналу свидетельств (R80); и то и другое — без ИИ;
  - генератор случайности и вывод зёрен задаёт `spec`, с тест-векторами: PCG, как в `math/rand/v2` Go, и места случайности, как у стенда standalone ([текст формата](../format/README.md), раздел 22; R59; Т-18 закрыт). Экземпляр шаблона задачи повторяется по пакету и зерну попытки: его выбирает одно число места `template`, ID задачи, `instance` ([текст формата](../format/README.md), раздел 23; R60).
- **Свои части интерфейса собираются при сборке, чужой код работает только в iframe-песочнице** (R16, раздел 6).
- **Без своих кластеров, очередей и шины событий** (R11). Части говорят синхронными запросами по контрактам из `spec`: `app` с `api` — по Connect, унарными вызовами, а код контрактов приходит из релизов `spec` (R83). Фоновые работы — задания Cloud Run по расписанию, как в canvas-api.
- **Журналы — без прямых идентификаторов, IP-адресов и содержания** (R09; privacy 4).
  - Cloud Run сам пишет журналы запросов со стандартным полем `httpRequest`, а в нём есть `remoteIp` — IP-адрес клиента. canvas-api записал то же о журналах Cloud Run и Firebase Hosting (privacy 4 canvas-api).
  - COPPA относит IP-адрес к постоянным идентификаторам, то есть к персональной информации (16 CFR 312.2).
  - Поэтому журналы запросов исключаются в Cloud Logging, а регион журналов выбирается до первого развёртывания (П-11).
  - Журналы хостинга `app` и сервиса входа решаются вместе с выбором этих сервисов (раздел 3.12; П-9).

  Источники — в разделе 8.

## 3. Компоненты

У каждого компонента — карточка: что он делает и чего не делает, его данные и связи, репозиторий и этап (product 11). Пункты «Решить при детализации» — то, с чего начинается работа в его репозитории (repositories 2.2). Вопрос, который касается нескольких репозиториев, — в реестрах `spec`, и карточка ссылается на него.

Задача, которая заводила репозиторий (RUN.md, T04–T14), могла назвать пункты детализации сверх карточки, а могла пропустить пункт карточки. Карточку под это правит «Итог детализации» самого репозитория — строкой его таблицы 3 «в реестр spec», когда решение уже принято, а не заранее.

### 3.1. app — приложение ученика и взрослого

- **Делает:**
  - оболочку: вход через сервис входа, выбор ученика на общем устройстве, начало работы — возраст, страна, согласие; класс ученика — когда паспорт модуля называет классы (R49);
  - три входа в приложение: «Мои предметы», «Карта навыков» и, позже, «Задача с моей бумаги» (product 4);
  - плеер урока и экран задачи: канва, ячейки ответа, выбор варианта, панель наставника с шагами решения и подсказками, строка разговора. Строка разговора первого среза — кнопки просьб, подсказка и «объясни иначе» (R82), без своего текста ученика: свой текст — позже, своей возможностью `tutor` (product 10; В40 `app`). Текст пункта листа для рукописи `app` показывает вместе с вариантами `choice`, рядом с листом, а не на нём; строку пункта рабочей тетради показывает канва (R32 и R34 canvas). Навыков, полосы и сложности задачи в её открытом виде нет (R51), как нет и её приёмов, ловушек, случая попроще, фразы-утечки и решения (R57);
  - урок — по его открытому виду: звенья в порядке автора, объяснения, примеры с разбором, чей показ автора ученик открывает по одной части и может спрятать, и задачи урока, которые даёт `api`. Навыков и возрастных категорий урока в открытом виде нет (R58);
  - прогресс и карту навыков;
  - раздел для взрослых за PIN: профили, тариф, свой ключ, настройки, выгрузка и удаление;
  - раскрытие, что ученик говорит с ИИ, а не с человеком (privacy 5.3; П-15);
  - озвучку слов наставника и открытых текстов модуля синтезом речи устройства — голосом, который называет сам, по правилу Т-13. Включена ли озвучка и её скорость — в стиле подачи профиля ученика, а голос по языку и разрешение взрослого на Android и Linux — на устройстве (R07 app; О-23);
  - интерфейс на `en` и `ru`: язык интерфейса ученика — поле его профиля, которое задаёт взрослый, а экраны до выбора ученика и раздел для взрослых — на языке устройства (R92). Переводы — по общим правилам пакетов интерфейса, а слова, которые показывает больше одного пакета, — по таблице слов раздела 6 (R91);
  - доступность — по стандарту пакетов интерфейса, WCAG 2.2 AA с 2.5.5 и 2.3.3 (R90). Чему `app` и пакеты пока не отвечают, `app` называет на странице «Доступность», среди юридических страниц (раздел 3.13; R11 app).
- **Не делает:**
  - не получает ключ, решение и ловушки нерешённой задачи, а её приём — только от `api`, на шаге, который его даёт, или по просьбе ученика (R57);
  - не выносит вердикт;
  - не обращается к поставщикам ИИ;
  - не отправляет на сервер штрихи и целое фото.
- **Данные и связи:**
  - на устройстве — штрихи с временем и нажимом, артефакты, а свой ключ — только у профиля владельца категории `adult` и только по его выбору на этом устройстве, иначе в памяти вкладки. `app` шлёт ключ с каждым запросом этого профиля, который зовёт ИИ (R84; R08 app). Ещё — контекст каждой отправки: на листе для рукописи — где вырезка лежит на листе, её целые числа, рамки групп штрихов, таблица «метка группы → ID штрихов» и дайджест отправки, а на рабочей тетради — таблица «окошко → ID штрихов» и дайджест. Его отдаёт канва вместе с работой, а держит `app` как есть: по дайджесту канва принимает контекст назад (R36);
  - говорит с `api` и с сервисом входа;
  - конфигурацию развёртывания читает при каждом старте из `/deployment.json` в корне своего origin, рядом с подписанной сборкой, но не в ней, и проверяет строго — до первого запроса в сеть. Схема файла `deployment.schema.json` и шаблон CSP `csp.json` лежат в сборке, формат — R09 app, а в `spec` он переходит с первым развёртыванием (R85). Сам `app` стоит в корне своего origin;
  - открытый вид задачи получает от `api` и читает по типам из релизов `spec` (R36) — версий формата модуля в окне. Типы TypeScript — пакет npm `@altnovatrail/spec`, `@altnovatrail/spec/formatv0/open`, по точной версии в `devDependencies`, а `api` читает тот же вид типами Go `types/formatv0/open` (R72, R73). Пока формат — v0, `app` и `api` переходят на новую версию вместе (R44; repositories 4);
  - собирает в себя `canvas` и `skill-map` — веб-компонентами (R36), по точной версии из npm (R37). Подпись версии проверяет рецепт `spec` `release-verify` в CI pull request, который меняет lock-файл (R77). Канве он даёт с задачей открытый вид паспорта её модуля, свойством `manifest`, и файлы её картинок — функцией `media`, из файлов части пакета для устройства, которые раздаёт `api` (R36 и поправка 2026-11-02 к нему). Типы элемента — `@altnovatrail/spec/canvas`, в том же пакете и по той же точной версии (R74). Паспорт он получает от `api` по дайджесту пакета попытки, один раз на пакет, и кеширует по нему, а не с каждой задачей (R62). Открытые виды снятой с публикации версии модуля он из кеша удаляет (R63);
  - иконки своих кнопок берёт из набора Material Symbols по таблице значений раздела 6: пакет `@iconify-json/material-symbols` по точной версии, вшитый при сборке, — в `dependencies`, как всё, что вшивает сборщик (поправка 2026-11-02 к R39). К API Iconify приложение не обращается (R78);
  - позже, с текстовой канвой, — озвучивает её «прослушать» по событию `speak` тем же синтезом речи, что и всё приложение (R36; Т-13). В первом срезе текстовой канвы нет (R41);
  - виджеты модулей открывает через хост виджетов из `canvas` (раздел 3.4).
- **Репозиторий и этап:** `app`, этап 2.
- **Решить при детализации:** решено всё — детализация закончена 2026-11-02 (T08 `app`): фреймворк и сборка — R03 app; хранение на устройстве — R04 app; шаги решения — R05 app; плеер урока — R06 app; озвучка — R07 app; свой ключ — R08 app и R84; конфигурация развёртывания — R09 app и R85; языки интерфейса — R10 app и R92; доступность интерфейса — R11 app и R90 (В38 `app`). Что `app` решает дальше, — раздел 3.10 его `docs/architecture.md`.
  - фреймворк и сборка: в canvas-api — React 19 и Vite 8 (R47 canvas-api), в standalone — Preact. Пакеты интерфейса фреймворка не навязывают (R36). От типов `spec` каждый пакет зависит своей копией по точной версии, а не `peerDependencies`: пакет несёт одни объявления, и копии ничего не стоят (R73). Дополнено 2026-11-02: и чем сборка вшивает иконки набора — плагином сборщика или скриптом на `@iconify/utils`, без автоустановки наборов, — и как `app` держит ту же версию набора, что у собранных им пакетов (R78). Всё, что вшивает сборщик, стоит в `dependencies`, а в `devDependencies` — только инструменты (поправка 2026-11-02 к R39; Т-36 закрыт);
  - что и сколько хранится на устройстве, в том числе контекст отправки (R36);
  - шаги решения: `app` ведёт их по открытому виду, а условия выхода из шага — события на устройстве, без ключа. Дополнено 2026-10-27: шаги и их условия выхода — `givens_ticked`, `answer_slots_filled` и `none` — в открытом виде `solving-steps.yaml`, а фишки «что известно и что найти» — в открытом виде задачи. Что значит «в ячейке что-то есть» у привязок `anywhere` и `sheet`, решают `app` и `canvas` (R57; RUN.md, Д38). Дополнено 2026-10-27: на рабочей тетради это свойство канвы `filled` (R36; RUN.md, Д41). Дополнено 2026-11-01: условие выхода `answer_slots_filled` `app` читает по привязке ячейки — у `choice` по своему выбору варианта, у других ячеек по `filled` канвы, а на листе `filled` говорит, есть ли штрих у ячейки `anywhere` или `sheet` (вторая поправка 2026-11-01 к R36; RUN.md, Д58);
  - плеер урока: как звенья сменяют друг друга и как показ автора открывается по частям и прячется. Пометку «последовательный» у модуля, чей граф навыков — цепочка, `app` выводит из ярусов `skill_tiers`: навыков модуля не меньше двух, и каждый стоит в своём ярусе (R58 и поправка 2026-11-02 к нему; RUN.md, Д39). Дополнено 2026-11-01: части показа открывает и весь показ прячет ученик кнопками элемента канвы, а `app` ведёт звенья, даёт каждому звену новый элемент, хранит состояние показа по событию `demochange` и возвращает его свойством `demoState`. Что делать с состоянием, сохранённым у другой версии модуля, чьего показа у примера уже нет, решает эта детализация (вторая поправка 2026-11-01 к R36; RUN.md, Д58);
  - озвучка — сначала синтезом речи устройства (Т-13). Дополнено 2026-11-02 (В17 `app`): решена R07 app — в «Делает» выше;
  - свой ключ взрослого на общем планшете: для профиля ребёнка он не используется (Т-9, О-4). Дополнено 2026-11-02 (В20 и В21 `app`): решён R08 app и R84 — в «Данные и связи» выше;
  - конфигурация развёртывания — адрес `api`, параметры сервиса входа — читается во время работы, а не вшивается в сборку. Тогда self-hosting берёт ту же подписанную сборку. Дополнено 2026-11-02 (В24 `app`): решена R09 app — в «Данные и связи» выше;
  - языки интерфейса (О-2) и доступность интерфейса. Схема переводов и стандарт доступности — общие для пакетов интерфейса, а их вход — подписи и строка кнопок `canvas` (R36). Уровень доступности ждёт О-24, а лист одним указателем прокручивают кнопки «Выше» и «Ниже» в строке `canvas` (R33 canvas; О-24, дополнено 2026-10-27). Дополнено 2026-11-02 (В30, В32 и В33 `app`): решены — стандарт доступности пакетов интерфейса R90, и О-24 решён; переводы — R91; язык интерфейса — R92.

### 3.2. canvas — канвы

- **Делает:**
  - виды канвы (concepts 8); в первом срезе — лист для рукописи и рабочая тетрадь (product 10; R41). ### 3.4. Виджеты модулей

- **Что это:** интерактивные компоненты модуля на канве — код автора модуля (concepts 8).
- **Как работают** (R16):
  - в iframe-песочнице без `allow-same-origin`, на отдельном регистрируемом домене. Вместе с `allow-scripts` он позволил бы странице того же origin снять песочницу (раздел 8);
  - CSP не даёт коду виджета ходить в сеть: загружается только сам бандл;
  - с приложением виджет говорит только по протоколу из `spec`;
  - бандл подписан и закреплён по хешу в пакете модуля, а пакет закреплён за попыткой;
  - официальные виджеты работают в той же iframe-песочнице, что и чужие;
  - детям — только виджеты, прошедшие ревью (О-9).
- **Этап 4.** В первом срезе виджетов нет: ни одному из трёх его модулей они не нужны (R41). Привязки ячейки к состоянию виджета в формате v0 нет: она придёт с протоколом виджета, минорной версией (R51). Образец для авторов — `widget-template` (раздел 3.13).
- **Решить при детализации** — в эпике E5 RUN.md:
  - протокол виджета. Что ему решать сверх R16 — по анализу автора 2026-10-21 (product 14). Сторона протокола в приложении — хост виджетов `canvas`, который `app` собирает в себя (раздел 3.2); «`app`» ниже — это он (В22 `canvas`):
    - канал. Отправителя сообщения HTML Standard велит проверять по origin, а у виджета без `allow-same-origin` origin непрозрачный и сериализуется как "null". Сверка `event.source` с окном iframe документы не различает: окно у iframe одно, а при переходе меняется только документ за ним. Поэтому анализ советует порт `MessageChannel`: `app` передаёт его виджету один раз, при первой загрузке iframe, и дальше слушает только его, а документ, на который виджет перешёл потом, этого порта не получал (раздел 8). Как `app` замечает такой переход, решает протокол;
    - версия состояния в каждом сообщении виджета: `app` знает, к какой версии относятся вердикт и слова наставника, а пометку на части виджета, которая с тех пор изменилась, не рисует — как пометку листа, чьи штрихи стёрты (architecture 3.2 canvas);
    - части виджета для пометок: слой наставника лежит над виджетом (concepts 8), поэтому виджет называет свои части и их рамки, а пометка держится за часть, как на листе — за штрихи;
    - виджет сообщает состояние и события ученика, а не вердикт. Верно ли, решает `module-kit` (concepts 9.2), а по какому состоянию — сообщённому виджетом или повторённому на сервере по зерну и событиям, — решает Т-24. Зерно виджета — своё, не зерно попытки: зерно попытки на устройство не уходит, а как виджет получает своё, решает протокол виджета (R59);
    - тесты соответствия протоколу — в `spec`, рядом с протоколом, как тест-векторы вердикта, и в его релизах тем же путём, что файлы формата: своим файлом релиза и в модуле Go (R64). Они на обе стороны протокола: их проходят и виджет, и хост виджетов `canvas`, каждый в своём CI (В22 `canvas`). Тесты одной стороны держат только её: хост, который разошёлся с тестовым, ломал бы виджеты, прошедшие тесты, и этого никто бы не заметил. Тестовый хост — в среде разработки `widget-template` (раздел 3.13); будет ли им сам `canvas`, решит эпик E5 вместе с `widget-template`, а условие для хоста от этого не меняется. Протоколу виджет отвечает, если проходит тесты, а библиотека для авторов — удобство, а не условие;
  - можно ли верить состоянию, о котором сообщает виджет (Т-24);
  - снятие с публикации версии виджета, которая оказалась вредной. Снятая версия модуля снимает и бандлы своих виджетов: устройство их больше не грузит, а причина «опасный бандл» придёт минорной версией формата вместе с протоколом виджета (R63; Т-30 закрыт).

### 3.5. api — сервис платформы

- **Делает:**
  - вход: проверяет токен сервиса входа;
  - учеников: псевдоним, возрастная категория, страна, стиль подачи, режим по умолчанию (concepts 10), языки, класс — если его спрашивает модуль (R49); записи согласия; права;
  - попытки: хранит дайджест пакета модуля, версию формата модуля, версию `module-kit` и зерно (R44). Зерно попытки `api` берёт из криптостойкого источника, когда попытка начинается, и на устройство его не отдаёт: по состоянию места случайности видно его зерно, а генератор не криптостойкий (R59); отдаёт открытый вид. Задачу ученику даёт, только если он в одной из её возрастных категорий, `age_categories` (R51), а урок — только если ученику подходят и урок, и каждая его задача (R58);
  - урок: его открытый вид — без навыков и возрастных категорий — и задачи урока по его звеньям. Задача урока — такая же попытка, как вне урока (R58). Урок `api` ведёт прохождением урока — строкой на профиль и урок, на пакете, где урок начат, одной на все устройства, со своим ID (concepts 5; R13 api). Место в уроке и состояние показа держит `app`. Обычный конец урока — «урок пройден» от `app`, который `api` принимает, когда кончились все звенья задачи; сам `api` кончает прохождение «без проверки», «не подходит» и «брошен» — 30 дней без действий, — а досрочно — если его введёт детализация `engine`; что контракт несёт уроку — RUN.md, T64 (В15 `app`, В16 `api`; R06 app);
  - шаблон задачи: экземпляр попытки — по её зерну, из пакета, и Starlark на попытке не запускается — ключ каждого экземпляра `module-kit` посчитал и проверил при проверке модуля. Приложению — открытый вид экземпляра, без поля `template` (R60). Пакет несёт числа каждого экземпляра, и `api` берёт номер `below(count)` и подставляет его числа кодом `module-kit`, не исполняя выражений (R62);
  - проверку: отправка → `tutor` читает работу — у рукописи два читателя → `module-kit` сводит их наблюдения в одно и выносит по нему вердикт на каждую ячейку ответа и на пункт. Хранит `api` сведённое наблюдение и рядом выбор касанием: по ним вердикт повторяется без ИИ (R03). Частей записи и других прочтений в наблюдении нет ([текст контрактов](../contracts/README.md), раздел 10; R86). Условия проверки ячеек `api` вычисляет кодом `module-kit` в потоке запроса и сразу — не больше, чем у процесса CPU (`GOMAXPROCS`): часы `module-kit`, 1 с на условие, идут по стенному времени, и «без проверки» не должно зависеть от нагрузки. Отмена `context` запроса — ошибка без вердикта: «без проверки» `api` её не записывает, и отправка остаётся без вердикта (В13 `module-kit`; R11 module-kit). У задачи с рубрикой — оценка по рубрике в `tutor` и отзыв по рубрике, без вердикта (R04; R41): отправка кончается отзывом, «не прочитать» или «без проверки», а попытку закрывает «Готово» ученика. Из такой попытки сервер хранит, чем кончилась каждая отправка, а у отзыва — отметки критериев и источник слов, без текста сочинения и слов отзыва (R87; R14 и R15 api). Проверка ячейки — в части пакета для сервера: ни её, ни её вида приложение не получает (R56);
  - по итогу попытки — свидетельство в `learner-model`, затем `engine` выбирает следующий урок или задачу и пишет код причины — из пула и уроков, которые `api` при закрытом ИИ ограничивает задачами без ИИ (concepts 12; В14 `api`; R11 api). Внутри урока дальше идёт звено в порядке автора, а движок `api` зовёт, когда прохождение урока кончилось или ученик просит другое (concepts 5; R13 api; В15 `api`). Выбор движка приходит в ответе, которым кончилась попытка вне урока или прохождение урока (R13, R17 api);
  - лестницу подсказок: какую ступень дать и о какой ячейке она говорит — о первой «пока нет» по порядку, — когда предложить взрослого или показ решения и когда нужен запасной текст (R82). Запасной текст ступеней 1–2 — текст значения ловушки, совет ловушки или шаблон ступени модуля, а третьей — случай попроще пункта (R57);
  - показ решения: ребёнку — с четвёртого неверного ответа, а при настройке взрослого «спросить перед показом», по умолчанию включённой, — только действием взрослого, иначе отказ «нужен взрослый»; ученику категории `adult` — с начала попытки. Показ закрывает попытку исходом «решение показано», и решение с ключом уходит на устройство, только когда попытка закрыта им или верным ответом (R82; поправка 2026-11-02 к R05);
  - приём задачи — на шаге решения, который его даёт: `app` называет попытку и место шага, а `api` отвечает ID приёмов задачи, пусто — если их нет. И по просьбе ученика до первого неверного ответа — без ИИ и без чтения работы. Какой приём он выдал, на шаге или по просьбе, `api` записывает, и свидетельство это несёт (R57; R82). «Что известно и что найти» открыты и приходят с открытым видом задачи: их показывает `app`, и `api` их не записывает (В12 `app`; R82; RUN.md, T62);
  - подсказку по просьбе после неверного ответа — ещё раз слова текущей ступени, без ИИ, — и «объясни иначе» — ту же ступень другими словами, один вызов ИИ на ступень, без работы, с прошлыми вопросами задачи (R82; раздел 4.1);
  - проверку утечки — до того, как любой текст наставника уйдёт на устройство. Поэтому слова наставника уходят целиком, не потоком (R54). Как она ищет ключи и фразы-утечки, нормативно говорит [текст формата](../format/README.md), раздел 20, а код её — в `module-kit` (R57);
  - там же — проверку формы подсказки и правило отзыва по рубрике (R70). Подсказка — ровно один вопрос, не больше двух предложений, буквы языка объяснений и не больше 30 слов по-русски и 35 по-английски, а на языке, которого замер не мерил, — без предела слов. Отзыв — не больше трёх предложений и 80 слов по-английски, а отрезок в кавычках от четырёх слов — только слова ученика. Подсказка, которая проверку не прошла, — запасной текст, а отзыв — фраза `app` «отзыва на этот раз нет», без повтора вызова (R87). Код обеих проверок — в `tutor`, тот же, что в его eval;
  - квоту ИИ платформы — в долларах по сообщению о расходе `tutor`, на сутки семьи, с потолками профиля и аккаунта по тарифу аккаунта, который приходит с инвайт-кодом. Исчерпанная квота — «без проверки» и запасной текст, а попытка ждёт (R11, R12 api; concepts 14). С этапа 3 — тарифы сверх закрытого среза и оплату (О-14);
  - свой ключ — только с запросом профиля категории `adult` (R04 api) и только в памяти запроса. При подключении `api` проверяет ключ через `tutor`, запросом без содержания ученика, а поставщиков, открытых своему ключу у профиля, называет по функции допуска (Т-20; R84);
  - свою часть выгрузки и удаление (раздел 4.5);
  - задания и команды оператора, как `admin` в canvas-api, а не отдельное приложение:
    - миграции;
    - сроки хранения (П-9);
    - проверку согласия (П-1);
    - допуск в закрытый срез;
    - список стран до DPIA (П-2);
    - задание после выкладки (R07 api);
    - смену тарифа по коду и открытие ИИ платформы после «лимита платформы» (R11 api);
    - очистку кортежей и `changelog` OpenFGA (R04, R05 api);
    - доведение удалений и удаление пользователей сервиса входа без аккаунта `api` (R21 api);
  - в первом срезе держит в своём образе пакеты модулей — все версии индекса закреплённого релиза `modules` в окне формата, снятые тоже (R07 api), — и раздаёт файлы их частей для устройства — медиафайлы, `LICENSE` и `NOTICE` (раздел 3.10). Новую попытку `api` даёт только по версии, которую индекс закреплённого релиза `modules` не отмечает снятой с публикации. Снятая версия остаётся в образе только для повтора вердикта: начатые на ней попытки закрываются «без проверки», а файлов её части для устройства `api` больше не раздаёт (R63). Открытые виды строит `module-kit` из части для сервера: паспорта, графа навыков, каталога приёмов и шагов решения `api` отдаёт по дайджесту пакета попытки, урока — ученику, которому урок подходит, задачи — с попыткой (R62).
- **Не делает:**
  - не хранит картинки и звук, которые уходят на проверку, и свои ключи; артефакты — только по выбору владельца аккаунта (П-8);
  - не обращается к поставщикам ИИ в обход `tutor`;
  - не пишет в журналы прямые идентификаторы, IP-адреса и содержание.
- **Данные и связи:**
  - база `api` — единственное хранилище данных учеников среди частей платформы. Это Neon Postgres, а хранилище OpenFGA — вторая база того же проекта (R04, R05 api);
  - говорит с сервисом входа, с поставщиками ИИ — через `tutor`, позже — с оплатой.
- **Репозиторий и этап:** `api`, этап 2.
- **Решить при детализации:**
  - вход и права — решено R03, R04 и R20 api: Firebase Auth, вход через Google, Apple — к первому развёртыванию; ID token с отзывом на каждом запросе; права — OpenFGA в процессе `api`, субъект — аккаунт, профиль — параметр запроса; свежий вход — `auth_time` не старше 5 минут. Для учителей права понадобятся в виде «кто, к чему и в какой роли получил доступ»;
  - база и где живёт модель ученика (П-7) — решено: база — Neon Postgres, а хранилище OpenFGA — вторая база того же проекта (R04, R05 api); модель ученика — в базе `api` (R80; R06 api);
  - журнал свидетельств и состояние навыков (Т-22) — решено R80: журнал только на дозапись, а состояние — кэш;
  - какую версию модуля получает новая попытка — решено R07 api: новейшую по semver неснятую версию закреплённого индекса в окне формата `api`, одну на всех учеников, а задача урока — на пакете, на котором урок начат (R13 api). Попытка хранит дайджест своего пакета. Конфигурация — `modules.json`: тег релиза `modules` и дайджест его индекса (R63). Попытки на снятой версии и вне окна закрывают «без проверки» задание после выкладки и проверка при запросе, а ни файлов части для устройства, ни открытых видов такой версии `api` не отдаёт (R44, R63);
  - перенос прогресса по таблице соответствия старых ID навыков новым после мажорной версии — `retired_skills` графа навыков (concepts 3; R49). Решено: `api` отсекает свидетельства `wrong_key` и отдаёт журнал и графы текущих версий, а переносит `learner-model` по условиям карточки 3.8 (R08 api; поправка 2026-11-02 к R80);
  - показ решения (О-7) и подсказка по просьбе ученика (О-21) — решено R82 (R09 и R10 api): показ ребёнку — с четвёртого неверного ответа и с настройкой взрослого «спросить перед показом», ученику категории `adult` — с начала попытки; просьба до первого неверного ответа — «что известно и что найти» и приём, после — текущая ступень без ИИ, а «объясни иначе» — раз на ступень; ячейка ступени и запасного текста — первая «пока нет» по порядку. Неотправленную работу просьба на чтение не шлёт, а на паузе работу не читают — только мигает кнопка (R69);
  - что ученик видит вместо отзыва по рубрике, который не прошёл правило отзыва (R70), и сочинение, которое не прочитать (R75), — решено R87 (R14 и R15 api): фраза `app` «отзыва на этот раз нет» и конец отправки «не прочитать», без вердикта, а из попытки сервер хранит только, чем кончилась каждая отправка, и отметки критериев (П-19 закрыт);
  - урок — решено R13 api: прохождение урока, его начало по запросу `app`, конец звена и причины конца прохождения; что нужно от контракта — RUN.md, T64 (В16 `api`), а от `engine` — карточка 3.8 (В15 `api`; R58; RUN.md, Д39);
  - тарифы (О-14) и оплата — этап 3. Квота этапа 2 — решено R11 и R12 api, а её числа — вход О-14;
  - протокол между `app` и `api` — решено R17 и R18 api: запросы по таблице architecture 3.9 api, на проводе — двоичный protobuf (третья поправка 2026-11-02 к R83). Формат, protobuf и buf, решил R11, а раскладку, правила buf, версии, сгенерированный код и транспорт Connect — R83; что `api` нужно от контракта — RUN.md, у таблицы 1 и в T62–T64 (В25 `api`). Контракт — пакет `novatrail.api.v1`: проверка попытки, `AttemptService`, — отправка, вердикт, слова наставника и пометки, «Подскажи», начало шага, показ решения и «Готово» — с одним перечислением причин отказов и исходов (R97; [текст контрактов](../contracts/README.md), раздел 15). `api` получает его своим переходом на тег (RUN.md, Д99);
  - канал реального времени — решено R19 api: в первом срезе его нет, а проверка рукописи — два запроса (Т-25);
  - с этапа 4 — условия проверки сторонних модулей в отдельном процессе с пределом памяти: go.starlark.net памяти не считает, а нехватку памяти и переполнение стека Go `recover` не ловит (О-9; R11 module-kit). Вычисление, которое остановил предел, — ошибка вычисления, то есть «без проверки» ([текст формата](../format/README.md), раздел 15);
  - удаление — решено R20 и R21 api: по свежему входу, а не по PIN (раздел 4.5).

### 3.6. tutor — наставник: чтение и слова

- **Делает:**
  - возможности ИИ (concepts 10, 15):
    - чтение рукописи и чтение текста: работа превращается в наблюдение, ключа модель не видит. Значение ячейки чтение отдаёт так, как оно записано: нормализует его вид проверки в `module-kit` (R56). Рукопись читают два читателя одного поставщика, двумя вызовами, и ячейка, которую они прочли по-разному, — «не прочитать» (R68). Так — у ячеек, чья проверка даёт вердикт, а лист под рубрикой читает один читатель (вторая поправка 2026-11-01 к R68). `tutor` отдаёт наблюдения обоих читателей или исход вызова, а сводит их `module-kit`. О проверке ячейки читатель не знает ничего — ни вида, ни вариантов выбора. Части записи и другие прочтения остаются у него: по ним он решает, что отдать ([текст контрактов](../contracts/README.md), раздел 10; R86);
    - разбор хода решения: модель видит ещё ключ и решение задачи и ищет первую ошибку в решении ученика (privacy 5.1). Ловушки задачи, которые может предположить ИИ, и совпавшую ловушку она получает помеченным блоком данных, с описаниями из каталога (R02; R57). Отдаёт разбор рамку первой ошибки в долях вырезки или ничего и ловушку из блока или ничего — типом `tutor`, а не наблюдением; рамка — та же рамка на вырезке, что в наблюдении (R86);
    - подсказку: слова для ступени, которую выбрала программа. На устройство они уходят целиком, после проверки утечки, а не потоком; поток — только у чтения, ответ которого читает программа (R54);
    - оценку по рубрике — с первого среза, для модуля сочинений (R41), двумя вызовами: чтение сочинения в текст, затем оценка прочитанного текста по критериям рубрики, без картинки (R75). Чтение сочинения отдаёт «не прочитать» только у сочинения целиком, а как оно отдаёт слово, которого не прочитать, — Т-37 (R87); позже — голос.

    Чтение и разбор — два вызова: ключ и решение задачи модель видит только в разборе. Один вызов — только для модели, которая пройдёт порог R03 `tutor` на почерке взрослых добровольцев, новым решением (R67). Слова модели проверяет `api`: утечку, форму подсказки и правило отзыва, а пола ученика они не выдают (R70);
  - промпты платформы: по одному на возможность, у каждого — свой eval-набор, а у возможности, которая пишет слова ученику, в нём есть пункт о роде (R70) и пункт о безопасности (R54 tutor). У разбора хода решения и подсказки вызов один (раздел 4.1), и промпт у них тоже один на обе, а мерят его оба eval-набора (R59 tutor). Модель для возможности допускают, когда она проходит и его, и eval-наборы модулей, где эта возможность нужна (R02; раздел 4.6);

### 3.7. module-kit — формат модуля в коде

- **Делает** (R17):
  - читает модуль автора — YAML с ограничениями формата — и проверяет его: схему, граф без циклов, ссылки, навыки-опоры общей таксономии и зависимости паспорта (R50), задачи и их ссылки на навыки, полосы и картинки, зоны листа, имена файлов и сигнатуры медиафайлов (R51), проверки ячеек — ключ выбора среди его вариантов, варианты без повторов после нормализации, несократимый ключ дроби, выражение условия и оцениваемость навыков пункта (R56), каталоги ловушек и приёмов, значения ловушек и шаблоны ступеней в паспорте (R57), уроки — их навыки, задачи и картинки, участки листа, возрастные категории и порядок уроков без цикла (R58), шаблоны задач — имена, выражения, подстановки и все экземпляры, каждый — всеми правилами задачи (R60), и их решатели — на каждом экземпляре (R61), тексты автора, которые ученик видит до решения, — проверкой утечки (`task.no-leaks`, а в уроке — `lesson.no-leaks`). Отказ по правилу формата называет ID правила (R45). О картинке с прозрачными пикселями предупреждает, но не отказывает: у картинки модуля — непрозрачный светлый фон ([текст формата](../format/README.md), раздел 14; вторая поправка 2026-11-01 к R51);
  - читает версии формата модуля в окне — пока формат v0, только текущую, а с v1 текущую мажорную и предыдущую, причём v0 уходит с выходом v1, — и проверяет, собирает и исполняет модуль по версии, которую называет его паспорт. Модуль вне окна отклоняет с причиной (R44);
  - собирает пакет модуля — канонический вид с ярусом каждого навыка и числами каждого экземпляра шаблона, часть для устройства и опись ([текст формата](../format/README.md), раздел 25; R49; R62) — и индекс модулей: из индекса прошлого релиза, с записью каждой опубликованной версии по дайджесту пакета и с отметками о снятии ([текст формата](../format/README.md), раздел 26; R63); сравнивает новую версию с каждой опубликованной по правилам сравнения версий и сверяет упразднённые навыки (concepts 3; R49; R89);
  - шаблоны задач (concepts 9.3): перебирает сочетания параметров в порядке счётчика, считает производные числа и ограничение — выражения узкого подмножества Starlark — и строит экземпляры, не больше 10 000 сочетаний на шаблон. Экземпляр попытки — номер `below(count)` места `template`, ID задачи, `instance` её зерна (R59; R60). Векторы шаблонов — в `format/vectors/templates/` `spec`: его CI считает их второй реализацией, а CI `module-kit` проходит их все;
  - решатели шаблонов (concepts 9.3): исполняет программу `template.solver` в диалекте go.starlark.net из [текста формата](../format/README.md), раздел 24, и вызывает `solve` на каждом экземпляре по порядку, с числами его открытых полей, — не больше 100 000 000 шагов на все экземпляры шаблона вместе. Результаты встают в ключ, значения ловушек, решение и фразы-утечки, и каждый экземпляр с ними проходит все правила задачи. Результаты векторов шаблонов CI `module-kit` считает сам, а векторы `task.template-solver` проходит все (R61);
  - открытый вид — по пометкам `x-open` в схемах (R05; R45): отметка считается, только где её подсхема применяется и проходит, а векторы открытого вида `spec` проверяет и сам (R51);
  - виды проверки и нормализацию (concepts 9.2): в формате v0 — `number`, `fraction`, `choice`, `predicate` и `rubric`, а как каждый читает значение и выносит вердикт ячейки и пункта, говорит [текст формата](../format/README.md), раздел 15. Векторы вердикта — в `format/vectors/verdicts/` `spec`: его CI считает их второй реализацией, а CI `module-kit` проходит их все, вердикты условия тоже (R56);
  - сведение двух чтений и вердикт по наблюдению (concepts 9.1): наблюдения двух читателей он сводит в одно по проверке ячейки, а вердикт выносит по сведённому наблюдению целиком, с причинами «не прочитать» из наблюдения ([текст контрактов](../contracts/README.md), раздел 10; R68; R86). Векторы сведения и вердикта по наблюдению — в `contracts/vectors/observation/v1/` `spec`: его CI считает их второй реализацией, а CI `module-kit` проходит их все, вердикты условия тоже (поправка 2026-11-03 к R86). Тем же кодом он выносит eval-раннеру `tutor` вердикт по истине разметки образца — наблюдению верно читающего (R95);
  - допускает вердикт, только если ключ или условие дал автор, решатель или взрослый (concepts 9.4);
  - проверку утечки (concepts 10) — как говорит [текст формата](../format/README.md), раздел 20. Векторы утечки — в `format/vectors/leaks/` `spec`: его CI считает их второй реализацией, а CI `module-kit` проходит их все (R57). Её вызывает `api` на словах наставника, а проверка модуля — на текстах автора;
  - ловушку по неверному значению — сравнением со значениями ловушек ячейки, как с ключом (R57);
  - песочницу Starlark для решателей шаблонов и условий проверки, как в standalone. Условие проверки — выражение Starlark от целого `value`, и лимит его шагов — 1 000 000 в счёте go.starlark.net — часть формата: сработавший лимит или ошибка дают «без проверки» (R56). Бюджет решателя шаблона — тоже в формате (R61). Версию go.starlark.net и диалект, один на весь Starlark формата, с перечнем встроенных имён, называет формат 0.3, а до него `module-kit` закрепляет ту же версию (R88; R11 module-kit);
  - сверку пакета по цепочке дайджестов от индекса, который закрепил pull request `api`: индекс → опись → части → файлы (R62, R63). Подпись ставит общий workflow релиза из `.github`, а проверяет её рецепт `spec` `release-verify` там, где файл входит в NovaTrail, — библиотека подписей не проверяет (R77; поправка 2026-11-01 к R17);

Пакет каждой CI скачивает из релиза, который называет её запись в индексе новейшего релиза, и сверяет по цепочке дайджестов от проверенного индекса (R77). Одной новейшей хватило бы по индукции, но только пока каждая опубликованная версия сама прошла сравнение, поэтому `modules` берёт каждую — ценой архива каждой версии в pull request, который поднимает версию модуля. Дополнено 2026-11-02 (В14 и В15 `module-kit`; R89): правила сравнения, части версии и 0.y.z входят в текст формата с форматом 0.3 (RUN.md, T69). ### 3.8. learner-model и engine

- **learner-model** — оценка владения навыками по свидетельствам (concepts 11):
  - отправная точка — модель standalone: модель Раша с полом угадывания, обновление по Elo, осторожное «освоено» (standalone: SPEC 2, R187);
  - уровень — на модуль: у каждого модуля ученика свой, на шкале полос этого модуля, а поправка на тему из standalone — у навыка: оценка владения навыком — уровень модуля плюс поправка навыка. Модули связывает только навык-опора, а предмета в модели нет (R03 learner-model);
  - «освоено» — с полосой освоения: высшей из полос, где навыку учат, на которой осторожная оценка держит порог «освоено». Порог — константа `learner-model`; новая цель коридора `engine` — новая константа модели, и оба изменения проходят `sim` одним прогоном (поправка 2026-11-02 к R23);
  - забывание — удержание навыка: без практики оценка не меняется, а тает удержание, и с ним вероятность верного ответа; практика вразбивку растит стабильность навыка. «Освоено» время не снимает, а даёт срок повторения — когда осторожная вероятность с удержанием падает ниже того же порога. Закон и константы — одни на все модули (R04 learner-model). Удержание и вероятности с ним на текущее время и срок повторения модель считает при чтении и в кэш не пишет (R80; R08 api);
  - веса свидетельств — решено R06 learner-model: в шаг идёт первый вердикт каждого пункта, а помощь — ступень лестницы до него, приём по просьбе, уже виденное решение — только не даёт поставить «освоено»; каждый из N ответов одной попытки весит 1/(1 + (N − 1)/3); ключ от автора, решателя или взрослого весит 1, ключ или навыки от ИИ — 0;
  - проба, повтор задачи, «освоено» и ловушки (R06 learner-model): пробу модель не узнаёт и подъёма за неё не даёт — проба весит как любая задача, а вернуть навык с паузы по её верному ответу — правило `engine`. Повтор задачи, не шаблона, чьё решение уже уходило на устройство, — помощь: ответ идёт в оценку и стабильность, но «освоено» не ставит. «Освоено» ставится и снимается по свидетельствам: снимают его два свидетельства подряд, где верных у навыка меньше половины. У навыка — каждая ловушка, которую нашла программа, с числом свидетельств и временем последнего, а какие частые, выбирает читатель;
  - перенос по таблице соответствия старых ID навыков новым после мажорной версии модуля — `retired_skills`: свидетельства упразднённого навыка идут каждому навыку, который его заменил, — каждая замена получает долю упразднённого навыка целиком, а «освоено» замена выводит из перенесённых свидетельств заново (R49; R08 learner-model). Переносит `learner-model` по журналу и графам текущих версий модулей журнала, которые даёт `api` (R08 api). Навык модуля, которого нет ни в `skills`, ни в `retired_skills` текущей версии, не идёт ни одному навыку, без ошибки; навык-опора идёт как есть, если его знает словарь какой-нибудь версии формата в окне `api`, а иначе — ни одному; навыки ловушки — по тем же правилам. Пересчёт не открывает пакетов прежних версий (поправка 2026-11-02 к R80);
  - свидетельства попыток на версии, снятой с публикации из-за неверного ключа, `wrong_key`, больше не идут в модель: их отсекает `api`, прежде чем отдать журнал, и модель пересчитывается по журналу свидетельств (R63; R80);
  - навык-опора общей таксономии — по его ID, `core.<имя>`, а не по полному. Владеет ли им ученик, решает `learner-model` по навыкам, которые ему учат, в модулях ученика (R50), и решил R07 learner-model: «владеет» — «освоено» хотя бы у одного такого навыка в любом модуле, чей граф пришёл; «не владеет» — только по модулям движка, где навыки с вердиктом, которые ему учат, не освоены или ещё без свидетельств; иначе «неизвестно» — учить некому или учат только навыки без вердикта. Каждое состояние модель отдаёт с причиной и навыками, которые учат, и забывание владения не снимает (concepts 4). Считает она их при чтении, и входы чтения — кэш, графы, время, класс и ID модулей движка — подключённых и подходящих ученику (R07, R08 learner-model);
  - отправная точка — полоса сложности класса ученика, а трудность задачи — по её полосе и сложности от 1 до 5 внутри полосы; как далеко отстоят полосы и где начинает ученик вне полос, решает `learner-model` (R51), и решил R03 learner-model. Угадывание — у пункта, по его ячейкам: пункт верен, только когда верна каждая ячейка, и угадать его — угадать каждую. У выбора — 1/k по числу вариантов ячейки, у привязки `choice` или у самой проверки, у свободного ответа — около нуля; числа — `learner-model` (concepts 11; R03 learner-model);
  - сборка — решено R09 и R10 learner-model: одни биты на любой сборке одной версии, WebAssembly тоже, и сборка для устройства как есть; код — только стандартная библиотека Go, а exp и log — свои, в пакете `detmath`; CI проверяет это с первого кода.
- **engine** — выбор следующего урока или задачи (concepts 12): пререквизиты, коридор успеха (R23), повторение, коды причин, зерно. На время выбора модель отдаёт ему вероятность верного ответа пункта с удержанием — для коридора, — оценку навыка с неуверенностью и удержанием, а у освоенного навыка ещё «освоено» с полосой освоения, осторожную вероятность с удержанием и срок повторения, с пометкой «уже», если порог не держится и без забывания. «Пора повторить» — время выбора не раньше срока, а возвращать ли освоенный навык в ротацию, когда давать навык, чей срок настал, сколько повторений в день и как они делят очередь, — правило движка (поправка 2026-11-02 к R23; R04 learner-model). Шаблон задачи для движка — одна задача, какой бы экземпляр ни выпал: повтор шаблона даёт новое зерно попытки и, скорее всего, другие числа (R60). Пререквизит из другого модуля — навык-опора, и навык-опора «неизвестно» урока не держит (concepts 4). Порядок уроков задаёт граф навыков, а где он порядка не даёт, выбирает правило движка. В уроке, чьи навыки не все с вердиктом, движок ничего не добавляет и не пропускает (R58). Урок у ученика идёт прохождением урока (concepts 5), и на входе движка — прохождения профиля: открытые — с местами звеньев задачи, которые кончились, — и кончившиеся, с причиной и временем конца. Навыки урока открытого прохождения на прежнем пакете приходят переведёнными по `retired_skills` текущей версии тем же правилом, что свидетельства (поправка 2026-11-02 к R80). Внутри урока движок не зовётся: звенья он не переставляет, и вызов на каждом звене ничего бы не решал. `api` зовёт его, когда прохождение кончилось и когда ученик просит другое, а выбор может быть и продолжением открытого прохождения (R13 api; В15 `api`). Попытка задачи с рубрикой свидетельства не даёт (О-17), и из модели ученика движку не узнать, какие сочинения уже написаны. Поэтому `api` даёт ему и закрытые попытки задач с рубрикой — ID задачи, причину и время закрытия, без отметок критериев: по ним движок держит порядок автора у навыков с рубрикой и вне урока (concepts 4; В18 `api`). Список кодов причин — контракт в `spec` (R29); генератор случайности и вывод зёрен — из `spec`, общие с `module-kit` и `sim` (R27). Нужна ли движку случайность, решает он сам, и тогда у него своё зерно выбора и свои имена мест (R59).
- **Общее:**
  - чистые вычисления без ввода-вывода: время приходит снаружи, а зерно — только движку, если ему нужна случайность (R59): `learner-model` случайности не берёт (R09 learner-model);
  - типы графа — свои и простые, не из `module-kit`; так библиотеки можно собрать и для устройства (Т-10). Задаёт их `learner-model`, а `engine` берёт у него (R28). Граф — на модуль: полный ID модуля, полосы по порядку с ID и классами, навыки и `retired_skills`; у навыка — полный ID, оцениваемость, `teaches`, полосы, где ему учат, пререквизиты и ярус из `skill_tiers`. Полосы, где навыку учат, выводит функция `learner-model` из навыков и описаний задач модуля, которые дают `api` и `sim`. Описание задачи — одно для свидетельства и для задачи-кандидата из пула движка: ID задачи или шаблона, полоса местом и ID, сложность, основные и вспомогательные навыки, происхождение ключа и тегов, пункты с навыками и ячейками. Что ещё нужно правилам движка, — строкой его T04; уроки и пул — типы `engine` (R10 learner-model);
  - каждое изменение проходит стенд `sim` по критерию, записанному до первого прогона кандидата (R163 standalone; Т-16).
- **Не делают:** не читают пакеты модулей и базу: граф и свидетельства им передаёт `api`. Пул задач, уроки, прохождения уроков и закрытые попытки задач с рубрикой движку тоже задаёт `api`: при закрытом ИИ в них только задачи, которые проверяются без ИИ, и уроки только из таких задач, а о причине движок не знает (В14 `api`; concepts 12).
- **Репозитории и этап:** `learner-model` и `engine`, этап 1.
- **Решить при детализации:**
  - веса свидетельств — решено R06 learner-model;
  - правило повторения `engine`: когда давать навык, чей срок настал, сколько повторений в день и как они делят очередь с новыми навыками, закреплением и пробами (R04 learner-model);
  - владение навыком-опорой — решено R07 learner-model (concepts 4). У `engine` остаются: держать ли урок при «не владеет», когда свидетельств ещё нет, что с открытыми навыками, когда владение уходит, и что движок делает с циклом пререквизитов между модулями через навыки-опоры, где с обеих сторон «не владеет»: формат проверяет каждый модуль отдельно и такого цикла не видит (R50);
  - свидетельство — решено R08 learner-model (R06, R10 learner-model; поправка 2026-11-02 к R82): факты попытки, а не выводы модели, — всё, что называет R82, и всё, что читает модель. У попытки: задача, полоса задачи и полоса старта — местом и ID, — сложность, навыки, происхождение ключа и тегов, исход (concepts 11; поправки 2026-11-02 к R80), время последнего действия в целых секундах UTC, приём на шаге и по просьбе, число «объясни иначе», уходило ли решение на устройство. У пункта: навыки, вид проверки и число вариантов ячеек, отправлен ли он и причины отправок без вердикта, первый вердикт и число неверных ответов до отправки, которая его дала, вердикт в конце и число неверных ответов до первого «верно». У ловушки, которую нашла программа: её навыки и места пунктов. Звена урока свидетельство не несёт: весов оно не меняет. Журнал хранит `api` как есть (R80), а в кэше — только то, что задают журнал, графы и версия `learner-model`; отправную точку навыков без свидетельств и владение навыком-опорой модель считает при чтении (поправка 2026-11-02 к R80). Полосу старта `api` берёт у `BandByGrade`, а `Append` заменяет её полосой из состояния, если у модуля оно уже есть, и отдаёт свидетельство, которое `api` хранит. Дозапись — тот же шаг, что пересчёт, и даёт те же биты на любой сборке одной версии `learner-model`. Вид только прирастает: прежняя версия читает новый, пропуская незнакомое, так что откат `api` — только вперёд, прежним кодом (Т-19), — журнала не ломает. Байты — двоичный вид protobuf по схеме `.proto` `learner-model`; её пакет `novatrail.learnermodel.v1` — схема библиотеки, а не контракт `spec`. Операции — `BandByGrade`, `Append`, `Read` с `Readout.Task` и `Recompute`;
  - задача — не шаблон, — чьё решение уже уходило на устройство ученика: движок сразу снова её не даёт, а через сколько даёт — решает `engine` (R82);
  - сборка для устройства (Т-10) — у `learner-model` решено R09 и R10 learner-model; у `engine` — его T05, а предложение `learner-model` — та же дисциплина кода и пакет `detmath`;
  - уроки (R58; RUN.md, Д39): когда движок даёт урок, а когда задачу вне урока; как правило выбирает между уроками, которых граф не упорядочил, — у навыков без вердикта без модели ученика; добавляет ли он закрепление в урок, чьи навыки все с вердиктом, и кончает ли такой урок раньше; и что движок отдаёт, когда пул и уроки пусты: при закрытом ИИ в первом срезе это частый случай (В14 `api`; R29). Введёт детализация закрепление и досрочный конец — `api` будет звать движок на конце звена урока, чьи навыки все с вердиктом, а ответ — следующее звено, задача закрепления — попытка прохождения «после звена k» — или конец прохождения «досрочно»: место для них в прохождении есть (R13 api; В15 `api`). Типы входа об уроках и о попытках с рубрикой — свои и простые, как типы графа (R28). Дополнено 2026-11-02 (В14 `modules`; R07 modules): у первой пачки олимпиадной математики — урок на навык и полосу, и задачи урока — одной полосы. Полосы у урока нет, и порядок по графу ставит каждый урок `pigeonhole-basic` после каждого урока `combinatorics-enumeration`, и после урока 5–6 тоже ([текст формата](../format/README.md), раздел 21). Предложение `modules` к T01 `engine`: полоса урока — полоса его задач; движок даёт урок полосы ученика, а порядок читает среди уроков, которые даёт ему, так что урок другой полосы урока не держит. Урок с задачами разных полос и урок без задач — тоже правило движка. Поле `band` у урока `modules` отверг: оно повторяло бы полосы задач и могло бы с ними разойтись, а отдельного поля порядка у урока нет и так (R58).

### 3.9. sim — стенд виртуальных учеников

- **Делает:**
  - гоняет `learner-model` и `engine` на тысячах виртуальных учеников разных профилей;
  - держит критерий и полосы допуска;
  - служит гейтом CI (repositories 4; Т-16).
- **Данные:** пакеты модулей — закреплённые по версии данные. Читает их часть для сервера, `server.json`, по типам канонического вида из `spec` — `formatv0.CanonicalView` модуля Go `spec` (R72), — без `module-kit` (R62), в том же окне версий формата модуля, что и `module-kit` (R44). Зёрна виртуальных учеников выводит генератором из `spec`, а не своей схемой (R27). Функция `seeded` стенда standalone — частный случай вывода `spec`: место главного зерна с именами «эксперимент, единица, назначение», так что числа стенда сохраняются. Нормальное и показательное распределения в формат не входят, и за их переносимость отвечает `sim` (R59). Данных живых учеников нет.
- **Не делает:** не меняет алгоритмы, а только меряет их.
- **Образец:** `tools/learners` и `docs/learners.md` в standalone.
- **Репозиторий и этап:** `sim`, этап 1.
- **Решить при детализации:** профили виртуальных учеников, и среди них — забывание: у учеников дни, занятия и перерывы, а забывают они по законам, отличным от закона модели; есть и ученики, которые не забывают, и ученики, чей уровень падает после перерыва. Языковых модулей в первом срезе нет, и забывание стенд проверяет на двух математиках (R41; R04 learner-model); критерий и полосы допуска — до первого кандидата (R163 standalone), со своими мерами забывания. Какие это меры, решает T02 sim; предложение `learner-model` — калибровка вероятности по длине паузы, сколько ответов модель догоняет настоящее падение, доля повторений со временем, ложное «освоено» после перерыва, а на учениках, которые не забывают, модель с забыванием не хуже модели без него (architecture 3.2 learner-model); веса свидетельств: ученики со страницами рабочей тетради, где ответы зависят друг от друга по закону, отличному от скидки модели, — ошибка, которую ученик повторяет на всей странице, день, когда всё идёт хуже, — с подсказками, приёмом по просьбе и повторами задач. Какие это профили и меры, решают T01 и T02 sim; предложение `learner-model` — ложное и раннее «освоено» с одной-двух страниц, калибровка вероятности на страницах и на ответах с помощью, сдвиг оценки после повтора задачи (R06 learner-model); владение навыком-опорой: ученик с обеими математиками и мера ложного «владеет» (R07 learner-model); что включает гейт `sim` в CI `modules` — граф или всё, что стенд читает из пакета (В5 `modules`; Т-16).

Картинки задач standalone `modules` рисует при порте в файлы `media/` с описанием (R51).

Первая пачка — 27 задач трёх навыков, по три на навык и полосу, и 9 уроков, по уроку на навык и полосу, на английском, с `under_13` и `adult` в аудитории (R07 modules; R76).
- **CI `modules`:**
  - проверка `module-kit`;
  - `sim`, если изменился граф, — с первого тега `sim`: первые релизы `modules` выходят раньше стенда, и до его тега гейта графа нет (R76);
  - с этапа 2, когда появятся `tutor` и страница образцов, — eval-раннер `tutor` на eval-наборе модуля, отдельным ключом платформы только для eval (R24). Образец набора — каждый файл `eval/`, имя которого кончается на `.json`, с разметкой, на задачу своего модуля. Задачу раннер берёт из пакета pull request по ID, и дайджест её открытого вида должен совпасть с образцом. Образец, который не подходит, раннер отвергает, и прогон не проходит, так что pull request, который меняет открытый вид задачи, в нём же переделывает или убирает её образцы ([текст контрактов](../contracts/README.md), раздел 13; R95);
  - файл образца eval-набора — по протоколу eval, без ключа и на pull request с форка тоже: рецептом `spec` через подмодуль, `just -f spec/justfile sample-check`, тем же кодом, что проверяет примеры `spec`; у PNG вырезок — ни одного вспомогательного чанка ([текст контрактов](../contracts/README.md), раздел 11; R93; RUN.md, T72);
  - на релизе — пакеты и индекс модулей; подпись ставит общий workflow релиза. Индекс прошлого релиза общий релиз скачивает с его bundle и проверяет рецептом `spec` `release-verify` на раннере, до сборки нового, а рецепт `release-files` `modules` получает уже проверенный файл — входом `previous-file`, по architecture 3.3 .github (R77; поправки 2026-11-01 и 2026-11-02 к R63), а CI `modules` берёт CLI `module-kit` бинарником релиза с проверенной подписью, а не через `go install` (R77).
- **Доставка по этапам:**
  - этап 1 — пакеты и индекс в релизах `modules`;
  - этап 2 — конфигурация `api`, `modules.json`, закрепляет тег релиза `modules` и дайджест его индекса, а дайджесты пакетов называет индекс (R63; R07 api). Pull request, который её меняет, — якорь доверия, а его CI проверяет подпись индекса рецептом `release-verify` (R77): с ним до `api` доходят и отметки о снятии, и снятые версии `api` не исполняет для новых попыток (R63). Файлы части для устройства раздаёт `api`;
  - с этапа 2 релиз `modules` по точному тегу берёт и CI `canvas`: сборка страницы образцов кладёт в неё задачи и медиа через CLI `module-kit` (R25; раздел 3.2), а отметки о снятии читает в индексе новейшего релиза (R63). До первого содержания `modules` задачи замера сборка берёт из релиза `tutor` (поправка 2026-10-21 к R25);
  - образ `api` держит все версии закреплённого индекса в окне формата, снятые тоже, и сборке база не нужна (R07 api). Для повтора вердикта старые версии берутся из релизов `modules`. Пакет, чья версия формата модуля ушла из окна, `api` уже не исполнит, и попытку на нём закрывает «без проверки» (R07 api), а повтор её вердикта идёт вне `api`, тем релизом `module-kit`, который её проверял (R44);
  - потом — хранилище с CDN, а индекс пишет сервис реестра (Т-17).
- **Две части пакета и опись** ([текст формата](../format/README.md), раздел 25; R62; Т-15 закрыт):
  - часть для сервера — канонический вид модуля: всё содержание, в том числе ключи, решения и ловушки, с ярусом каждого навыка и числами каждого экземпляра шаблона;
  - часть для устройства — `LICENSE`, `NOTICE` и медиафайлы, а когда в формате будут виджеты, — их бандлы; ключей и текстов модуля в ней нет;
  - опись пакета называет модуль и обе части по дайджестам, а дайджест пакета — дайджест описи (concepts 15);
  - eval-набор в пакет не входит: образцы eval-раннер берёт из папки модуля в CI `modules`.
- **Индекс модулей** ([текст формата](../format/README.md), раздел 26; R63; Т-30 закрыт):
  - файл `module-index.json` в каждом релизе `modules`, один на все модули. Он накопительный: называет каждую опубликованную версию каждого модуля по дайджесту пакета, с тегом релиза, в файлах которого лежит пакет, и с навыками-опорами, которым версия учит;
  - релиз собирает его из индекса прошлого релиза и своих пакетов, внутри общего релиза: после номера и до публикации. Записи не удаляются и не меняются;
  - версию снимает следующий релиз: его индекс помечает её запись `withdrawn` с причиной — `wrong_key`, `answer_leak` или `unsuitable_content`. Снятая версия остаётся только для повтора вердикта;
  - снятую новейшую мажорную исправляет версия выше неё по semver, и, когда исправление готово, — в том же релизе, что её снимает. Снятие исправления не ждёт (вторая поправка 2026-11-02 к R63);
  - имя файла пакета в релизе выводится из записи индекса — без перебора файлов релиза и без REST API: так пакет находят сборка образа `api`, CI `canvas` и повтор вердикта (вторая поправка 2026-11-02 к R63);
  - пакет лежит в релизе архивом `sha256-<hex>.tar.gz` — `package_digest` записи, где `:` заменено на `-`. Внутри — пакет файлами, в корне архива, без верхней папки, и ничего, кроме них и их папок. Адрес — `https://github.com/altnovatrail/modules/releases/download/<release>/sha256-<hex>.tar.gz`, публичный, без токена. Релиз несёт архивы только тех версий, которые публикует сам (В4 `modules`; R03 modules);
  - прежние версии модуля для сравнения версий CI `modules` берёт из релизов, которые называют записи индекса новейшего релиза: пакет каждой опубликованной версии, снятые тоже, по цепочке дайджестов от проверенного индекса (В12 `modules`; поправка 2026-11-02 к R03 modules; раздел 3.7).
- **Репозиторий и этап:** `modules`, этап 1.
- **Решить при детализации:** решено всё (R03–R05 и R07 modules; поправка 2026-11-02 к R03 modules): раскладка модулей, имя файла пакета и откуда CI берёт прежние версии, путь образцов добровольцев в eval-набор (R04 modules; П-16), порт задач standalone (R05 modules) и первая пачка олимпиадной математики (R07 modules). Лицензия — Apache-2.0, и у кода, и у содержания (R20), а содержание standalone входит под MIT, с его уведомлением в `NOTICE` модуля (R12; R05 modules).

  - К поставщикам ИИ он ходит через `tutor` и становится его вторым потребителем (раздел 3.6).
- **widget-template**, этап 4: образец виджета, сторона протокола для автора и среда разработки виджета.
- **Канал MCP** (О-15): второй транспорт `api` или отдельный сервис — решить вместе с О-15.
- **Оплата**, этап 3: часть `api` и внешний поставщик.
- **Учителя и школы**, этап 5: роли и права в `api`.

## 4. Потоки

### 4.1. Проверка рукописного ответа

`tutor` — библиотека в процессе `api`. На схеме он нарисован отдельно, чтобы была видна граница R03. Чтение и разбор — два вызова (R67). Чтение рукописи — ещё и два читателя одного поставщика (R68): на схеме они — одна стрелка «запрос».

```mermaid
sequenceDiagram
    participant A as app
    participant P as api
    participant T as tutor
    participant M as поставщик ИИ
    A->>P: отправка — вырезка работы
    P->>T: чтение рукописи — работа, открытый вид, возрастная категория, путь к ИИ
    T->>T: допуск — путь разрешён, модель из допущенных
    T->>M: запрос без идентификаторов
    M-->>T: ответ модели
    T-->>P: наблюдения двух читателей
    Note over P: module-kit — одно наблюдение из двух и вердикт по ключу и происхождению
    P-->>A: «Пока нет. Прочитано: 6»
    A->>P: слова наставника — работа ещё раз и номер неверного ответа
    Note over P: лестница подсказок — какая ступень
    P->>T: разбор хода решения и подсказка — работа, ключ и решение задачи, ловушка, ступень, прошлые вопросы задачи, стиль подачи, язык объяснений, возрастная категория, путь к ИИ
    T->>T: допуск
    T->>M: запрос без идентификаторов
    M-->>T: ответ модели
    T-->>P: вопрос наставника
    Note over P: проверка утечки и формы, иначе — запасной текст
    P-->>A: вопрос и пометки на слое наставника
    Note over A,P: по итогу попытки — свидетельство в learner-model. Вне урока и в конце прохождения урока engine выбирает следующий урок или задачу с кодом причины, и выбор приходит в том же ответе, а в уроке идёт следующее звено
```

- Чтение и разбор — разные возможности ИИ: разбор видит ключ, чтение — нет (раздел 3.6; R67). Наблюдения двух читателей `module-kit` сводит в одно, и ячейка, которую они прочли по-разному, в нём неоднозначна: вердикт — «не прочитать» (R68; R86).
- Стиль подачи на схеме и ниже — только то из него, что меняет слова: озвучка в вызов ИИ не идёт, как и режим (privacy 4; О-23).
- Читают работу только по действию ученика — по «Проверить»; «шаг готов» в формате v0 работу не читает (поправка 2026-11-02 к R69), а на паузе ИИ не зовут (R69). Вердикт `module-kit` выносит по наблюдению целиком, а не по строкам, пока они приходят (поправка 2026-10-28 к R54).
- Свидетельство — итог попытки, а не отдельной отправки (concepts 11).
- Сбой ИИ или исчерпанная квота — нейтральная фраза, а не «пока нет» (R04).
- Картинку сервер не хранит, поэтому для разбора приложение присылает работу ещё раз (R09).
- **Подсказка по просьбе** работу не шлёт и чтения не зовёт (R69). До первого неверного ответа она даёт «что известно и что найти» и приём задачи, после — ещё раз слова текущей ступени, без ИИ. «Объясни иначе» — тот же вызов подсказки, что на схеме, но без работы: ключ и решение задачи, ловушка ячейки ступени, ступень, прошлые вопросы задачи, стиль подачи, язык объяснений, возрастная категория и путь к ИИ, — один раз на ступень. Прошлые вопросы той же задачи получает каждый вызов слов попытки, чтобы их не повторять (R82; privacy 4).
- На рабочей тетради работа — вырезки заполненных окошек с их местами, без текста пункта, а место в наблюдении — ячейка ответа (поправки 2026-10-27 и 2026-10-28 к R53).
- **Задача с рубрикой** — тоже два вызова, но другие: чтение сочинения и оценка по рубрике (R75). Вердикта у пункта с рубрикой нет: вместо `module-kit` и лестницы подсказок — оценка и отзыв.
  1. `app` шлёт работу — вырезку листа для рукописи.
  2. `api` зовёт чтение сочинения — с тем же, что получает чтение рукописи: работой, открытым видом, возрастной категорией и путём к ИИ. Лист читает один читатель (вторая поправка 2026-11-01 к R68), без рубрики, и `api` получает наблюдение — текст, как он написан.
  3. `api` зовёт оценку по рубрике — с прочитанным текстом, условием задачи как темой, критериями рубрики по порядку, стилем подачи, языком объяснений, возрастной категорией и путём к ИИ. Картинки, ключа и решения задачи в ней нет. Модель отдаёт по каждому критерию обоснование и выполнен ли он, и один отзыв на всё сочинение.
  4. Отзыв проходит проверку утечки и правило отзыва (R70) и уходит на устройство.

  Сочинение, которое не прочитать, до оценки не доходит, и ученик видит просьбу переписать лист, как при «не прочитать» (concepts 9.1). Вердикта у пункта с рубрикой нет: отправка кончается «не прочитать», и записывается только её время (R87; R14 и R15 api). Попытка открыта для переписки, а кончает её «Готово» ученика.

### 4.2. Ответ вводом, выбором, правкой или состоянием виджета

ИИ здесь не нужен: `app` присылает значение, а `module-kit` сравнивает его с ключом или условием (concepts 9.2). Так же работают режим без ИИ (О-5) и платформа совсем без поставщика ИИ — например, self-hosting без договоров с поставщиками.

### 4.3. Свой ключ

- Ключ бывает только у профиля владельца категории `adult` (R04 api; О-4). На устройстве он лежит, только если так решил владелец ключа на этом устройстве, а иначе — в памяти вкладки, пока открыт его профиль; шифрования в браузере нет, и `app` говорит это прямо (R84; R08 app).
- Ключ и его поставщик приходят с каждым запросом профиля владельца, который зовёт ИИ: с работой на чтение, со словами ступени и с «объясни иначе», который работы не шлёт (раздел 4.1). Поставщика без ключа `app` называет в начале попытки. В `api` и `tutor` ключ живёт только в памяти запроса — не в базе и не в журналах (privacy 5.2); с профилем другой категории `api` его не принимает.
- При подключении `api` проверяет ключ через `tutor` запросом без содержания ученика; поставщиков, открытых своему ключу, называет функция допуска. Отказ поставщика по лимиту — «лимит исчерпан» с причиной (R55 tutor), отказ ключа — свой исход, и ни один не переводит вызов на ИИ платформы без действия владельца ключа (privacy 5.1, 5.2).
- Функция допуска пропускает его, только если это разрешают условия поставщика для возрастной категории ученика (privacy 5.3), — по ячейке таблицы допуска: у своего ключа открыта только категория `adult`, без фактов развёртывания (R96). Рекомендация О-4 — свой ключ только для 18+.
- Модель — только из допущенных: свой ключ не открывает модель без eval (R07).

### 4.4. От автора к ученику

Модуль → CI `modules` (`module-kit`, `sim`; с этапа 2 — eval) → пакет → `api` закрепляет его за попыткой → `app` получает открытый вид. Подробно — repositories 4.

### 4.5. Выгрузка и удаление

- **Выгрузку собирает `app`.**
  - Штрихи, артефакты и задачи с бумаги лежат на устройстве, а свою часть отдаёт `api`.
  - Работы с других устройств выгружаются с них.
  - Формат выгрузки — открытый, в `spec` (R09).
  - Своего ключа в выгрузке нет: выгрузка — данные учеников, а ключ — секрет владельца ключа (R84; privacy 5.2).
- **Удаление подтверждается свежим входом.**
  - `api` удаляет данные из базы и удаляет аккаунт у сервиса входа.
  - Другие устройства стирают свои данные при следующем обращении к `api`, пока живёт их ID token — около часа после удаления: тот отвечает, что аккаунта больше нет. Отзыв токенов прежних ID token не гасит — «existing ID tokens may remain active until their natural expiration (one hour)» (Admin SDK Firebase для Go v4.22.0, `auth/user_mgt.go`, прочитано `api` 2026-11-02; architecture 4 api). Позже сервис входа на устройстве выходит сам, и данные стираются при следующем входе на нём: новый вход даёт новый UID без аккаунта `api`, и «нет допуска», когда в реестре устройства есть аккаунт, `app` читает как вход другого аккаунта (RUN.md, Д89). Устройство, которое не откроют, держит их, пока их не сотрёт браузер или взрослый (R20, R21 api; architecture 3.10 api).
- **Честные сроки** называют резервные копии базы, сервис входа, журналы платформы и поставщиков ИИ и другие устройства (privacy 1).
- **Что остаётся от согласия** после удаления — П-14.

### 4.6. Смена модели ИИ и смена алгоритма

- Новую модель для возможности ИИ допускают, когда она проходит eval-набор возможности и eval-наборы всех опубликованных модулей с этой возможностью. Ложные тревоги считаются по вердикту, через `module-kit` (repositories 4): по отчёту раннера — сообщению протокола eval без содержания работ, — и для допуска годится только отчёт с вердиктами `module-kit` ([текст контрактов](../contracts/README.md), раздел 14; R95; поправка 2026-11-03 к R07). У оценки по рубрике вердикта нет, и её мерят ложные тревоги на выполненных критериях, а вторая мера — согласие с людьми и каппа по критерию (R71). Модель на устройстве допускают так же (R66). Eval-наборы модулей лежат в git `modules`, вне пакета и файлов релиза (R62; R03 modules), и встречаются с раннером в CI `modules`: модель допущена, когда слит pull request `modules`, который переходит на тег `tutor` с ней в списке допущенных и прогоняет eval-наборы всех модулей. Порядок — repositories 4 (В9 `modules`; R04 modules).
- eval у поставщика сверх OpenAI и Anthropic идёт по его условиям: Together, Cerebras и Fireworks запрещают benchmarking, а SambaNova — публиковать его результаты без её согласия (R65; privacy 5.3).
- Изменение `learner-model` или `engine` проходит `sim` по критерию, записанному заранее (repositories 4).

## 6. Интерфейс: пакеты и iframe-песочница

- **Микрофронтенды.** Автор хотел «микрофронтенды в своих репозиториях». В NovaTrail это пакеты интерфейса — `canvas` и `skill-map`: части интерфейса в своих репозиториях, со своими релизами.
  - `app` собирает их по точной версии в одно приложение (R16).
  - Во время разработки `app` подключает рабочие копии пакетов, а в релиз идут только точные версии.
- **Почему без загрузки во время работы** (R16):
  - При точных версиях `app` всё равно закрепил бы версию каждой части, поэтому независимой выкладки не получилось бы.
  - Цена при этом осталась бы: расхождение версий, дубли фреймворка, более сложные CSP, кэш и офлайн.
- **Как пакеты стыкуются с приложением** — веб-компонентами, с типами данных из релизов `spec` (R36): у пакетов несколько потребителей, а фреймворк каждого решает его репозиторий. Выходят пакеты в npm, в области `@altnovatrail` (R37).
- **Чужой код** — только виджеты модулей, и только в iframe-песочнице (раздел 3.4).
  - Shadow DOM — не средство защиты: он изолирует стили и дерево DOM, но не код (раздел 8).
  - Поэтому модуль не встраивается в страницу веб-компонентом через `<script src>`, как предлагал Gemini (R16).
- **Второй потребитель пакета** — например, сайт или карточка канала MCP — получает вторую сборку того же пакета. Так в standalone собран виджет чата: одна HTML-страница в iframe хоста.
- **Иконки** — один набор каталога Iconify, Material Symbols, у всех пакетов интерфейса (R78).
  - Каждый пакет берёт пакет набора `@iconify-json/material-symbols` сам, по точной версии, и вшивает при сборке только свои иконки: `canvas` и `skill-map` — из `devDependencies`, а `app` — из `dependencies` (поправка 2026-11-02 к R39). Во время работы к API Iconify нет ни одного запроса.
  - Имя иконки — `material-symbols:<база>-outline-rounded`. Выбранный вариант выбора и включённый режим — та же иконка с заливкой, `material-symbols:<база>-rounded`.
  - Одно значение — одна иконка, и одна иконка — одно значение. Таблица ниже называет кнопки строки `canvas` — их видит экран задачи `app` — и значения, которые нужны больше чем одному пакету. Новое значение встаёт в неё строкой «в реестр spec». Иконку для значения, которое есть только у него, пакет выбирает из набора сам, но не из тех, что в таблице; если она уже стоит у другого пакета на другом значении, оба значения встают в таблицу.
  - У иконки нет своего имени для программы чтения с экрана: имя кнопки — её подпись (R36).

  | Значение | Кнопки | База имени | Заливка | Справа налево |

  | ластик | `canvas`: «Ластик» | `ink-eraser` | когда выбран | как есть |
  | отменить | `canvas`: «Отменить» | `undo` | — | отражается |

- **Доступность** — один стандарт у всех пакетов интерфейса: WCAG 2.2 уровня AA и сверх него 2.5.5 — цели не меньше 44 × 44 CSS px — и 2.3.3 — движение по `prefers-reduced-motion` (R90). Подпись рядом с иконкой видна всегда. Чему пакет пока не отвечает, он объявляет сам, а `app` называет это на своей странице «Доступность». Свой контейнер прокрутки — только с `tabindex="0"`, ролью `region` и именем (ошибка WebKit 277290).
- **Переводы** — правила общие, а таблицы у каждого пакета свои (R91):
  - язык подписей — атрибут `lang` на самом элементе; язык в таблице ищется усечением тега, RFC 4647, раздел 3.4, а не найденный — английский, со своим `lang`;
  - подстановки по имени вместо склейки строк, формы числа — категории CLDR, `other` всегда;
  - строки без рода ученика и без первого лица ИИ;
  - каждый пакет несёт каждый язык интерфейса — `en` и `ru` (R92);
  - названия навыков-опор — английские, с `lang="en"` (R50).

## 7. Чего в архитектуре нет

- Своих кластеров, очередей и шины событий (R11).
- Сервиса на каждую область: без очередей это распределённый монолит из синхронных цепочек (R15).
- Картинок и звука, которые уходят на проверку, и своих ключей на сервере (R09; R84).
- Канала реального времени в первом срезе (Т-25).
- Рассылок и уведомлений: контакты взрослого нужны только для входа и подписки (privacy 1).
- Консоли оператора как отдельного приложения: в первом срезе это команды и задания `api`.
