## 1. Principles

- **The boundary between the program and AI runs along the code.**
  - Everything that calls a model is in `tutor`. A model that would read the work on the device is its code too: its weights, eval and admission are with `tutor`, and the verdict is with `module-kit`. In the first slice there is no such reading.
  - The verdict is given by `module-kit`, the learner model is computed by `learner-model`, the next lesson or task is chosen by `engine`. None of these libraries calls a model.
  - A task from the learner's paper is the one exception: it has no key, and its verdict is a model's, given by the Check of `tutor`, one call that also gives the place of a mistake and the hints. The program holds the Check's answer to its schema, turns it into the verdicts of the attempt and checks its words for the model's hidden answer. Such a verdict moves nothing but the learner's own view of that task: the task is in no module, and neither `learner-model` nor `engine` sees it.
  - CI of `api` checks the full list of dependencies: the SDKs of AI providers get into the build only through `tutor`.
- **Of the platform's parts, only `api` stores learners' data on the server.**
  - `tutor` stores nothing. The types of its requests have no fields for the learner's and account's identifiers, so AI sees the work but does not know whose it is.
  - Outside the platform, part of the data is held by the sign-in service, the AI providers and, from stage 3, payment.
- **A separate process only where it is needed.** In the first slice there is one service, `api`; `tutor`, `module-kit`, `learner-model` and `engine` are libraries in its process. `tutor` will become a service when it gets a second consumer.
- **The key of an unsolved task is only on the server.** The app gets the task's open view. The open view is built by `module-kit` by the marks `x-open` in the format's schemas: a field without the mark is closed, so a new field of the format is closed until it is explicitly opened. Of a task from paper, the model's hidden solution and answer, which its Check gives, stay on the server too.
- **Reproducibility**:
  - an attempt stores the digest of its module package, the module format version, the version of `module-kit` and the seed. A package digest is the digest of its inventory, and it depends only on the module's files and the format version of its manifest, as [the format's text](../format/README.md) sets it. A module is checked and executed by the format version that its manifest names, and a new format version does not change its verdict until the author moves the module to it;
  - an engine choice stores what its replay by the evidence log needs: the versions of `engine` and `learner-model`; the package digests, and which of them are the engine's modules, connected and suitable for the learner; the seed, empty, since the engine takes no randomness, as the version of `engine` in the record shows; the reason code; the release of `modules`, by whose index the withdrawal marks are known; the number of the last evidence it was made by; the time of the choice, for which the model computed retention and the review date; the grade by which the model computed the starting point of modules without evidence; whether the pool was limited to tasks without AI; the skill chosen on the skill map; the age category of the profile, by which `api` selected the pool and the lessons. The category changes at the yearly refinement and at a change of country, and the connections at any time, and the digests also name the modules of the log, which only `learner-model` gets: so the record keeps them. The summary of issues, the lesson runs and closed attempts with a rubric the engine saw, and the last attempt and its outcome the replay derives from the records of choices and attempts before the time of the choice: once written, they do not change;
  - a verdict is repeated by the stored observation, a choice by the evidence log; both without AI. A verdict of a task from paper is a model's and is not repeated: the same work may get another at another Check, and once the attempt ends `api` keeps nothing of it;
  - the generator of randomness and the derivation of seeds are set by `spec`, with test vectors: PCG, as in Go's `math/rand/v2`, and places of randomness, as at standalone's simulator, by [the format's text](../format/README.md). An instance of a task template is repeated by the attempt's package and seed: it is chosen by one number of the place `template`, the task's ID, `instance`, by the same text.
- **Our own parts of the interface are assembled at build time, others' code runs only in an iframe sandbox**.
- **No clusters, queues or event bus of our own**. The parts talk by synchronous requests by the contracts from `spec`: `app` with `api` by Connect, with unary calls, and the code of the contracts comes from the releases of `spec`. Background work is Cloud Run jobs on a schedule, as in canvas-api.
- **Logs without direct identifiers, IP addresses and content**.
  - Cloud Run itself writes request logs ([Cloud Run: logging](https://docs.cloud.google.com/run/docs/logging); sources 4.1) with the standard field `httpRequest`, and it has `remoteIp`, the client's IP address ([LogEntry](https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/LogEntry), `HttpRequest`; sources 4.2). canvas-api recorded the same about the logs of Cloud Run and Firebase Hosting ([`docs/privacy.md` of canvas-api@0901af0](https://github.com/mathtrail/canvas-api/blob/0901af0/docs/privacy.md)).
  - COPPA counts an IP address among persistent identifiers, that is, among personal information (16 CFR 312.2; sources 3.1).
  - So the request logs are excluded in Cloud Logging by the filter of each sink: Google accepts the record and discards it before storage ([Cloud Run: logging](https://docs.cloud.google.com/run/docs/logging), "the logs exclusion feature from Cloud Logging"; sources 4.1), — and the logs' region is `us-east4`, as for the whole platform.
  - The hosting of `app`, Firebase Hosting, and the sign-in service, Firebase Auth, store IP addresses in their logs themselves, for several months and several weeks (sources 4.4); `infra` does not turn on the export of the Hosting logs to Cloud Logging.

## 3. Components

Each component has a card: what it does and does not do, its data and links, its repository and stage. The items "To decide when detailed" are what the work in its repository begins with. A question that concerns several repositories is in the registers of `spec`, and the card refers to it.

A repository's detailing may name items beyond its card or skip one of them; the card follows it by a row «в реестр spec» of the repository's table 3 once the decision is made, not in advance.

### 3.2. canvas — canvases

- **Does:**
  - canvas kinds; in the first slice, the handwriting sheet and the workbook. A workbook is a page of 1000 × 1400 units, like a sheet, without a grid: the item lines with boxes are put on the template layer by its layout, by the task and its own table of widths, not by the device's font. A task from paper is solved on a sheet whose grid the learner turns by the bar's last button — dots as it comes, lines, blank, squares, round —, with the task's crop over it as tracing paper in place of the template: the learner moves it by its grip "Move the task", hides and shows it by the button atop the tools, and writes on it as on the sheet;
  - layers: the template, the widget, the demo, the learner's work, the tutor's layer. On the demo layer is the demo of a lesson's worked example: its parts open one at a time and hide all at once, and a picture in a sheet area stands at the size of the area. From format 0.4 an example stands on a workbook too: the example's lines by the page layout, and a part of the demo fills a box with its value. On the sheet and on the workbook of an example the learner does not write. ### 3.4. Module widgets

- **What it is:** interactive components of a module on the canvas, the module author's code.
- **How they work**:
  - in an iframe sandbox without `allow-same-origin`, on a separate registrable domain. Together with `allow-scripts` it would let a page of the same origin remove the sandbox ([HTML Standard](https://html.spec.whatwg.org/multipage/iframe-embed-object.html#attr-iframe-sandbox), the attribute `sandbox`);
  - CSP does not let the widget's code go to the network: only the bundle itself is loaded;
  - the widget talks with the app only by the protocol from `spec`;
  - the bundle is signed and pinned by hash in the module package, and the package is pinned to the attempt;
  - official widgets run in the same iframe sandbox as others';
  - to children, only widgets that passed review (О-9).
- **Stage 4.** In the first slice there are no widgets: none of its three modules needs them. There is no binding of a slot to the widget's state in format v0: it will come with the widget protocol, as a minor version. The template for authors is `widget-template`.
- **To decide when detailed**, in epic E5 of the plan (`run/EPICS.md`):
  - the widget protocol. What it has to decide beyond the rules above is by an analysis outside the repository (sources 8.4). The app's side of the protocol is the widget host of `canvas`, which `app` builds into itself; "`app`" below is it (В22 `canvas`):
    - the channel. The HTML Standard says to check the sender of a message by origin, and a widget without `allow-same-origin` has an opaque origin, serialized as "null". A comparison of `event.source` with the iframe's window does not tell documents apart: an iframe has one window, and at a navigation only the document behind it changes. So the analysis advises a `MessageChannel` port: `app` passes it to the widget once, at the first load of the iframe, and then listens only to it, and a document to which the widget navigated later never got this port ([HTML Standard](https://html.spec.whatwg.org/multipage/web-messaging.html#authors): cross-document messaging, its ports and the WindowProxy). How `app` notices such a navigation is decided by the protocol;
    - the version of the state in each message of the widget: `app` knows to which version the verdict and the tutor's words belong, and a mark on a part of the widget that has changed since then it does not draw, like a mark of a sheet whose strokes were erased;
    - the parts of the widget for marks: the tutor's layer lies over the widget, so the widget names its parts and their boxes, and a mark holds on to a part, as on a sheet it holds on to strokes;
    - the widget reports the learner's state and events, not a verdict. Whether it is correct is decided by `module-kit`, and by which state — the one the widget reported or the one repeated on the server by the seed and the events — is decided by Т-24. The widget's seed is its own, not the attempt's seed: the attempt's seed does not go to the device, and how the widget gets its own is decided by the widget protocol;
    - the tests of conformance to the protocol are in `spec`, beside the protocol, like the verdict vectors, and in its releases by the same path as the format's files: as a release file of their own and in the Go module. They are for both sides of the protocol: both the widget and the widget host of `canvas` pass them, each in its own CI (В22 `canvas`). Tests of one side hold only that side: a host that diverged from the test one would break widgets that passed the tests, and nobody would notice. The test host is in the development environment of `widget-template`; whether `canvas` itself will be it, epic E5 will decide together with `widget-template`, and the condition for the host does not change from that. A widget conforms to the protocol if it passes the tests, and the library for authors is a convenience, not a condition;
  - whether the state the widget reports can be trusted (Т-24);
  - the withdrawal of a version of a widget that turned out harmful. A withdrawn version of a module withdraws the bundles of its widgets too: the device no longer loads them, and the reason "dangerous bundle" will come as a minor version of the format together with the widget protocol.

### 3.5. api — the platform's service

- **Does:**
  - sign-in: checks the token of the sign-in service;
  - learners: the pseudonym, age category, country, presentation style, default solving mode and hint mode, interface language, grade — if the module asks for it; consent records; permissions;
  - attempts: stores the digest of the module package, the module format version, the version of `module-kit` and the seed. The attempt's seed `api` takes from a cryptographically secure source when the attempt begins, and does not give it to the device: from the state of a place of randomness its seed can be seen, and the generator is not cryptographically secure; it gives the open view. It gives a task to a learner only if they are in one of its age categories, `age_categories`, and a lesson only if both the lesson and each of its tasks suit the learner;
  - the lesson: its open view — without skills and age categories — and the lesson's tasks by its segments. A lesson's task is the same attempt as outside a lesson. `api` leads a lesson by a lesson run — a row per profile and lesson, on the package where the lesson began, one for all devices, with its own ID. The place in the lesson and the state of the demo are held by `app`. The usual end of a lesson is "lesson passed" from `app`, which `api` accepts when all task segments have ended; `api` itself ends a run "unchecked", "not suitable" and "abandoned" — 30 days without actions, — and an early end the rule of `engine` does not give in the first slice; what the contract carries to a lesson is `LearningService`: open a lesson by the choice, a run by its ID and "lesson passed", and the answer that ends a segment's attempt names the next segment;
  - the task template: the attempt's instance is by its seed, from the package, and Starlark is not run on an attempt: the key of each instance `module-kit` computed and checked at the module's check. To the app, the instance's open view, without the field `template`. The package carries the numbers of each instance, and `api` takes the number `below(count)` and substitutes its numbers by the code of `module-kit`, without executing expressions;
  - the check: a submission → `tutor` reads the work, with two readers for handwriting → `module-kit` joins their observations into one and gives by it a verdict for each answer slot and for the item. The operator chooses the reading mode, `API_READING_MODE`: `pair`, by default, or `single`, one reader, Haiku 5.5 · `medium`, whose observation gets the verdict without the join, for every learner, and `api` accepts it at every rung; in `single` the admission is the pair's entry with Haiku as its reader, and a rung that admits no entry refuses the reading as an admission refuses it, not the configuration at the start. `api` stores the joined observation, or the one reader's, and beside it the tapped choice: by them the verdict is repeated without AI. There are no writing parts and other readings in the observation. The slot checks' predicates `api` computes by the code of `module-kit` in the request's flow and at once, no more than the process has CPUs (`GOMAXPROCS`): the clock of `module-kit`, 1 s per predicate, runs by wall time, and "unchecked" must not depend on the load. A cancellation of the request's `context` is an error without a verdict: `api` does not record it as "unchecked", and the submission stays without a verdict. A task with a rubric has an assessment by the rubric in `tutor` and feedback by the rubric, without a verdict: a submission ends with feedback, "unreadable" or "unchecked", and the attempt is closed by the learner's "Done". Of such an attempt the server stores how each submission ended, and for feedback, the criteria's marks and the source of the words, without the text of the essay and the words of the feedback. The slot check is in the server part: the app gets neither it nor its kind;
  - tasks from paper, for every profile, each call of AI through `tutor` and admitted by the table of `admission/`:
    - finding the tasks: the photo of a page, in the request's memory, to `tutor` in one request, and the task frames, each with the frame of its instruction above it when the page prints one, with no text, and the turn that put the page upright back to the device; with the learner's request about the page, the request and the frames on the page now go with it, `api` checks their bounds, and keeps none of them;
    - the Check: each `SubmitWork` of a work with something written is one call of `task_checking`, with the task's crop as printed, the work — the crop with the strokes on it and the sheet's strokes —, the crop of its instruction when there is one, the language of the tutor's words that the request names, the learner's age category and the attempt's history, which `api` gathers from what it keeps: the verdicts of the Checks before, the rungs shown and the tutor's words before; the strokes go only as drawn in the work, with no stroke's points and no writing history. The verdict of each task the frame holds — one, or up to 20 — is the model's: `api` holds the answer to its schema, gives the attempt an item for each task, at the box read, solved when every task is correct and one wrong answer counted by a Check with any task not yet, an error before the answer among them, a slot with no answer and no error "So far correct", which counts none, and checks the tutor's words and each rung of the ladder for the hidden answer of a task not yet answered correctly, a number the statement prints or the learner wrote being no leak, leaving out the words and giving a rung's fallback text for what names it. A Check that read nothing of a solution in any slot is "Couldn't check this one", `CAUSE_NO_KEY`, and an empty sheet `app` does not send; an `unreadable` slot asks to rewrite. ### 3.6. tutor — the tutor: reading and words

- **Does:**
  - AI capabilities:
    - the reading of handwriting and the reading of text: the work turns into an observation, the model does not see the key. The reading gives a slot's value as it is written: its check kind in `module-kit` normalizes it. Handwriting is read by two readers of one provider, by two calls, and a slot that they read differently is "unreadable"; in the mode `single`, which the deployment chooses, by one reader, Haiku 5.5 · `medium`, the second of the admitted pair. So it is for slots whose check gives a verdict, and a sheet under a rubric is read by one reader. `tutor` gives the observations of both readers, or in `single` of the one, or the AI call outcome, and `module-kit` joins two. The reader knows nothing about the slot check, neither the kind nor the options of a choice. The writing parts and other readings stay with it: by them it decides what to give, as the [contracts text](../contracts/README.md) sets it;
    - the analysis of the course of solution: the model also sees the key and the task's solution and looks for the first error in the learner's solution. The task's traps that AI may suggest, and the matched trap, it gets as a marked block of data, with the descriptions from the catalog. The analysis gives the box of the first error in fractions of the crop or nothing, and a trap from the block or nothing, as a type of `tutor`, not as an observation; the box is the same crop box as in the observation;
    - a hint: the words for the rung that the program chose. They go to the device whole, after the leak check, not as a stream; a stream is only for reading, whose answer a program reads;
    - the correct answer words: the praise of a step and the question which technique helped, by a call of their own, with the work, the key and the task's solution and its techniques, and with a form rule of their own beside the hint's form check. They have a capability of their own, `correct_answer_words`, with its own eval set: a model that was measured on the hint is not admitted on these words. `api` makes this call at `GetCorrectAnswerWords`;
    - the assessment by a rubric, from the first slice, for the essay module, by two calls: the reading of the essay into text, then the assessment of the text read by the rubric's criteria, without the picture. The reading of an essay gives "unreadable" only for the essay as a whole, and how it gives a word that cannot be read is Т-37; later, voice;
    - for a task from paper, three of their own: finding the tasks on the photo of a whole page, turned upright first by the model's word of which way up it is, whose answer is their task frames, each with the frame of its instruction above it when the page prints one, with no text, and the turn, each sum or equation that says by itself what to do a task of its own — with the learner's request about the page, the request and the frames on it now as data, and none of its frames repeating one the learner drew; reading the statement on a task's crop for Recognise, as printed, "□" for each box an answer goes in, never a formula or a key; and the Check, `task_checking`, one call with its instructions, the schema of its answer, its request, the read of its answer and its version, as each call of `tutor` has them. The Check gets Image 1, the task's crop as printed, Image 2, the work, each stroke drawn in its style, in colour, Image 3, the crop of the instruction, when there is one, their sizes, the language of the tutor's words, the age category and the attempt's history, all as data, never instructions, and the strokes only as drawn in the work, with no stroke's points and no writing history. It gives for each answer slot, 1 to 20 in the order of the page, its verdict — `correct`, `incorrect`, `unreadable` or `no_answer` —, its confidence, what it read with its box, its assumptions, its errors, each a box on Image 2 with the place in words, its kind and an explanation, and its own solution and answer, hidden; and for the frame the tutor's words, `tutor_text`, and a ladder of 2 or 3 hints, from a question to a pointer at the place. There is no call that solves the task and no reading of the work apart: the verdict, the place of the mistake and the hints come in the one call. Each of the three asks up to three models of one provider in turn — Haiku 5.5 · `high`, Sonnet 5.5 · `medium`, Opus 5.5 · `medium` —, the next only when the one before did not do by the program's rule of its call; the Check's goes on at a failure, an answer off its schema, a `low` confidence or an `unreadable` slot. The answers are of the contract `novatrail.paper.v1`, which the [contracts text](../contracts/README.md) sets. The leak check of the Check holds `tutor_text` and each rung against the hidden answer of a task not yet answered correctly, a number the statement prints or the learner wrote being no leak: words that name it do not do, and a rung that names it gives way to its rung's fallback text. "Explain differently" of a task from paper is a prompt of its own under `hint` and `solution_analysis`, by the same cascade, with the task's crop as printed, the rung, the hidden solution and answer and the questions before, without the work; a question of the learner's own is the same prompt, on its version 3, with the question and the conversation before it as data, answered as a tutor does — what the task asks or what a word means, a question that leads on —, never with the answer or a step, no nearer than the current rung. ### 3.8. learner-model and engine

- **learner-model** — the estimate of knowing skills by evidence:
  - the starting point is the model of standalone: the Rasch model with a guessing floor, an Elo update, a cautious "mastered" ([standalone@42b4408](https://github.com/mathtrail/mathtrail-standalone/tree/42b4408));
  - the level is per module: each of the learner's modules has its own, on the scale of that module's bands, and the correction for the topic from standalone is the skill's: the estimate of knowing a skill is the module's level plus the skill's correction. Modules are linked only by an anchor skill, and the model has no subject;
  - "mastered" comes with a mastery band: the highest of the bands where the skill is taught at which the cautious estimate holds the threshold "mastered". The threshold is a constant of `learner-model`; a new target of the corridor of `engine` is a new constant of the model, and both changes pass `sim` in one run;
  - forgetting is the skill's retention: without practice the estimate does not change, but the retention fades, and with it the probability of a correct answer; spaced practice grows the skill's stability. The module's level forgets too, at the next evidence: after a pause of the module of at least 14 days since the last practice of any of its skills, the weight of the module's answers, if above 20, falls to 20 before the step, so the answers after the break move the level more, and every skill of the module is less certain — "mastered" comes later and the review date nearer; a reading changes nothing. Time does not take "mastered" away but gives a review date — when the cautious probability with retention falls below the same threshold. The law and the constants are one for all modules. The retention and the probabilities with it at the current time and the review date the model computes at reading and does not write to the cache;
  - the weights of evidence: into the step goes the first verdict of each item, and help — a rung of the ladder before it, a technique on request, an already seen solution — only keeps "mastered" from being set; a leading question on request, which evidence from format 0.4 carries as its own field, is help, like a technique on request, and the check kind `time` is a free answer, without guessing; each of N answers of one attempt weighs 1/(1 + (N − 1)/3); a key from the author, a solver or an adult weighs 1, a key or skills from AI weigh 0. An answer by a second way in a slot with a number — by the keyboard or by digit buttons — weighs as an answer in handwriting, and a submission whose verdict the learner saw the model always counts (О-25);
  - a probe, a repeat of a task, "mastered" and traps: the model does not recognize a probe and gives no rise for it — a probe weighs as any task, and returning a skill from a pause by its correct answer is a rule of `engine`. A repeat of a task, not a template, whose solution has already gone to the device is help: the answer goes into the estimate and the stability, but does not set "mastered". "Mastered" is set and removed by evidence: it is removed by two pieces of evidence in a row where the skill has fewer than half correct. The skill holds each trap the program found, with the number of pieces of evidence and the time of the last one, and which are frequent the reader chooses;
  - the transfer by the table of correspondence of old skill IDs to new ones after a major version of a module — `retired_skills`: the evidence of a retired skill goes to each skill that replaced it — each replacement gets the retired skill's share whole, and "mastered" the replacement derives anew from the transferred evidence. `learner-model` transfers by the log and the graphs of the current versions of the log's modules, which `api` gives. A module's skill that is in neither `skills` nor `retired_skills` of the current version goes to no skill, without an error; an anchor skill goes as it is if the dictionary of some format version in the window of `api` knows it, and otherwise to none; the skills of a trap by the same rules. The recomputation opens no packages of earlier versions;
  - the evidence of attempts on a version withdrawn because of a wrong key, `wrong_key`, no longer goes into the model: `api` cuts it off before giving the log, and the model is recomputed by the evidence log;
  - an anchor skill of the shared taxonomy is by its ID, `core.<name>`, not by the full one. Whether the learner knows it `learner-model` decides by the skills that teach it, in the learner's modules: "knows" is "mastered" on at least one such skill in any module whose graph came; "does not know" only by the engine's modules where the skills with a verdict that teach it are not mastered or still without evidence; otherwise "unknown" — nobody to teach it, or only skills without a verdict teach it. Each state the model gives with a reason and the skills that teach it, and forgetting does not remove knowing. It computes them at reading, and the inputs of reading are the cache, the graphs, the time, the grade and the IDs of the engine's modules — connected and suitable for the learner;
  - the rules in place of calibration: the starting point is a band below the difficulty band of the learner's grade — a band's width below on the module's scale, below the lowest band too —; the adult's correction, a fact of the evidence log that `api` appends, moves the module's level a band easier or harder in one step; three failures in a row of the module — a failure as `learner-model` defines it by its evidence — lower the level by a band. `sim` checks them in a short run;
  - the hardness of a task is by its band and its difficulty from 1 to 5 within the band; how far apart the bands are and where a learner outside the bands starts `learner-model` decides. Guessing is the item's, by its slots: an item is correct only when each slot is correct, and to guess it is to guess each one. For a choice it is 1/k by the number of the slot's options, of the binding `choice` or of the check itself, for a free answer about zero; the numbers are `learner-model`'s;
  - the build: the same bits on any build of one version, WebAssembly too, and the build for the device as it is; the code is only Go's standard library, and exp and log are its own, in the package `detmath`; CI checks this.
- **engine** — the choice of the next lesson or task: prerequisites, the success corridor, repetition, reason codes. The detailing is decided, in `engine`'s own decisions: the core of the rule — the rule of standalone on the module's skills, with the corridor, the prerequisites and the queue; several modules in turn, anchor skills, a skill from the map and what the engine does not read; lessons; repetition; reason codes, the rule without randomness and the repeat of a choice; the types; the build for the device. For the time of the choice the model gives it the probability of a correct answer of an item with retention — for the corridor —, the estimate of a skill with uncertainty and retention, and for a mastered skill also "mastered" with the mastery band, the cautious probability with retention and the review date, with the mark "already" if the threshold does not hold even without forgetting. "Time to review" is a time of choice no earlier than the date, and whether to return a mastered skill into the rotation, when to give a skill whose date has come, how many repetitions a day and how they share the queue is the engine's rule. A task template for the engine is one task, whichever instance comes up: a repeat of a template gives a new seed of the attempt and, most likely, other numbers. A prerequisite from another module is an anchor skill, and an anchor skill "unknown" does not hold a lesson back. The order of lessons is set by the skill graph, and where it gives no order, the engine's rule chooses. In a lesson whose skills are not all with a verdict, the engine adds nothing and skips nothing. A lesson goes for the learner as a lesson run, and at the engine's input are the profile's runs: the lesson, its skills, the end reason — an open one has none — and the time of the end; the places of finished segments the rule does not read. The skills of the lesson of an open run on an earlier package come translated by `retired_skills` of the current version by the same rule as evidence. Inside a lesson the engine is not called: it does not reorder segments, and a call at each segment would decide nothing. `api` calls it when a run has ended and when the learner asks for something else, and the choice may also be the continuation of an open run. An attempt at a task with a rubric gives no evidence (О-17), and from the learner model the engine cannot learn which essays have already been written. So `api` also gives it the attempts at tasks with a rubric closed by "Done" — the task's ID and the time of closing, without the marks of criteria: by them the engine keeps the author's order for skills with a rubric outside a lesson too, and reads no other close reasons. The time of practice from the model is not the time of issue: a task issued without evidence gives no practice. So `api` also gives the engine a summary of issues from the records of choices and attempts that it keeps anyway: for a skill, the time of the last issue, and the issue of a lesson is the issue of each of its skills, and, if the last closed attempt of the skill was a probe or a repetition, its result on the skill — as facts: how many items where the skill is primary got a first verdict, how many of them "correct" and whether the solution was shown; for a module, the number of choices, of a task and of a lesson separately; for a task, when its solution last went to the device. By it the rule keeps the queue, the course of a probe and of repetition, the return of a skill from a pause by a correct answer of a probe or of a repetition and the pause before a task with a seen solution, and "failure" and "correct" by the facts it computes itself, not `api`; the types of the summary are its own and simple, like the types of the graph. In the trial series of a module the engine does not work through an error and gives no probes, and the series is a state of the model: `Read` gives for a module whether its trial series has ended and whether its last evidence was still in it — the second is needed so that the error of the series' last answer is not worked through. The rule "open" of the skill map the engine takes as an input: for a skill that the map opened and the learner chose, it gives a lesson or a task on it if the pool and the lessons hold at least one, and the reachability for "My subjects" may be its own. The list of reason codes is a contract in `spec`, the enumeration `ReasonCode` of the contracts' text, [contracts/README.md](../contracts/README.md): a branch of the rule that is not in it `engine` asks for with a row «в реестр spec». - **Does:**
  - runs `learner-model` and `engine` on thousands of virtual learners of different populations;
  - holds the criteria and the tolerance bands;
  - serves as the CI gate of the libraries and of `modules`.
- **Data:** module packages — data pinned by version. It reads their server part, `server.json`, by the types of the canonical view from `spec` — `formatv0.CanonicalView` of the Go module `spec` —, without `module-kit`, in the same window of module format versions as `module-kit`. The seeds of virtual learners it derives with the generator from `spec`, not by a scheme of its own. The function `seeded` of the simulator of standalone is a particular case of the derivation of `spec`: the place of the main seed with the names "experiment, unit, assignment", so the simulator's numbers are kept. The normal and the exponential distributions are not part of the format, and `sim` is responsible for their portability. The gate's bands lie in `sim`, in the gate file: it names the commits of `learner-model` and `engine`, the release of `modules` — by the tag and the digest of the index — and the packages by digests. Synthetic packages `sim` has only for its code and tests, not for judging candidates. There are no data of live learners.
- **Does not:** does not change the algorithms, only measures them.
- **Limit:** an anchor skill that no module of the learner teaches the simulator's truth counts as known, and knowledge of an anchor outside the platform enters it only as a shift of the skills that teach it (the population `A-unpractised`, the measure `M9` of `sim`). A learner of olympiad maths alone who does not know the anchor the simulator does not see. This does not hinder the rule of `engine` — it has no check of the anchor —, but a candidate with a check of the anchor or with proposing a module needs, before judging, a population of olympiad maths alone where the learner does not know the anchor, and a measure that reads it: the criterion comes before the first candidate.
- **Example:** `tools/learners` and `docs/learners.md` in standalone.
- **Repository and stage:** `sim`, stage 1. A release of `sim` comes out by itself after green CI on `main`.
- **To decide when detailed:** everything is decided: populations of virtual learners with a calendar and forgetting; two criteria, of the model and of the engine, on a common basis — with measures of forgetting, of the weights of evidence and of a false "knows", the gate's bands and pinned seeds; the gate in CI of `modules` — everything the simulator reads from a package; how CI of the libraries takes the simulator, and the order of releases. What `sim` decides next is in its `docs/architecture.md`.
  - The third criterion is the fairness of the learner model by the grade: virtual learners of the same skill and different grades come to the same estimate and the same kind of task within a number of attempts written down before the first run. `sim` holds it by an evaluation of the base, whose result is in [dpia.md](dpia.md), and by the constraint `fair` of the criteria of the model and of the engine, which holds a candidate no worse than the base. The base does not hold it, and the judgement waits for 100 children.
  - Until then a short run checks the three rules in place of calibration against the base by a criterion written before it: grade 5's `M11.same` by the 50th answer above 0.5525, no cell worse by `fair`, the guard lowering the level of at most 5 % of the learners under grade 3. Its numbers, with the one check of `fair` that failed and was accepted, are in [dpia.md](dpia.md).

## 4. Flows

### 4.1. Checking a handwritten answer

`tutor` is a library in the process of `api`. On the diagram it is drawn separately, so that the boundary between the program and AI is visible. Reading and the analysis are two calls. Reading handwriting is also two readers of one provider: on the diagram they are one arrow "request". In the reading mode `single` there is one reader, and nothing to join.

```mermaid
sequenceDiagram
    participant A as app
    participant P as api
    participant T as tutor
    participant M as AI provider
    A->>P: submission — a crop of the work
    P->>T: reading handwriting — the work, the open view, the age category, the AI route
    T->>T: admission — the route is allowed, the model is among the admitted
    T->>M: request without identifiers
    M-->>T: the model's answer
    T-->>P: the observations of two readers, or of one in single
    Note over P: module-kit — one observation from two, or the one in single, and the verdict by the key and the provenance
    P-->>A: "Not yet. Read: 6"
    A->>P: with the tutor's panel open, or when it opens — the tutor's words: the work once more and the number of the incorrect answer
    Note over P: hint ladder — which rung
    P->>T: analysis of the course of solution and a hint — the work, the key and the solution of the task, the trap, the rung, the task's past questions, the presentation style, the explanation language, the age category, the AI route
    T->>T: admission
    T->>M: request without identifiers
    M-->>T: the model's answer
    T-->>P: the tutor's question
    Note over P: leak check and form check, otherwise the fallback text
    P-->>A: the question and the marks on the tutor's layer
    Note over A,P: at the end of the attempt — evidence into learner-model. Outside a lesson and at the end of a lesson run engine chooses the next lesson or task and writes the reason code, and the choice — without the code — comes in the same answer, and in a lesson the next segment goes
```

- Reading and the analysis are different AI capabilities: the analysis sees the key, reading does not. The observations of two readers `module-kit` joins into one, and a slot that they read differently is ambiguous in it: the verdict is "unreadable". In the reading mode `single` the one reader's observation gets the verdict as it is.
- The presentation style on the diagram and below is only what of it changes the words: voicing does not go into the AI call, nor does the solving mode (О-23).
- The work is read only on the learner's action — on "Check"; "Step done" in format v0 does not read the work, and on a pause AI is not called. `module-kit` gives the verdict by the observation as a whole, not by lines while they come.
- Evidence is the result of an attempt, not of a separate submission.
- A failure of AI or an exhausted quota is a neutral phrase, not "not yet".
- The server does not store the picture, so for the analysis the application sends the work once more. It asks for the tutor's words only while the tutor's panel is open, or once when it opens; with the panel closed, "Check" ends at the verdict.
- **A hint on request** sends no work and does not call reading. Hint with the tutor's panel closed opens it, and the opening asks the rung's words of the last wrong answer, when they were not asked, as on the diagram, with the work. Before the first incorrect answer it gives "givens and unknown" and the task's technique, after it the words of the current rung once more, without AI. "Explain differently" is the same call of a hint as on the diagram, but without the work: the key and the solution of the task, the trap of the rung's slot, the rung, the task's past questions, the presentation style, the explanation language, the age category and the AI route — once per rung. The past questions of the same task each call of the attempt's words gets, so as not to repeat them.
- On a workbook the work is the crops of the filled boxes with their places, without the item's text, and the place in the observation is the answer slot.
- **A task with a rubric** is also two calls, but other ones: reading an essay and the assessment by the rubric. An item with a rubric has no verdict: instead of `module-kit` and the hint ladder, an assessment and feedback.
  1. `app` sends the work — a crop of the handwriting sheet.
  2. `api` calls reading the essay — with the same as reading handwriting gets: the work, the open view, the age category and the AI route. The sheet is read by one reader, without the rubric, and `api` gets the observation — the text, as it is written.
  3. `api` calls the assessment by the rubric — with the read text, the task statement as the topic, the rubric's criteria in order, the presentation style, the explanation language, the age category and the AI route. There is no picture, key or solution of the task in it. The model gives for each criterion a justification and whether it is met, and one feedback on the whole essay.
  4. The feedback passes the leak check and the rule of feedback and goes to the device.

  An essay that is unreadable does not reach the assessment, and the learner sees a request to rewrite the sheet, as at "unreadable". An item with a rubric has no verdict: the submission ends with "unreadable", and only its time is recorded. The attempt is open for rewriting, and the learner's "Done" ends it.

### 4.2. An answer by typing, choice, edit or widget state

AI is not needed here: `app` sends the value, and `module-kit` compares it with the key or the predicate. The mode without AI (О-5) works the same way, and so does the platform with no AI provider at all — for example, self-hosting without agreements with providers.

### 4.3. Own key

- A key exists only for the owner profile of the category `adult` (О-4). On the device it lies only if the key's owner decided so on this device, and otherwise in the tab's memory while their profile is open; there is no encryption in the browser, and `app` says so plainly.
- The key and its provider come with each request of the owner profile that calls AI: with the work for reading, with the rung's words, with the correct answer words and with "explain differently", which sends no work. A provider without a key `app` names at the start of the attempt, and with each request whose answer or refusal may give an engine choice, so that the choice goes by the same route. In `api` and `tutor` the key lives only in the request's memory — not in the database and not in the logs; with a profile of another category `api` does not accept it.
- On connection `api` checks the key through `tutor` with a request without the learner's content, `CheckOwnKey`: the key is accepted, wrong, the key has no rights, or the provider is closed for the profile; the providers open to an own key `ListOwnKeyProviders` names, by what `tutor` admits for at least one kind of call of `api`. A provider's refusal by a limit is "limit reached" with a cause, a refusal of the key is an outcome of its own, and neither moves the call to platform AI without an action of the key's owner.
- The admission function lets it through only if the provider's terms allow it for the learner's age category — by the cell of the admission table: for an own key only the category `adult` is open, without deployment facts. The recommendation of О-4 is an own key only for 18+.
- The model is only from the admitted ones: an own key does not open a model without eval.

### 4.4. From the author to the learner

Module → CI of `modules` (`module-kit`, `sim`; from stage 2 eval) → package → `api` pins it to the attempt → `app` gets the open view. In detail — the flows between repositories in [repositories.md](repositories.md).

### 4.5. Export and deletion

- **The export is assembled by `app`.**
  - Strokes, artifacts and tasks from paper lie on the device, and `api` gives its own part, which holds the open attempts of tasks from paper — their counts and rungs — without the model's hidden solution and answer.
  - Works from other devices are exported from them, but for the stored works: while the storage of works is on, `api` keeps the last work each device put, its part of the export names them, and `app` writes each into the export beside that part, by `GetWork`, one at a time, so that no answer is larger than a work.
  - The export format is open, in `spec`: [the part `export/`](../export/README.md) — a ZIP of JSON files, where the manifest, the device's files, the stored works and the pages from paper are written by `app`, and `api.zip` is the part of `api`, byte for byte; the evidence log, the state and the observation are the JSON of their protobuf messages with their own `.proto`.
  - There is no own key in the export: the export is learners' data, and the key is a secret of the key's owner.
- **Deletion is confirmed by a fresh sign-in.**
  - `api` deletes the data from the database and deletes the account at the sign-in service. Without a fresh sign-in the deletion gets the refusal "fresh sign-in needed", `CAUSE_FRESH_SIGN_IN_NEEDED`.
  - The connection "Sign in with Google" in the owner's Google account is not removed by the deletion at the sign-in service. After the answer "deleted" `app` removes it: it revokes the Google access token of the fresh sign-in at `https://oauth2.googleapis.com/revoke`, and `api` does not get this token ([OAuth 2.0 for Client-side Web Applications](https://developers.google.com/identity/protocols/oauth2/javascript-implicit-flow), "Token revocation"; sources 4.6; measurements 4.1). While `app` has no deletion screen, the connection stays, and the owner removes it themselves on the page of Google's connected apps.
  - A deleted profile other devices erase by the account's list of profiles, which `app` reads at start.
  - Other devices erase their data at the next call to `api` while their ID token lives — about an hour after the deletion: it answers that the account is gone, `CAUSE_ACCOUNT_GONE`. The revocation of tokens does not put out earlier ID tokens — "existing ID tokens may remain active until their natural expiration (one hour)" (the Firebase Admin SDK for Go v4.22.0, `auth/user_mgt.go`, read by `api` 2026-11-02; sources 11.1 api). Later the sign-in service on the device signs out by itself, and the data are erased at the next sign-in on it: a new sign-in gives a new UID without an account of `api`, and "no access", when the device's register holds an account, `app` reads as the sign-in of another account. A device that is not opened keeps them until the browser or an adult erases them.
- **Honest retention periods** name the backups of the database, the sign-in service, the logs of the platform and of AI providers, and other devices.
- **What remains of consent** after deletion is the minimal record of a child consent — its ID, the date, the method of verification and the date of deletion, without the account and profile IDs —, kept for 5 years.

### 4.6. A change of AI model and a change of algorithm

- A new model for an AI capability is admitted when it passes the capability eval set and the eval sets of all the published modules with this capability. False alarms are counted by the verdict, through `module-kit`: by the runner's report — a message of the eval protocol without the content of works —, and for admission only a report with the verdicts of `module-kit` will do. The assessment by a rubric has no verdict, and it is measured by false alarms on met criteria, and the second measure is agreement with people and kappa per criterion. A model on the device is admitted the same way. The eval sets of modules lie in the git of `modules`, outside the package and the release files, and meet the runner in CI of `modules`: a model is admitted when the pull request of `modules` is merged that moves to the tag of `tutor` with it in the list of admitted models and runs the eval sets of all modules.
- eval at a provider beyond OpenAI and Anthropic goes by its terms: Together, Cerebras and Fireworks forbid benchmarking, and SambaNova forbids publishing its results without its consent.
- A change of `learner-model` or `engine` passes `sim` by a criterion written down in advance.
- A change of the rule of `engine` does not rewrite the reason codes saved with the choices and does not change the meaning of a code. A new branch of the rule comes with a new code, and the code of a branch that the engine removed stays in the list and is no longer given.

## 6. Interface: packages and the iframe sandbox

- **Micro-frontends.** Micro-frontends in their own repositories: in NovaTrail these are the UI packages — `canvas` and `skill-map`: parts of the interface in their own repositories, with their own releases.
  - `app` builds them by exact version into one application.
  - During development `app` connects working copies of the packages, and only exact versions go into a release.
- **Why without loading at run time**:
  - With exact versions `app` would pin the version of each part anyway, so there would be no independent deployment.
  - The cost would remain: diverging versions, duplicates of the framework, more complex CSP, cache and offline.
- **How the packages join the application** — as web components, with data types from the releases of `spec`: the packages have several consumers, and the framework of each is decided by its repository. The packages come out in npm, in the scope `@altnovatrail`.
- **Foreign code** is only the widgets of modules, and only in the iframe sandbox.
  - Shadow DOM is not a means of protection: it isolates styles and the DOM tree, but not code: "Shadow DOM is not a security feature" ([Shadow DOM v1](https://web.dev/articles/shadowdom-v1)).
  - So a module is not embedded into the page as a web component through `<script src>`.
- **The second consumer of a package** — for example, the site or a card of the MCP channel — gets a second build of the same package. So the chat widget of standalone is built: one HTML page in an iframe of the host.

## 7. What the architecture does not have

- Its own clusters, queues and event bus.
- A service per area: without queues that is a distributed monolith of synchronous chains.
