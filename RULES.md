# RULES.md — the rules every NovaTrail repository shares

Every NovaTrail repository's CLAUDE.md imports this file: spec's as `@RULES.md`, every other repository's as `@spec/RULES.md`, from spec checked out as a git submodule at an exact tag (R21 spec). A repository's role and its own documents are in its CLAUDE.md; what follows holds in all of them. The file changes only in spec, and a repository takes the new version with a new tag of spec.

The file is read in every repository, so whatever it cites from spec carries the suffix "spec": "repositories 8 spec", "R14 spec". spec's documents are under `docs/` in spec itself and under `spec/docs/` everywhere else.

## The bar

Every document meets one bar and is written for whoever reads it. The documents under `docs/`, but for the epic archives `docs/plan/`, are read by a session of Claude Code, not by the author, and so are the rules and tables of the work plan — RUN.md, `run/` and spec's COORDINATION.md —, which are terse, for the session (R154 spec): the session acts on them for an engineer, a module author or a lawyer. Write them so that it can do so without asking what you meant, and shape them to be read in parts, a section or an entry at a time (R143 spec). The bar is concrete:

- one term means one thing in every document; the vocabulary is concepts 15 spec;
- every claim about the outside world — a provider's terms, a price, a law — cites its source and the date it was read. The source, its date and its quote are a record of the repository's `docs/sources.md`, and the claim cites the record by its number, as a section: `sources 2.3`;
- a gap is never filled silently: it becomes an open question with options and a recommendation;
- a decision says why, and what was rejected;
- each fact has one home, and a text holds the current state, not its history: a document names the file where a value is set — `deploy/*.json`, the submodule, `package.json`, a Dockerfile's `ARG` —, not the value, and keeps no chronicle; the history is git, the releases and the archives (R160 spec);
- a code comment says only what the code cannot — why, a constraint, a pitfall, an exported API's contract —, never the code again, its history, its task or a section of a document; where its reason is a decision, it ends with its number, `(R25)`.

The texts people read are written for them: spec's legal texts in `legal/`, the normative texts for authors (R42 spec), README files, the bodies of the plan's tasks, the order of spec's COORDINATION.md, the epic archives and the reports to the author.

## The project

NovaTrail is a universal open platform for adaptive learning, interactive lessons and AI tutoring, for any subject and any age (decision R01 spec). A subject comes as a module — data, not code and not instructions to a model (R02 spec). A program decides every verdict; the AI only reads the learner's work and words the tutor's replies (R03 spec). NovaTrail succeeds MathTrail, olympiad maths for grades 1–6, which is frozen; its ideas, code and content are carried over selectively (R01 spec). The platform is split into repositories from day one, and `spec` is their shared source of truth (R10 spec); which repositories there are and what they are called is R18 spec.

The name is written **NovaTrail**, with a capital T. Identifiers stay lowercase: the organization `altnovatrail`, `novatrail-spec`, `NOVATRAIL_DEVCONTAINER` (R13 spec).

## How we work

- The author runs tasks one at a time: «Выполни задачу Txx из RUN.md». Do only that task, by the rules in RUN.md. An epic across repositories runs itself: «Сделай эпик E…» in spec's orchestrator container (R156 spec).
- One task is one session (R143 spec): its planning and execution run in one session of Claude Code, an inbox triage in the session it was started in, and the next task in a new session or after `/clear`. The hook `UserPromptSubmit` of `.claude/settings.json`, spec's `tools/session/`, stops a prompt that starts another task in the same session — «Выполни задачу T…», «планируй T…» — and names `/clear`; the inbox triage names no task and goes on. What the next task needs from this one lives in files, not in the session.
- Before proposing a change, read the repository's decision log, `docs/decisions.md`, and the sections the change touches. Do not re-propose what a decision rejected without new evidence. If a decision has to change, ask the author and record the change.
- A decision is its text in force, with its why and what it rejected. A change rewrites the entry in its place, and every entry it changes too; git keeps the old text, and the commit says why. An entry that still has dated amendments is rewritten whole when a task touches it (R160 spec).
- A new number — R, О-, П-, Т- — is the next one still free when it is written down, not when the work began. Each register's opening names the next free number; keep it current.
- Facts about AI providers, laws and prices come from the primary source, quoted with the date read, into a record of `docs/sources.md`. What could not be verified is not stated as fact: it becomes an open question. The results of a measurement — what was measured, how, on what, and the numbers — go to `docs/measurements.md`, which the first measurement starts, and the documents that describe how things are built cite them: `docs/architecture.md` holds neither (R143 spec).
- A run longer than a few minutes — tests, a simulation, a build, CI — goes to the background, and the session waits for its notification or a Monitor of its condition, never a `sleep` loop in the foreground: each call that polls rereads the whole context (R143 spec). The orchestrator's executor waits in the foreground instead, by its contract (R159 spec).
- Plan for the fewest pull requests and rounds of CI (R159 spec): tasks of one repository in a row, none waiting on another, share one branch and one pull request; a pull request of its own is only where a dependency needs it. What can run locally runs first: CI confirms, it does not find. The bookkeeping goes in before the first round, a fix after its local check: one round a pull request.
- Code comes with its tests: a pull request that adds or changes code adds or changes the tests of its automated suite too. Where a repository's coverage goes to Codecov, the merge waits for `codecov/patch`, at least 90% of the changed lines covered (R48 spec).
- Do not commit: the author commits after review, unless the author's word, as «доведи до мержа», says otherwise. «Сделай эпик E…» says it for each task it runs: its executor opens the pull request, the orchestrator merges it on green checks (R156 spec); a task across repositories pushes each change and ships on the author's «да» (R166 spec).
- Finish with a short report to the author in Russian: what was done, which files, what is still open.

## Citations

- A document is cited by its name and section: "product 7", "architecture 3.5". A repository cites its own documents and decisions without a suffix. Any other repository cites spec's with the suffix "spec" — "architecture 3.8 spec", "R18 spec" — and another NovaTrail repository's decisions with that repository's name, "R03 api".
- The open questions О-, П- and Т- are spec's registers — product 13, privacy 9 and repositories 8 spec — so their numbers need no suffix anywhere. A repository other than spec keeps no register of open questions: what it has still to decide is listed in its `docs/architecture.md`.
- An example of a citation, rather than a citation, is written in code — `R03`, `architecture 2` — so that the documents check does not take it for one (R32 spec).
- MathTrail's decisions are cited as "R37 canvas-api" and "R213 standalone", or in a list as "canvas-api: R37, R38"; each log is numbered independently. MathTrail's repositories, `github.com/mathtrail/canvas-api` and `github.com/mathtrail/mathtrail-standalone`, are not checked out in any NovaTrail repository. When a task needs them, clone them into a temporary directory, never into the repository.

## Across repositories

`spec` is what every repository shares: the vocabulary, the formats and contracts, the platform's documents and decisions, and these rules. Outside spec it is read-only, at the tag the repository pins, and a session changes neither spec nor any other repository from where it works, but for the orchestrator's merges (R156 spec) and a task across repositories (R166 spec).

- Some things belong in spec: a question that concerns more than one repository, a decision that settles one of spec's open questions, and any change to a component's card in architecture 3 spec. Outside spec, the session writes such a thing into table 3 of its plan — `run/QUESTIONS.md` (R153 spec) —, its question opening with the mark «В реестр spec», with its options and recommendation, and names it in its report. Nobody carries it: on the author's word, or at the end of spec's epic, spec's session reads every repository's table 3 on GitHub's main, and the author decides and numbers the new rows (R81 spec). Whatever else a session has for spec goes the same way, as a row of table 3: what a repository took with a move to a tag, spec sees by its submodule.
- A component's card in architecture 3 spec is the summary; the repository's own `docs/architecture.md` is the detail. When the detail changes what the card says — what the component does and does not do, its data, its links — the card changes too, by the same route.
- A repository moves to a newer tag of spec on purpose, in a task of its own: its commit says why, and the lines of its CLAUDE.md and RUN.md that name the tag change with it; it is no entry of the log (R160 spec).

## Hard rules

- **Devcontainer only.** All work happens inside the devcontainer (`.devcontainer/`). If `NOVATRAIL_DEVCONTAINER` is not `1`, you are on the host: stop and ask the author to "Reopen in Container". "The change is only documents" is no reason to go on. The one exception is a cloud session of Claude Code that the author started for the task: it works without the container, and its report names every check it could not run. The orchestrator's executor runs by `docker exec` in its repository's container; the orchestrator's own holds the host's Docker socket, root on the host, and opens no code but NovaTrail's (R156 spec).
- **Exact versions only.** No `latest`, floating tags or ranges. Images are pinned by tag and digest, tools by exact version, each where it is installed: an `ARG` in `.devcontainer/Dockerfile`, a literal in `.devcontainer/devcontainer.json`. An archive the Dockerfile downloads is checked against its sha256, an `ARG` beside its version for each architecture, before it is unpacked (R34 spec). A system package apt installs comes from a snapshot of the Ubuntu archive alone — a source of its own whose URI names the snapshot's ID, an `ARG` beside the list of packages — and the ID is raised by hand like a version (R40 spec).
- **Production images.** An image that runs in production — a Cloud Run service or its jobs — is a static Go binary, built with `CGO_ENABLED=0` and `-trimpath`, on `gcr.io/distroless/static-debian13:nonroot` pinned by its digest: no shell, no package manager, not root, and nothing in it beyond the binary and what the repository's own decisions put there. Docker Hardened Images are not used. Any other runtime comes only by an amendment to R105 spec, to the same bar. NovaTrail publishes no image: the base holds files under GPL-2 and MPL-2.0, which a published image would distribute. A service's release carries its signed binary and the `Dockerfile`; whoever deploys builds the image around the binary that `release-verify` accepted and keeps it in a private registry of their own (R105 spec).
- **Language.** The work plan — RUN.md and the tables of `run/` — and spec's cross-repository plan, COORDINATION.md, are in English, terse, for the session; in Russian are the bodies of tasks in table 1 and in `run/TASKS.md` (R155 spec), the section «Порядок» of COORDINATION.md and the epic archives `docs/plan/` (R154 spec). The documents under `docs/` are in English, for the Claude Code session that reads them (R143 spec): a document still in Russian stays so until a task of its own translates it, by `tools/translation/README.md` spec and with `just -f spec/justfile translation-check` (in spec, `just translation-check`). A quote of a source stays in its own language, and the prefixes О-, П-, Т-, Д and В stay Cyrillic. Everything else — README.md, CLAUDE.md, AGENTS.md, RULES.md, code, comments, schema descriptions and prompts — is in English (R14 spec), and so are the normative texts for authors: the module format in spec's `format/`, the widget protocol and the guides (R42 spec). Commit messages, issues and a pull request's title and description are in English, a person's too, and a session's are terse, for the session that reads them; reports to the author are in Russian (the 2026-11-17 amendments to R14 spec).
- **No learners' data in the repository.** No learner's name, work, handwriting, voice or photo, no email or account identifier — not even in examples, which are synthetic.
- **No secrets in the repository.** Keys and tokens live in environment variables or a secret manager, never in a committed file.
- **Release files are verified.** A file of a NovaTrail release — a binary, an archive, an index — enters code or CI only once `just -f spec/justfile release-verify` has accepted it (in spec, `just release-verify`), where it enters NovaTrail; a package of `@altnovatrail` from npm, once `release-verify-npm` has accepted the lock file, in CI of the pull request that changes it. From then on the digest the check pinned holds the file — the lock file's `integrity`, the chain of digests from a pinned index — and nothing checks its signature again: `module-kit`'s library checks none (R77 spec).
- **Licenses.** Everything is Apache-2.0 — code, documents and the official modules' content (R12 spec, R20 spec). One exception is the code of conduct in `.github`, the Contributor Covenant 2.1 with its placeholder for how to report filled in, under that text's license, CC BY 4.0 (R22 spec). Add only dependencies whose licenses are compatible with Apache-2.0. A development or CI tool that never ships and puts none of its own code into what ships — a checker, a browser for tests — may carry another OSI-approved license or free terms, for open source or for everyone, only as a named exception, in the license check or in the decision that brings it in; free terms, only while no image or archive that NovaTrail publishes holds the tool and NovaTrail can be built, run and deployed without it. The sign-in service's mark on its own button, Google's "G", ships in `app` only as the service's brand rules allow, named in `app`'s NOTICE as its trademark (R12 spec). The licenses of third-party modules are open (О-10).
- **Loading.** What an interface awaits from an asynchronous load is a skeleton (R168 spec), never a blank or a spinner.
- **Learners' data first.** Anything that touches a learner's data is read against privacy spec before it is proposed.
